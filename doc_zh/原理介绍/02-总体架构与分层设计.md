# 第二章 · 总体架构与分层设计

## 2.1 分层不是选择，而是需求的推论

很多项目的分层是"风格"，OpenCode 的分层是"推论"。推论的起点是第一章末尾埋下的那个硬需求：**同一个会话，必须能同时被终端、浏览器与桌面应用观察和驱动，且三端画面一致**。把这句话展开成约束，分层的形状就被唯一确定了。

约束一：业务逻辑只能写一次。若核心逻辑分散在三处，三端迟早出现行为分叉——终端里能做的操作浏览器做不了，或者同一个权限弹窗在两端的语义不同。因此必须存在一个唯一的领域内核，三种前端只是它的不同视图。

约束二：内核不能依赖任何一个前端，也不能依赖任何一种传输。否则"桌面版要加一个内核功能"就会牵连 TUI 的构建，"把 server 跑进 Cloudflare worker"就会拖上 Node 专属依赖。内核必须对"谁在调用它、通过什么协议调用"完全无感。

约束三：类型必须端到端贯通。前端消费的每一个事件、调用的每一个端点，其类型必须与内核实现共享同一份定义，不能靠手写接口文件同步——手写同步必然腐化。

这三条约束分别推出了三件事：需要一个与传输无关的领域核心（core）；需要一组"声明一次、处处复用"的契约（schema 与 protocol）；需要把三者组合起来的产品层（tui、app、desktop 与 sdk）。剩下的工作只是给每一层找到最合适的实现技术。本章的任务，就是沿这条推论链把整个仓库的骨架讲清楚。

## 2.2 Monorepo 布局与依赖方向

OpenCode 是一个 Bun workspaces 加 Turborepo 的 monorepo，根 package.json 的 workspaces 覆盖 packages/*、packages/plugins/*、services/*、packages/console/* 与 packages/stats/*。目录里的包可以按职责分成五组。

第一组是**契约与内核**：packages/schema（全部跨进程契约的 zod/Effect Schema 定义：会话、消息、工具、配置、agent、错误、事件等）、packages/core（领域行为与持久化，src 下有一百多个模块，是全仓库最大的包）、packages/ai（自研的模型协议层，第七章专述）、packages/codemode（受限的 TypeScript 程序执行环境，第六章专述）。

第二组是**传输与组合**：packages/protocol（用 effect 的 HttpApi 声明公开 API）、packages/server（HTTP 服务器与运行时装配）、packages/client（由 protocol 生成的 TypeScript 客户端，禁止手改）、packages/sdk（把 client、core、server 组合成可编程形态）。

第三组是**用户形态**：packages/cli（命令行入口与服务生命周期）、packages/tui（终端界面）、packages/app（浏览器端共享界面）、packages/desktop（Electron 桌面应用）、packages/session-ui 与 packages/ui（跨形态复用的会话组件与基础组件）、sdks/vscode（VS Code 插件）。

第四组是**支撑设施**：packages/util（通用工具，含 Effect 辅助）、packages/effect-drizzle-sqlite（Effect 化的 drizzle SQLite 封装）、packages/httpapi-codegen（把 HttpApi 契约编译成各客户端形态的代码生成器）、packages/http-recorder、packages/patchmark、packages/merman、packages/theme、packages/identity、packages/function 等。

第五组是**外围**：packages/console/*（SST 云端管理面）、packages/web（官网与文档站，Astro）、services/*（www、changelog、files、update 等云端服务）、packages/plugins/figma（官方插件示例）、specs/（设计文档）、script/（仓库脚本）。

分组只是地图，真正保证架构不被腐蚀的是**依赖方向约束**。根 AGENTS.md 明确要求运行时依赖保持有向：schema 位于最底层，被所有人依赖但不依赖任何人；core 与 protocol 依赖 schema；server 依赖 core 与 protocol；client 只依赖 schema 与 protocol；sdk 负责"组合 client、core 与 server"——注意"组合"这个词，sdk 不实现业务，它只是把三块积木拼成一个可编程的整体；tui、app、desktop、cli 等入口处在最外层。这个约束让第二章 2.1 节的三条需求在工程上可执行：任何人提交一个让 core import tui 的改动，都违背了"内核无感前端"的推论，审查时会被拒绝。

依赖方向还可以画成一张最小图：

```
            ┌────────────┐
            │   schema   │   契约层：定义一次，处处复用
            └─────┬──────┘
        ┌─────────┼──────────┐
        ▼         ▼          ▼
  ┌───────┐  ┌──────────┐  ┌────────┐
  │  ai   │  │   core   │  │protocol│
  └───┬───┘  └────┬─────┘  └───┬────┘
      └──────►┌───┴────────────┴───┐
              │       server       │  装配层
              └─────────┬──────────┘
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │  client  │◄──│    sdk   │   │ tui/app/ │
  │ （生成物）│   │ （组合）  │   │ desktop  │
  └──────────┘   └──────────┘   └──────────┘
```

## 2.3 Schema 先行：契约层的哲学

分层架构最容易失败的地方不是层本身，而是**层与层之间的接缝**。接缝上的类型若是两份独立维护的定义，漂移只是时间问题。OpenCode 的解法是 schema 先行：所有跨进程交换的数据结构——会话消息、工具定义与结果、权限请求、配置文档、MCP 事件、PTY 事件、文件差异——全部在 packages/schema 里定义一次，用 zod/Effect Schema 声明，运行时做校验，编译期出类型。

这一做法的收益要在三个场景里才看得完整。场景一，**wire 序列化**：前端从事件流收到的每个事件载荷，都用 schema 校验后再进入渲染，坏数据在边界处被拦截，而不是在 UI 深处引发神秘崩溃。场景二，**存储**：SQLite 里的会话与消息行同样按 schema 解码（第四章），老版本写入的数据在新版本代码里要么兼容要么显式迁移，不存在"数据库里藏着没人认识的字段"。场景三，**代码生成**：packages/client 的全部代码由 httpapi-codegen 从 HttpApi 契约生成，生成物里的类型与 schema 一一对应，CONTRIBUTING.md 明确要求改协议后必须运行生成命令、禁止手改生成物。

值得强调一个容易混淆的词：这里的 schema 是**数据契约**，不是数据库 DDL。数据库表结构由 drizzle 表定义承载（core/src/session/sql.ts、core/src/event/sql.ts 等），而 schema 包定义的是"在进程之间流动、在存储中休眠的数据长什么样"。两者在第四章会配合出现：表列存序列化后的 JSON，读出时经 schema 解码。

## 2.4 Effect：为什么整个后端构建在一个函数式运行时上

翻开 packages/core 的任何一个文件，几乎都会看到 Effect 的影子：服务用 Context.Service 声明，装配用 Layer.effect，控制流用 Effect.gen。对一个 TypeScript 项目来说，引入一个完整的函数式效果运行时是重大决策，必须给出工程理由，而不能是品味偏好。

理由藏在 agent 的工作负载里。第一章说过，agent 循环的每一次迭代都是"长时间流式 IO + 并发工具执行 + 随时可能被用户打断"的组合。用朴素的 async/await 写这种代码，会立刻撞上四个经典难题：其一，**中断传播**——用户按 Esc 后，正在流式传输的请求、正在执行的子进程、正在写入的数据库行，谁停谁不停？裸 async/await 里"取消"是一个约定俗成的标志位，靠自觉检查；Effect 里中断是一等公民，fiber 被打断时未完成的清理仍会执行。其二，**资源安全**——子进程、文件句柄、数据库连接必须在所有退出路径（正常、出错、被打断）上释放，Effect 的 Scope 把"获取即登记、退出即释放"变成类型保证。其三，**重试与超时的组合**——模型调用需要"指数退避重试、总时长上限、按错误类型区分可否重试"，这类策略在 Effect 里是可组合的调度器，而不是散落各处的 while 循环。其四，**并发原语**——信号量（Semaphore）、PubSub、Deferred、Queue 这些原语被 agent 的各个子系统反复使用，例如插件注册用 Semaphore 串行化激活（core/src/plugin.ts），事件总线用 PubSub 分发给订阅者（core/src/bus.ts）。

一个最能说明问题的实例：SessionStep.attempt 把收尾段放进 uninterruptibleMask（packages/core/src/session/runner/step.ts:138），含义是"即使 fiber 在此刻被中断，屏蔽区内的代码也会跑完"——用户按 Esc 打断模型流的瞬间，Step 事件与工具结算仍然落库。这个保证若靠手写 try/finally 表达，在中断、错误、正常退出三条路径的排列组合下极难做对；在 Effect 里它是一行声明。此外，错误建模也受益：DrainResult 这样的可辨识联合类型迫使调用方穷尽处理每一种循环出口（第二章 2.1 提到的类型即文档），Effect 的类型化错误通道让"哪些错误会被向上传播"成为函数签名的一部分。

当然，Effect 有代价，2.9 节会正面讨论。这里先记住结论：**agent 的负载特性（流式、并发、可中断、资源密集）与 Effect 的能力集（中断、作用域、调度、并发原语）几乎是逐点对齐的**，这不是巧合，而是选型时对着需求清单挑的。

## 2.5 Location 模型：一棵服务子树就是一个工作目录

OpenCode 架构里最独特的抽象是 Location。定义：**一个 Location 是一个工作目录实例及其完整的 Effect 服务子树**。服务器可以同时托管多个 Location——用户可能同时打开三个仓库、或在同一个仓库的不同 worktree 里各挂一个会话组，每个 Location 有自己的会话集合、配置视图、文件监听、MCP 连接与权限状态，彼此隔离。

实现机制值得细看。core 里的每个子系统都是一个 Context.Service（例如 "@opencode/SessionRunner"，packages/core/src/session/runner/index.ts:44），用 Layer.effect 提供实现；这些 Layer 再经 makeLocationNode（来自 @opencode/util/effect/app-node）包装成节点挂进依赖图。服务之间不是直接 import 单例，而是从 Effect 上下文里按需获取——这意味着**同一份服务代码，在不同 Location 里是不同实例**，各自持有各自的配置与状态。比如压缩服务（session/compaction.ts）的 Settings（auto/keep/precompute/buffer）在每个 Location 里可以不同；权限服务的已保存规则（permission/saved.ts）按 Location 各自持久化。

Location 之上有全局层：makeGlobalNode 构造全局服务节点（bus.ts 的导入清单可见），全局层承载跨 Location 共享的设施——数据库（database/database.ts）、事件日志（event-logger.ts）、凭据（credential.ts）、模型目录（models-dev）等。于是整个运行时的形状是一棵两级树：根是全局服务，每个 Location 是根下的一棵子树。packages/server/src/routes.ts 的 makeRoutes 里，applicationServiceNodes 列出约二十九个应用级服务节点（routes.ts:57-88），AppNodeBuilder.build（routes.ts:117-164）按部署选项替换实现后构建整张图——数据库路径可以换、PTY 实现可以换、事件持久化策略可以换、文件监听可以换、MCP 的 clientInfo 可以换（125-155 行的替换清单），simulation 模式甚至能把整组后端动态换成模拟实现（165-173 行），这是第十四章测试体系的基石。

用一张图概括两级树与替换机制：

```
                     AppNode（全局）
        ┌────────┬───┴────┬─────────┬──────┐
     Database  Bus    Credential  ModelsDev …
        │        │        │        │
  ┌─────┴────────┴────────┴────────┴─────┐
  │            Location A                │
  │  Session / Tool / Permission / MCP   │
  │  Config / Watcher / Snapshot / …     │
  └──────────────────────────────────────┘
  ┌──────────────────────────────────────┐
  │            Location B（另一个 worktree）
  │  同一套服务定义，另一组实例与状态        │
  └──────────────────────────────────────┘
```

Location 模型的深层价值是**把"多租户"从一个运维概念变成了类型结构**。任何服务的实现者在编写时就知道自己活在"某个 Location 的上下文"里，要么声明依赖 Location 服务获取自己的目录与身份，要么显式提升到全局层。实例的生灭（用户打开/关闭一个目录）由 location-lifecycle 与 location-activity 等模块管理，服务的按目录查找由 location-service-map 提供。没有这个抽象，"同时管三个仓库"会在每个子系统的代码里变成一串 if。

## 2.6 一次用户请求的全旅程

把分层串起来的最好方式是走一遍完整链路。用户在 TUI 输入一句话，之后的旅程是：

1. **TUI 层**：输入被 prompt 组件捕获（packages/tui/src/component/prompt/），经编辑器与自动补全处理后，通过 client 包生成的方法发出 HTTP 请求。client 是生成物，类型来自 protocol。
2. **server 层**：请求进入 effect HttpApi 的路由，命中 session 相关 handler（packages/server/src/handlers/session.ts 或 message.ts）；中间件链先做鉴权（middleware/authorization）、再把请求归属到正确的 Location（middleware/session-location），业务错误经 middleware/schema-error 统一成协议错误格式。
3. **core 层**：handler 调用 Session 服务，输入写入收件箱（session/inbox.ts），然后触发 SessionRunner.drain（runner/llm.ts:64-221）。drain 先做陈旧结算（崩溃恢复，第三章），再 advanceToStep 处理控制项，最后进入 runStep → SessionStep.attempt。
4. **ai 层**：attempt 组装请求（session/model-request.ts），经 packages/ai 的 LLM 客户端发起流式调用；事件逐个返回，被 publisher 投影成会话事件。
5. **工具执行**：解析出工具调用后，Tool 服务执行（core/src/tool.ts 的 snapshot().execute），权限断言在执行前发生（第八章），工具结果写回历史。
6. **广播与回灌**：每一步都通过 Bus 发布事件（core/src/bus.ts），server 的事件流端点（event-feed.ts）把事件推给所有订阅的前端；TUI、Web、桌面据此渲染同一画面。工具结果同时回灌进下一轮模型请求，循环继续，直到某个出口条件满足。

注意这条链路的**信息流与控制流分离**：控制流沿"前端 → server → core → ai"单向向下，而信息流（事件）沿"core → Bus → event-feed → 所有前端"广播向上。这意味着任何前端都不直接"调用"另一个前端能看到的状态，一切状态变化都以事件形式对全体订阅者可见。三端一致的根源就在这里：它们消费同一份事件流与同一套消息投影。

## 2.7 分层的代价与边界

诚实的架构评估必须包含代价。Effect 的成本有三：学习曲线陡峭（generator 语法、类型层数深、错误通道复杂），栈深度与运行时开销高于裸 async（对 IO 密集型负载影响小，但精神负担真实存在），生态内调试工具链不如主流 async 生态成熟。monorepo 分层的成本有二：跨包改动要按依赖方向排队（先 schema 后 core 再 server），提交粒度变大；生成物（client）引入"改协议必须重新生成"的纪律成本。

但这些成本换来的是可量化收益：业务只写一次、三端天然一致、崩溃恢复有类型保证、测试可以用 simulation 模式整体替换后端。对一个人内核年迭代极快的产品，**复用与一致性的价值远大于分层的摩擦**——这个判断本身就值得读者在自己的项目里重新核算，因为分层收益与形态数量成正比，与团队规模无关。

分层还有清晰的**边界感**：core 不 import server；ai 不依赖 core；schema 不依赖任何人。每当想跨过边界时，正确的做法是把共享物下沉（沉到 schema 或 util），而不是加一条反向依赖。仓库里 packages/util 与 packages/schema 之所以体积庞大而性质单纯，正是这种"下沉式"演化的结果。

## 2.8 Effect 深入一层：Layer、Node 与依赖图的语法

2.4 节讲了"为什么用 Effect"，这里补"Effect 在本仓库怎么用"。三个原语构成装配语法的骨架。**Context.Service**：每个服务是一个 tagged 类型（如 "@opencode/SessionRunner"），服务的消费者在 Effect 环境里按 tag 取用——类型系统因此知道"这个函数需要哪些服务"，依赖缺失是编译错误而不是运行时崩溃。**Layer**：服务实现的构造器，Layer.effect(Service, Effect.gen(...)) 的模式在 core 里重复上百次（plugin.ts 顶部的 layer 定义是标准样例）；Layer 可组合（Layer.provide 把依赖接进去）、可复用、可替换——替换正是 AppNodeBuilder 做的事。**Node**：仓库自建的抽象（@opencode/util/effect/app-node），makeLocationNode 把一个服务 Layer 包装成"可挂树的节点"，makeGlobalNode 造全局节点；Node 之间形成两级树（全局根、Location 子树），LayerNode 类型（@opencode/util/effect/layer-node）标注"可替换节点"。三个原语的分工：Service 定义"是什么"、Layer 定义"怎么造"、Node 定义"挂在哪"。装配层的 AppNodeBuilder（core/src/effect/app-node-builder.ts）遍历节点清单，对每个可替换节点应用 replacements，最后一次性构建出运行时图。

这套语法的实际威力在**测试装配**上最明显：测试代码用与生产完全相同的节点清单构建图，只替换几个边界节点（内存数据库、伪 LLM），得到的测试对象与生产对象结构同一——第十四章的 kernel 测试因此可能。对比"手工 new 一堆服务"的传统装配，图式装配把"系统由哪些部分组成"变成了数据（节点清单），可审查、可替换、可复制。

## 2.9 替换机制案例研究：一次部署选项的旅程

把 2.5 的替换机制具体化。以"数据库路径"为例走一遍：CLI 启动时确定数据目录（Global 服务）→ 构造 options 传入 createRoutes → makeRoutes 的 AppNodeBuilder.build 在 Database 节点上应用替换（换成指向该路径的 SQLite 后端——sqlite.bun.ts 或 sqlite.node.ts 按运行时选择）→ core 里的所有服务从上下文取到的 Database 都是这个实例。整个过程 core 的业务代码零改动——"数据库在哪"是部署事实，不是业务事实。同类的替换点还有：PTY 实现（本地原生绑定或远端）、事件持久化策略（写库或跳过——测试用）、文件监听（Watcher 的目标目录）、MCP 的 clientInfo（标识自己的身份字符串）、配置来源（第九章的四种来源）。每个替换点的共同形状：**接口在 schema 或 core 定义，实现在装配时绑定**。这本质上是依赖倒置原则在运行时维度的重演——只是"依赖注入容器"换成了类型化的 Node 图，注入时机从应用启动细化到节点构建。

## 2.10 包生态的分工哲学：为什么有这么多小包

初见仓库的人常问：packages/util、packages/schema 为什么不并进 core？答案在 2.7 的边界感之外还有一条经济学理由：**包边界是复用的最小单位**。packages/util 被 core、server、tui、console 多方依赖，若并进 core，前端想用一个小工具就得拖上整个领域内核；packages/schema 被所有层依赖，若并进 core，client 生成物的依赖图会引入 core（违背 2.2 的依赖方向）。小包策略的本质是把"公共依赖"从"领域内核"里剥离，让依赖图保持扇形而不是全连通。代价是包管理的琐碎（每个包的 package.json、tsconfig、构建配置），Bun workspaces 与 Turborepo 把这个代价压到很低。同类逻辑也解释了 packages/effect-drizzle-sqlite 的存在——它是"Effect 化的 drizzle 封装"这样的通用设施，不属于领域逻辑，因此独立成包，甚至可以回馈社区。观察一个 monorepo 的包划分是否健康，有一个速判法：看每个包的"离开成本"——把一个包单独发到 npm 是否自然？OpenCode 的 schema、util、effect-drizzle-sqlite、httpapi-codegen 都通过了这个测试，而 core 显然通不过（它本来就不该通过）——这个不对称正是分层健康的标志。

## 2.11 本章小结

本章完成了三件事：从"三端一致"的需求推论出分层形状（2.1-2.2）；解释了 schema 先行与 Effect 选型的工程理由（2.3-2.4）；给出了 Location 模型与运行时装配的完整图景（2.5），并用一次请求的全旅程把各层缝合（2.6）。从这里开始，后续各章都是对这个骨架的纵深剖切：第三章剖开 core 里最大的器官（会话引擎），第四章剖开持久层，第五章剖开上下文管理，第六至八章剖开执行三角，第九至十一章剖开可扩展性与传输面，第十二至十三章回到外围，第十四章收束。建议读者此刻对照第二章 2.2 的依赖图，在仓库里任选三个文件走一遍 import 链，验证依赖方向约束在真实代码中的成立——架构的可靠性最终由每一次代码审查维护，而不是由图维护。
