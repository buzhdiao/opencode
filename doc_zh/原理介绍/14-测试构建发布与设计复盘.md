# 第十四章 · 测试、构建发布与设计复盘

## 14.1 测试矩阵：一个快迭代项目的质量面

OpenCode 迭代极快（doc_zh/README 开篇即警告"行号会漂移"），快迭代项目的质量只能靠测试纪律兜底。仓库的测试分两处：packages/core/test/ 与 packages/server/test/，且 CONTRIBUTING.md 明确"校验在受影响的包内进行（cd packages/core && bun run test && bun typecheck），仓库根不跑测试"——测试与被测代码同包放置，turbo 的任务图按依赖裁剪测试范围。core 的测试文件清单本身就是一份功能索引：bus.test.ts（事件总线的核心语义）、bus-session-routing.test.ts（事件按会话路由）、bus-unpersisted.test.ts（未持久化事件的行为——第四章瞬时/持久双通道的测试面）、database.test.ts、database-drizzle.test.ts、database-migration.test.ts（迁移正确性——第四章 4.5 的纪律兑现）、credential.test.ts 与 credential-lock.test.ts（凭据与并发锁）、codemode.test.ts 与 codemode/ 目录（受限解释器）、command.test.ts、agent.test.ts、catalog.test.ts（目录）、app.test.ts、artifact.test.ts、boot-work.test.ts（启动）、browser-attach.test.ts 与 browser-idle.test.ts（浏览器集成）、config/ 目录（配置）、effect/ 目录与 effect-app-node-platform.test.ts（Effect 基建——装配层的测试）、aisdk.test.ts 与 aisdk-native.test.ts（第七章的 AI SDK 兼容轨）。server 侧另有 event、middleware、handler 级的测试。

这个矩阵揭示的测试哲学是**按风险分配深度**：迁移（毁数据）、凭据（泄秘密）、总线（全局正确性）、解释器（执行不可信代码）这四类"单点故障面"有独立命名测试甚至专项目录；而"效果层"（effect/）测试装配语义，因为装配错误的表现是深层运行时失败，最难人肉排查。

## 14.2 Kernel 测试思想与 simulation 模式

第二章 2.5 留了一个伏笔：AppNodeBuilder 的 simulation 替换（routes.ts:165-173）可以"动态换上模拟后端"。现在兑现它的意义。OpenCode 的测试策略不是传统的"mock 单个依赖"，而是**kernel 测试**：把整个服务图组装出来（真实的服务定义、模拟的外部边界——数据库用内存库、LLM 用录制或伪实现、文件系统指向临时目录），然后在图的入口注入输入、在出口断言行为。这与内核测试同构：不测函数，测系统在边界条件下的行为。

支撑设施有三。其一，packages/ai/src/testing.ts——AI 层的测试面（伪 LLM 事件流、可编程的响应序列），让会话循环的测试可以精确控制"模型说什么"（什么时候发工具调用、什么时候断流、什么时候溢出——第三章六种 Outcome 的每一个都能被确定性触发）。其二，tui/src/simulation/——前端模拟模式（不连真 server 也能跑界面，供 UI 开发与视觉回归）。其三，packages/http-recorder——HTTP 录制器（真实 provider 交互录制成 fixture，测试回放；外部 API 的测试金标准是录制回放而不是打真 API：稳定、免费、无速率限制）。三者合起来覆盖"模型流、HTTP 边界、整图装配"三个测试深度，加上 e2e 回归（boot-work、browser-attach 这类启动与附着测试是 e2e 形态的缩小版），构成"单元—模块—整图—端到端"的完整金字塔。

## 14.3 构建与发布：多形态产品的分发工程

构建面的事实清单：包管理是 Bun（根 bunfig.toml、bun.lock），任务编排是 Turborepo（turbo.json），原生依赖用 patches/ 目录维护补丁。发布产物是**多形态矩阵**：npm 包（@opencode/cli，npm/pnpm/yarn 均装）、Homebrew（两个 tap：官方 formula 与快速更新的 anomalyco/tap）、Arch（pacman 稳定版与 AUR beta 版）、mise、Nix（flake.nix）、安装脚本（curl 安装到 $HOME/.opencode/bin）、桌面应用（macOS 双架构 dmg、Windows exe、Linux deb/rpm/AppImage，packages/desktop）。README 的安装段完整列出了这个矩阵。CI 侧（.github/workflows/）：check.yml（lint/typecheck）、release.yml（发版流水线）、还有一批机器人工作流（triage-close-issues 等）与多语言 README 维护（bot-docs-locale.yml）。

多形态矩阵的工程含义是**一次内核、多次壳封装**：CLI 壳、桌面壳（Electron）、云服务壳（SST 定义在 sst.config.ts 与 infra/）都是内核的分发皮。发布工程的难点不在打包本身，而在**矩阵的一致性**：同一个 commit 产出的 npm 包、brew bottle 与桌面 dmg 必须行为一致——这依赖第 14.2 的测试在发布前全绿，以及版本号的单一出处（CHANGELOG.md 与 release 流水线）。

## 14.4 httpapi-codegen 深读：代码生成器的工程

packages/httpapi-codegen/src/index.ts 的模块注释值得逐条解剖，它概括了一个成熟代码生成器的全部要件。发射器有五个：compile()（反射 HttpApi 契约，收集每个端点的输入/成功/错误 schema，做**可移植性与命名校验**）；emitEffect()（内联生成"契约 + 类型 + 客户端"全套 Effect 代码）；emitEffectImported()（生成"适配层"——引用既有 Api/分组/端点变量，不重建契约，给已是 Effect 项目的用户）；emitEffectShape()（只生成类型层，即 client 的 AppApi 接口来源）；emitPromise()（零依赖 Promise 风格客户端，types/client-error/client/index 三件套）。

三个关键设计尤其值得迁移。第一，**命名与遍历顺序解耦**：生成符号名一律由分组/端点标识推导，"新增端点不会改名无关产物"——生成器的头号公敌是输出不稳定（diff 噪声、下游误改），名字只从语义推导不从顺序推导是稳定性的根基。第二，**可移植性判定**：schema 的注解/检查/编码链能否被生成器复现，决定该端点走内联生成还是权威导入——不是所有 schema 都值得展开成代码，判定边界把生成物控制在"能正确生成"的子集。第三，**产物清单**：所有生成文件以 prettier 格式化，并用清单文件记录上次产物以便清理过期文件——生成物的垃圾回收，靠清单而不是靠人记忆。加上"命名空间迁移时生成 deprecated 别名保兼容"（第十一章提过），这个生成器展示了代码生成的完整生命周期：编译、发射、格式化、清单化、兼容迁移。

## 14.5 Code Mode 的 stdlib：给模型的"标准库"面

packages/codemode/src/stdlib/ 值得单独一节：它定义了模型写编排程序时**可见的标准库面**。这个面的选择是安全与表达力的平衡点：给得太多（fs、net）等于打开沙箱（第六章 interpreter 的限制失效）；给得太少，模型被迫用工具调用做本地逻辑，Code Mode 的收益缩水。OpenCode 的取向是纯函数式工具集（数据处理、集合操作、字符串处理），凡涉及世界副作用的（读文件、发请求）一律走工具命名空间——**stdlib 是纯计算面，工具是世界面**，两面的边界就是沙箱的边界。tool-schema.ts 与 tool-runtime.ts 保证"模型代码里看到的工具签名"与"引擎真实执行的签名"永远一致（同一 schema 两个消费方向），tool-error.ts 保证工具错误在程序内是可捕获的值而不是异常逃逸。

## 14.6 设计复盘：五个正确决策

全书机制已解剖完毕，现在做复盘。五个我认为最正确的决策（附论证）：

**决策一：内核与传输的彻底分离**（第二章）。三端一致不是靠 UI 同步，而是靠"业务只在 core 写一次 + 事件先落库再广播"。这个决策的成本是分层纪律，收益是每一种新前端（VS Code 插件、GitHub 集成、SDK 嵌入）的接入成本趋近于零——served 的"协议即代码"让接入面自动生成。

**决策二：Effect 作为全后端的运行时**（第二章 2.4）。中断、作用域、并发原语与 agent 负载逐点对齐；uninterruptibleMask 一行代码表达"结算必须完成"的安全性质。代价（学习曲线、调试面）真实存在，但换来的是**性质的可表达性**——很多保证在裸 async 里"写不出来"，只能"约定出来"，而约定会腐化。

**决策三：事件溯源的收件箱与陈旧结算**（第三、四章）。崩溃恢复从"尽力而为"变成"幂等批处理"，靠的是状态先行落库与 append-only 事实流。这是全书可迁移性最强的设计——任何长任务系统（爬虫、流水线、机器人）都可以直接套用。

**决策四：压缩的预计算套利**（第五章）。识别出"缓存折扣 × 提前计算"的时序矛盾并正面解决，是全仓库最漂亮的一个成本优化：它证明了 agent 的资源管理可以像数据库的查询优化一样被推导，而不是拍脑袋调参。

**决策五：权限的三值 effect 与 fail-closed 基线**（第八章）。ask 作为独立语义显式存在，让"需要人"成为可配置、可审计的一等策略；缺省全拒的基线让规则的演化方向必然是"逐步放行"而不是"逐步收紧"——安全系统的默认演化方向应该是保守的。

## 14.7 设计复盘：三个代价与未竟之事

诚实的复盘也要记录代价。**代价一：Effect 的认知门槛**。贡献者要同时掌握 TypeScript、Effect、领域逻辑三层，CONTRIBUTING 需要引导新人跨这道坎；错误堆栈的可读性是持续的痛点。**代价二：生成物纪律**。client 与 migration.gen、schema.gen 的"改协议必须重新生成"依赖人的自觉与 CI 检查，生成清单虽自动化了清理，但"忘了生成就提交"的 PR 仍会出现。**代价三：双扩展面的维护负担**。MCP 与插件两套扩展面有部分重叠的语义（工具注入、生命周期），重叠处的不一致（比如两面对"工具目录"的归属）是文档与实现要持续对齐的地方。未竟之事的线索在代码里公开可见：edit 工具的 LSP TODO（edit.ts:256-258）、experimental/ 下的语音与实验传输——OpenCode 把未完成明确标出来而不是藏起来，这本身是工程文化的优点。

## 14.9 测试金字塔的深度对照：从函数到整机

14.1-14.2 的矩阵可以整理成一张"深度对照表"，每个深度对应不同的故障捕获能力与维护成本：

| 深度 | 载体 | 捕获什么 | 成本 | 实例 |
| --- | --- | --- | --- | --- |
| 单元 | 纯函数测试 | 算法错误 | 低 | wildcard 匹配、slug 生成 |
| 模块 | 服务级测试 | 状态机错误 | 中 | bus.test、credential-lock |
| 集成 | 多服务协作 | 接缝漂移 | 中高 | bus-session-routing、database-migration |
| 整图 | kernel + simulation | 装配与端到端语义 | 高 | boot-work、simulation 模式 |
| 录制回放 | http-recorder fixture | 协议兼容回归 | 中（一次性录制） | provider 协议变更 |
| 类型层 | typecheck | 结构性破坏 | 极低（编译器代劳） | bun typecheck 全包 |

表的读法有两处关键。其一，**类型层是免费的单元测试**——Effect 的类型化错误通道与 schema 校验把大量"参数传错、状态漏处理"的 bug 拦在编译期，这是 2.4 选型决策在测试侧的分红；其二，**录制回放是外部世界的缓存**——provider 的真实交互录成 fixture 后，协议兼容回归不再依赖真 API（稳定、免费、无速率限制），OpenCode 用 packages/http-recorder 生产这类 fixture。金字塔的策略含义：下层宽而便宜（单元与类型层跑在每次提交），上层窄而精准（整图与录制回放跑在关键路径）。与 kernel 测试思想（14.2）合起来看，OpenCode 的测试策略可以概括为**"类型系统挡结构错误、kernel 测试挡语义错误、录制回放挡协议漂移、多形态发布前全绿"**——四道闸各拦一类故障。

## 14.10 发布工程的风险清单

14.3 的发布矩阵有典型的失败模式，把它们写成风险清单（每条附缓解手段）。**风险一：矩阵不一致**——npm 包与桌面版行为分叉。缓解：版本号单一出处、release 流水线同一 commit 全矩阵构建。**风险二：原生绑定差异**——PTY 与 SQLite 的平台差异（sqlite.bun/node/workerd、editor-zed-sqlite 的 bun/node 双文件）。缓解：运行时差异全部收口到 "#sqlite"、"#pty" 的导入映射（database/migration.ts 的 supportsForeignKeyToggle 是能力探测的样例），差异面可枚举。**风险三：安装路径污染**——安装脚本写入 $HOME/.opencode/bin，与包管理器安装冲突（README 特意提醒移除旧版本）。缓解：安装文档明示路径、包管理器 formula 统一入口。**风险四：升级与数据迁移的交错**——用户从 v1 升级时既有版本跨越又有数据迁移（第四章 v1-migration）。缓解：迁移随服务挂载、有进度界面（migration handler 与 TUI 的 migration-overlay）、可观测可重试。**风险五：补丁漂移**——patches/ 目录的原生依赖补丁在依赖升级后失效。缓解：锁文件（bun.lock）固定依赖版本，补丁与依赖同升级。这份清单的共同主题：**发布工程的本质是把"构建一次的确定性"扩展到"分发 everywhere 的确定性"**，每个风险都是确定性在某条传送带上的断点。

## 14.12 CI 的组织：门禁、发布与自动化的分工

14.3 提到 CI 工作流，这里把它组织成一张职责表（工作流名来自仓库调研）：check.yml 是**门禁流**（lint、typecheck、受影响包的测试——PR 合并前的正确性闸门）；release.yml 是**发布流**（构建多形态产物、打版本、上传分发渠道）；机器人流是**治理自动化**（triage-close-issues 等 issue 治理、bot-docs-locale 维护多语言 README）。三种流的分工遵循 CI 设计的经典原则：**门禁要快**（check 在几分钟内给结论，否则开发者绕过它）、**发布要全**（矩阵完整性优先于速度）、**治理要省**（机器人做的是确定性重复劳动，不值得人花时间）。用户侧的 GitHub Actions 集成（doc_zh/components/07 的 /oc 触发体系）不属于仓库自身 CI，而是"给用户仓库用的 CI 产物"——两者共用 GitHub Actions 平台但目的不同：前者保障 OpenCode 自身的演化，后者把 OpenCode 的能力注入用户的工作流。这个区分提醒一个 CI 设计的通用视角：**CI 不只是测试跑在云上，而是"项目自治规则的机器化"**——门禁流机器化的是代码规范，机器人流机器化的是社区治理规范，用户集成机器化的是协作规范。读一个项目的 .github/workflows/ 目录，读到的其实是这个项目的自治宪法。

## 14.13 规范资产：specs、CONTRIBUTING 与 AGENTS.md 的治理作用

质量不只来自测试，还来自**规范资产的分层**。仓库里有三个层级的规范载体。specs/（设计文档，specs/v2）承载**架构决策的书面记录**——为什么这么设计、备选方案是什么，新贡献者从这里获得"决策的为什么"而不是"现状的什么"；CONTRIBUTING.md 承载**贡献流程的规范**（怎么装环境、怎么跑校验、什么贡献受欢迎——LSP 与 formatters 是官方点名的低门槛贡献面、models.dev 是 provider 元数据的正确入口、生成物勿手改），它把第二章的依赖方向等架构约束翻译成贡献者可执行的指令；AGENTS.md 承载**给 AI 协作者的项目规范**（依赖方向、live TUI 测试的服务发现方式）——这个文件本身就是 OpenCode 产品哲学的自举示范：仓库用自己的产品机制（指令系统，第九章）管理自己的开发。三层规范的读者不同（架构评审者、贡献者、AI 代理），内容有分工但相互引用，避免同一规则的多头维护。规范资产的维护成本常被低估：过时的规范比没有规范更糟（误导贡献者），因此规范文件与代码同 PR 演进的纪律（改了协议必须同步 CONTRIBUTING 的生成命令说明）与测试同等重要。一个可操作的判断标准：任何"只在某人的脑子里"的规则都是负债——要么写进三层规范之一，要么承认它不是规则。

## 14.14 复盘的方法论附录：如何评估一个 agent 架构

把 14.6-14.7 的复盘推广成一份可复用的评估清单——读者可以用它评估任何 agent 系统（包括自己的项目）。**维度一：循环的健壮性**——有没有步数上限、崩溃恢复、断流续写？（第三章的六种 Outcome 是及格线）**维度二：上下文的预算化**——窗口管理是显式的（水位线、压缩、预算表，第五章）还是隐式的（满了就报错）？**维度三：权限的完备性**——缺省拒绝？命令级解析？人可批准？规则可审计？（第八章的公理清单）**维度四：状态的持久性**——进行中的状态落库吗？崩溃后能结算吗？事件可回放吗？（第三、四章的公理）**维度五：扩展的隔离性**——坏扩展能拖垮宿主吗？扩展的生命周期可控吗？（第六、十章）**维度六：传输的契约性**——协议是声明的还是散落的？客户端是生成的还是手写的？（第十一章）**维度七：可观测性**——状态变化是结构化事件吗？故障可重现吗？（第十六、十四章）七个维度各有一组可观察的判据（引用各章机制），打分不需要看代码行数或 star 数——看机制在不在。这份清单的最后一个用途是自我提醒：**架构评估的对象是机制的存在性，不是实现的优雅性**——一个丑但存在的崩溃恢复，胜过一个漂亮但缺失的；工程评估的第一问永远是"有没有"，第二问才是"好不好"。

## 14.16 质量面与开发节奏的匹配

最后一个工程话题：质量设施如何匹配快节奏开发。OpenCode 的迭代速度（doc_zh/README 的行号漂移警告）意味着质量面必须在"快"与"稳"之间动态平衡，可观察的平衡手段有三。**手段一：测试分层随风险漂移**——14.9 的金字塔不是静态的：出过事故的机制升层（迁移测试在数据事故教训后加厚——4.5 的纪律），稳定多年的机制降层（跑得快的类型检查扛走大部分回归）。**手段二：模拟资产的复利**——14.2 的 simulation、testing.ts、http-recorder 都是"一次投入多次复用"的资产：录一次 provider 交互，之后的每次协议回归都免费；这类资产的投入时机是"第一次需要真环境调试时"——早了浪费，晚了重演成本已经付过一次。**手段三：门禁的成本核算**——CI 门禁（14.12）的每一分钟延迟都是全体开发者的税，门禁里放什么要有"漏检代价除以检测成本"的算账：typecheck 与单元测试性价比最高（秒级、拦截结构性错误），整图测试性价比中等（分钟级、拦截装配错误），e2e 性价比最低（分钟到小时级、只拦关键路径）——OpenCode 的"包内测试加根不跑测试"（CONTRIBUTING 的原则）正是成本核算的结论。三条手段合起来的立场：**质量设施是投资组合，不是道德义务**——按风险与收益配置，随节奏调仓。这个立场与 14.14 的评估清单互补：评估别人看机制存在性，配置自己看投入回报率。

## 14.17 结语：读码的方法论

最后回到方法论。本套文档的写法是"先立模型、再看结构、后验咬合"：第一章的循环模型预言了三大机制，后续章节逐一到代码里找到对应物。读者若只带走一样东西，建议带走这个读码姿势：面对一个复杂系统，先从它的**工作负载特性**（流式、并发、可中断、资源约束）推导出它**必须**具备的性质（终止性、可恢复、权限、预算），然后去代码里验证这些性质被哪些结构承载——结构与需求的咬合处，就是架构的真意。OpenCode 的源码是一片好林区：服务图清晰、注释诚实、常量有理由、未竟之事公开标记。愿本套文档成为进入这片林区的等高线图，而不是替代行走的缆车——真正的理解只发生在你亲手打开 packages/core/src/session/runner/llm.ts 的那一刻。
