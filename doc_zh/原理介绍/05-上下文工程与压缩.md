# 第五章 · 上下文工程与压缩

## 5.1 上下文预算：agent 引擎里的"内存管理"问题

第一章的二次律证明了上下文占用必然逼近窗口上限，本章处理这个必然性。先把问题的三个约束摆清楚。约束一是**硬容量**：模型窗口 $W$ 是常数（各家模型从 128k 到 1M 不等），超过即请求被拒。约束二是**软成本**：输入 token 单价乘以每步上下文长度，成本随历史累积二次增长（1.4 节）。约束三是**缓存杠杆**：主流 provider 对"与上次请求相同的前缀"提供大幅折扣，但前缀一旦改变，缓存全部失效——这 third 约束最隐蔽也最关键，它意味着**改变历史的操作有隐藏代价**：在中间删一段历史，其后所有 token 的缓存折扣清零，下次请求按全价计费。

这三个约束合起来，把上下文管理变成一道经典的资源管理题，与操作系统的内存管理同构：窗口是物理内存，历史是地址空间，压缩是换页，缓存是 TLB——甚至"提前在后台准备好换页内容"都对应预取。OpenCode 的压缩模块（packages/core/src/session/compaction.ts，千行级）就是这道题的解法，它的每个常量都能在约束上找到位置。

解法的第一步是选择**压缩产物**的形状。OpenCode 把检查点（checkpoint）定义为"历史摘要 + 最近一段原文"：旧的交互被总结成一条摘要消息，最近的若干 token 的原文原样保留。为什么不全部总结？因为细节的保真度随总结距离衰减——模型自己三步前刚写的代码，摘要里一行"修改了 X 模块"可能丢失关键细节，而最近交互正是模型下一轮最需要的上下文。"摘要 + 保留尾部"是在保真与省空间之间的分段决策：越新的信息越完整，越旧的信息越浓缩，这正是一切分层存储（寄存器—缓存—内存—磁盘）共同的形状。

## 5.2 触发判定：due 与水位线

压缩不是"满了才压"，而是**提前触发**——等到真满了，压缩本身（一次模型调用）都会因超长而失败。触发判定 due（compaction.ts:437-446）回答"现在该不该压"，其核心是水位线公式：估算当前上下文占用，与"上限"比较，超过即触发。上限由 calculateCeiling（compaction.ts:1160-1168）计算，规则是**预留 15% 的窗口、且至少留出 16k token 的空隙**。写成公式，设当前占用为 $u$，窗口为 $W$，则触发条件近似为：

$$u \ge W - \max\left(0.15 \cdot W,\ 16\,k\right)$$

两个数各有含义：15% 是比例缓冲，覆盖"下一步模型输出加上工具结果"的常规增长——一步之内上下文的自然膨胀不应触及上限；16k 是绝对下限，防止小窗口模型按 15% 算出的余量小到压缩来不及发生。比例加绝对值的组合是资源管理的通用手法（TCP 拥塞控制、数据库检查点阈值同款），比例项自适应大窗口、绝对项兜底小窗口。

占用估算 $u$ 本身值得交代：它不是一个精确值而是**保守高估**——历史消息按 token 计数、图片按 1500 token、PDF 按 2000 token 折算（compaction.ts:151-152），窗口未知的模型按 200k 假设（compaction.ts:137）。高估是刻意的选择：估算误差方向的后果不对称——低估导致压缩太晚、请求被拒、整步失败；高估只是多压一次、多花一点摘要成本。**不对称误差必须往便宜的方向偏**，这是所有工程估算的第一原则。

## 5.3 预计算：把缓存当仓库用

compression 里最精妙的设计是后台预计算（precompute，compaction.ts:348-404）。观察：水位线触发压缩的那一刻，往往正处于 prompt 缓存的最佳命中区间——最近几步的上下文前缀高度重叠，缓存是热的。但压缩一旦执行并替换历史，缓存立刻失效（5.1 约束三）。于是有个时序矛盾：**最需要省钱的时刻做了最破费的操作**。

precompute 的解法是把"做摘要"与"换入摘要"解耦：当距离上限还有 60k token 时（预计算提前量），就趁缓存还热，**在后台把摘要写好存起来**（写摘要本身用一次便宜的调用，且此时缓存命中使它更便宜）；等水位线真正触发时，直接换入现成摘要（usePrecomputed，compaction.ts:411-435），不再现场调用模型。用成本模型核算：设摘要成本为 $c_s$，无缓存版价格为 $p$、缓存版为 $\epsilon p$（$\epsilon \ll 1$），预计算多付的是一次"提前调用"的缓存价 $\epsilon p \cdot c_s$，省下的是触发时刻的全价 $p \cdot c_s$ 加上"压缩期间会话被阻塞"的时延成本。只要 $\epsilon$ 足够小（provider 的缓存折扣普遍在一个数量级以上），预计算严格占优。这个设计把 5.1 的第三个约束从"被动接受"变成"主动套利"，是整个模块里最值得学习的一手。

Settings（compaction.ts:42-50）暴露四个参数：auto（是否自动压缩）、keep（保留尾部的 token 预算，默认 15000）、precompute（是否启用预计算）、buffer（缓冲参数）。默认值 {auto: true, keep: 15000, precompute: false}（compaction.ts:269）经过 State 模式注册（core/src/state.ts，第九章），可被配置与插件改写——但默认关闭 precompute 这个事实也说明团队对"提前花小钱省大钱"仍留了谨慎：预计算依赖 provider 缓存语义的稳定性，语义一变，套利可能变亏损。

## 5.4 收缩策略：deliver 的逐级退让

压缩不是总一次成功。摘要模型可能拒绝请求（历史实在太长，连摘要调用都超限），可能因 payload 超限被拒（字节级超限，典型是图片）。deliver（compaction.ts:615-703）是这套失败退让的实现，核心是一个**逐级瞄准**算法：目标"当前占用"从 85% 开始，被拒则降级到 70%、再 50%、再 35%，直到成功或见底。把它写成递推：

$$u_{k+1} = \rho_k \cdot u_k, \quad \rho_k \in \{0.85, 0.70, 0.50, 0.35\}$$

为什么逐级而不是一步到位？因为**压缩的目标值本身影响质量**：目标越松（85%），保留的原文越多、摘要越短、信息损失越小；目标越紧（35%），丢失越多。算法的隐含假设是"第一次尝试大概率成功"（正常水位线触发时 85% 就够了），失败才逐级加深——成功路径的质量损失最小化，失败路径的收敛性有保证（级数单调递减且有下界）。这种"从最乐观开始、按失败信号加深"的策略，与第六章 edit 工具的三级降级匹配、第九章配置的逐级回退同构，可以说是 OpenCode 的通用错误恢复模式：**乐观优先，失败驱动的退让链**。

对"payload too large"类失败，deliver 走另一分支：字节超限多半是图片造成的，此时改发**纯文本**摘要请求（剥离二进制载荷）——摘要本来就不需要原图。识别这个分支靠的是 packages/ai 的 isContextOverflowFailure（compaction.ts:680 的消费点）：错误分类层把"上下文溢出"从一般错误中辨出来，压缩模块据此分派策略——错误分类的粒度直接决定恢复策略的精度，第七章会再回到这一点。

## 5.5 历史文本化：flattenAndDropOldest 的降级阶梯

deliver 定下目标后，真正改写历史的是 flattenAndDropOldest（compaction.ts:717-785）。它把"要被摘要覆盖的旧历史"压成一条文本消息，但压缩不是一刀切，而是**按交互从旧到新逐级降级**：最老的交互保留完整原文；更老的裁剪工具输出（保留命令与结论，去掉长 stdout）；再老的连工具输出也去掉（只留调用痕迹）；再老的只留用户文本；最老的整条省略。最新交互**绝不降级**——它是模型下一步最需要的上下文。

这个阶梯的排序值得推导：降级的判据是"信息对下一轮决策的边际价值"。最近的交互价值最高（模型正在处理的事情）；用户文本的价值高于工具输出（用户的意图必须永远保留，工具输出可以重新获取——大不了再跑一次命令）；交互的时间顺序代表"被后续交互引用的概率"递减。于是降级顺序 = 价值顺序，每级降级都从当前价值最低的信息开刀。这与操作系统的页面置换（LRU 的思想：最久未用的最可能不再需要）在精神上完全一致，只是"价值"的定义从时间局部性换成了对话结构。

## 5.6 组装侧：系统提示、指令与 recent-text

压缩管理历史的"存量"，组装决定每一步请求的"增量"。一次请求的上下文由几层堆叠：系统提示、指令基线、历史（含检查点）、新输入。系统提示是 runner 的常量模板（packages/core/src/session/runner/prompt/system.txt），定义 agent 的身份、工具使用规范与行为约束；system-prompt.ts（session/system-prompt.ts）负责其装配与插件可定制点（第十章插件可以对 system prompt 织入内容）。指令基线（AGENTS.md 等）通过 SessionModelRequest.baseTranscript 注入（compaction.ts:998-1005 的消费点可见），位置在系统提示之后、历史之前——指令属于"半永久层"，既不该被压缩掉（它是行为契约），也不该每步重读（它由 instruction-state 缓存与门控）。recent-text.ts（session/recent-text.ts）负责"最近文本"的界定——哪些内容属于 5.1 说的"必须保留原文的尾部"，与压缩的 keep 参数衔接。

组装侧还有一个第五步的伏笔：指令装载是异步的，指令基线的就绪状态由 instruction-state.ts（session/instruction-state.ts）管理，未就绪时输入保持 pending（第三章 3.3 的 InstructionState.prepare）。这条门控保证了一个重要不变量：**任何进入模型的请求，其指令层要么完整、要么显式缺失（无指令可用），绝不存在"装了一半"**。

## 5.7 压缩的会话级视角：检查点序列与 Compacted 结局

回到第三章的状态机，现在可以完整解释 Compacted 结局了。压缩触发后，这一步的结局是 Compacted，runStep 重新走组装——新上下文里检查点替代了旧历史，请求体积回落到目标值。检查点本身作为消息落库（第四章的表），它有类型标记，投影层（前端渲染）把检查点显示为"历史已折叠"的分界；会话的 step 计数不回退——压缩改的是上下文空间，不是时间轴。用户手动 /compact 走 advanceToStep 的控制项分支（llm.ts:130-174），与自动压缩共享 flatten 机制但参数不同（手动压缩通常更激进，因为用户主动要求释放空间）。

压缩与子代理的交互也值得一笔：子代理会话有自己的独立压缩（每个会话独立做预算管理），主会话收到的是子代理的总结文本，天然就是"子代理历史的压缩产物"——**子代理机制在结构上就是一次预压缩**：与其让主上下文装下全部探索细节，不如让子代理消化细节、上交结论。这解释了为什么 OpenCode 用 general 子代理处理复杂搜索：搜索产生海量中间输出，若在主循环内进行，二次律的成本极其陡峭。

## 5.8 压缩的原子性：检查点替换不能开天窗

压缩改写历史，而历史同时正被读取（模型请求的组装、前端的投影、回放协议的补发）。替换必须原子：要么检查点完整生效，要么历史原样保留。实现层面的原子性由两件事保证：存储侧，检查点作为**新消息**追加落库（第四章 append-only 公理——压缩不改写旧消息，而是写入替代物并推进投影基线），追加是单事务原子操作；语义侧，后续组装只从"当前检查点 + 之后的消息"取材料，旧消息成为不可见的历史层（仍在库里，供审计与回溯）。这个"标记替代而非物理删除"的设计还有一个妙用：用户对压缩结果不满意时，理论上可以从旧历史层重建（未物理删除意味着可恢复）；压缩本身失败（模型拒绝、超时）时历史自然无恙——失败路径零破坏。对比"就地重写历史"的朴素实现：失败时历史可能已经残缺，且永远失去原始信息。**不可变事实 + 可变指针**再次胜出——这与第四章事件溯源是同一原理在压缩场景的重演。

## 5.9 多模态预算：非文本内容的折算艺术

5.2 提到图片按 1500 token、PDF 按 2000 token 折算，这里展开这组数字背后的方法论。问题的本质是：非文本内容没有天然的 token 计数（tokenizer 只处理文本），但它们真实地占用窗口预算（provider 在请求层按内部规则折算）。引擎需要一个**保守的本地估算**以驱动水位线与预算决策。折算值的推导逻辑：图片占用与分辨率相关（provider 多按像素或分块计），1500 是中分辨率图的典型量级，低分辨率图低估无害（高估侧的余量被 5.2 的不对称原则吸收），超高分辨率图的实际占用可能更高——因此折算是下界偏估，配合水位线的余量兜底；PDF 的 2000 折算按"页均文本量"估算，同样偏保守。比具体数字更重要的是三个原则：其一，**折算表是策略不是事实**——provider 的真实折算规则会变，本地估算只需保证"水位线不晚触发"的单调正确性；其二，**多媒体内容是压缩的头号目标**——payload too large 分支（5.4）改发纯文本的逻辑成立，正是因为图片对"下一轮决策"的边际价值通常低于其占用；其三，**折算发生在两个层**——工具输出的图片在规范化阶段就压缩转码（第六章 normalizeImages，物理减小），进上下文后按折算表计预算（逻辑计量），物理与逻辑双重治理。

## 5.10 与操作系统内存管理的系统对照

本章的机制与操作系统的内存管理存在惊人的结构对应，把对照表摆出来有助于建立"上下文管理即资源管理"的直觉，也便于把 OS 领域的成熟结论迁移过来。

| OS 内存管理 | OpenCode 上下文管理 | 对应关系 |
| --- | --- | --- |
| 物理内存 | 模型窗口 $W$ | 硬容量上限 |
| 页面 | 消息/交互 | 管理粒度 |
| 换页（swap） | 压缩检查点 | 换出到慢介质（摘要） |
| 预留水位 | calculateCeiling 的 15%/16k | 触发提前量 |
| 预取（prefetch） | precompute | 提前备好换出物 |
| LRU 降级 | flatten 的从旧到新阶梯 | 价值递减的淘汰序 |
| TLB 缓存 | prompt 缓存 | 前缀命中折扣 |
| 缺页中断 | 上下文溢出错误 | 资源耗尽的信号 |
| OOM killer | OutputLimit 两次判失败 | 兜底放弃 |

对照不是修辞游戏：OS 领域几十年的结论可以直接借用。比如"预取要靠预测"（precompute 的 60k 提前量相当于预取距离，距离过长浪费、过短失效）；"换出粒度影响抖动"（压缩粒度过小会频繁触发——抖动 thrashing 在上下文场景的表现就是"压缩-再溢出-再压缩"的循环，15% 余量是反抖动参数）；"缓存局部性是折扣来源"（相邻步前缀重叠即时间局部性）。带着这张表读 compaction.ts，每一行代码都能找到它在 OS 教科书里的亲戚。

## 5.12 预算分配：一次请求的四级预算表

水位线管总盘，但一次请求内部的预算怎么分？把 5.6 的组装层做一次预算核算。设可用预算为 $B$（窗口减去安全余量），一次请求的四大项是：系统提示（$S$，常量，system.txt 加装配）、指令基线（$I$，项目相关的常量层）、历史（$H$，压缩后的存量）、本轮增量（$\Delta$：新输入加预期输出加工具结果预留）。约束是 $S + I + H + \Delta \le B$，而四项的可压缩性完全不同：$S$ 与 $I$ 是行为契约（不可压），$H$ 可压缩（压缩模块管），$\Delta$ 半可控（工具输出有上限、输出有 OutputLimit）。由此推出分配策略的三条公理：**固定层优先锁定**（$S$、$I$ 先占，它们小而不可让）；**历史层是弹性缓冲**（$H$ 吃掉剩余的大部分，水位线触发时压缩它）；**增量层有硬顶**（$\Delta$ 的工具输出受工具层裁剪、输出受 OutputLimit，防止一步把弹性层吃穿）。这个四级模型还解释了两个跨章设计：为什么指令就绪门控（5.6）重要——$I$ 层的迟到会打乱 $S+I+H+\Delta$ 的既定划分，门控保证划分在第一步就稳定；为什么 keep 默认 15000（5.3）——它就是 $H$ 中"最近原文"子层的预算常量。预算表也可以反向用于诊断：上下文溢出时先查哪层失控（$S$ 恶化？指令过长？工具输出漏裁？），比盲目调阈值有效得多。

## 5.13 压缩质量的评估：怎么知道摘要没丢关键信息

压缩是模型调用，其质量（摘要保真度）没有确定性判据，但工程上仍有可管理的评估面。第一，**结构判据**：检查点必须完整保留"用户目标、当前进度、未决问题"三类骨架信息——这三类丢失会立即表现为模型行为的断裂（忘了自己在干嘛、重复已做的事）；提示词模板（三类智能续写提示词同源的提示工程）把骨架要求写死，摘要模型的输出被模板约束。第二，**行为判据**：压缩后的第一步输出与压缩前的意图轨迹对比——若模型开始重复压缩前的动作（重读同一文件、重做同一修改），是摘要丢信息的强信号。第三，**保底机制**：最新的交互绝不降级（5.5）保证了即使摘要质量差，模型手里仍有最近的事实原文——摘要只覆盖"远期记忆"，近期的可靠性不依赖摘要质量。第四，**用户可见性**：检查点在界面上显式呈现（"历史已折叠"），用户可以感知压缩发生并在必要时手动介入（/compact 或恢复）。这四条合起来是一个诚实的立场：**摘要质量无法前置保证，只能通过结构约束、行为监测与保底设计把最坏情形的破坏力限制住**。这与可靠性工程对"不可测组件"的标准处理（隔离、降级、监控）完全同构。

## 5.15 指令与提示词的层次模型：从常量到变量的梯度

第五章讲了很多"预算"，这里补一个与预算正交的视角：进入模型的内容按**变化频率**分层，层次决定缓存友好性与治理方式。第一层是**常量层**：系统提示（system.txt 的模板加装配），整个进程生命周期不变——缓存命中的黄金前缀；第二层是**半常量层**：指令基线（AGENTS.md 体系），随项目演化、会话内不变——改动它会使该会话后续所有请求的缓存失效，因此热重载（9.5）对进行中的会话要谨慎处理边界；第三层是**会话层**：历史与检查点，每步追加但前缀保持——追加式设计（第四章）正是为了保前缀；第四层是**步层**：本轮新输入与工具结果，每步全换——永远处于上下文尾部，不影响缓存。四层的梯度给出两条工程规则：**越不变的放越前**（缓存按前缀命中，常量层必须先于可变层出现——这也解释了 5.6 组装顺序为什么是系统提示、指令、历史、输入）；**改半常量层要付全量缓存税**——指令编辑的时机会影响成本，批量改指令最好在会话间隙做。这个分层模型还揭示了一个常见反模式：把高频变化的内容（比如时间戳、动态状态）拼进系统提示——每步都污染第一层，缓存全废。治理口诀：**常量在前、追加在后、变化居中、动态殿后**，背下这十六个字，上下文组装的大部分缓存问题都能预防。

## 5.17 长会话的退化模式与应对策略

超长会话（几十步、跨天）有一组可观察的退化模式，本章的机制是它们的对症药，汇总成一张"症状—机理—应对"表。**模式一：目标漂移**——模型逐渐偏离最初目标，做起了相邻但不相关的事。机理：最初目标在旧历史里，被压缩成摘要后权重衰减（5.13 的骨架信息稀释）。应对：把目标物化——写入 todo 工具（6.12 的会话内元数据）或项目文件，让目标每步都出现在近期层（5.1 的"尾部保留"覆盖它）。**模式二：重复劳动**——反复读同一文件、重跑同一命令。机理：工具结果被裁剪（5.5 的降级阶梯）后模型忘了已经读过。应对：适度放宽 keep 预算（Settings，5.3），或引导模型把关键发现写入文件。**模式三：越改越坏**——修改引入新问题，修复又引入新问题。机理：上下文里堆满了中间失败状态，模型的注意力被错误历史污染。应对：手动 /compact（3.3 的控制项——把失败细节压掉、保留结论），必要时回滚快照（13.3）后重新出发。**模式四：上下文费暴涨**——成本随步数陡增。机理：水位线没触发（估算偏小）或缓存失效（前缀被破坏，5.15 的分层被违反）。应对：检查压缩设置与 precompute（5.3），排查是谁在改动上下文中部。这张表的价值在于把"长会话不好用"的模糊抱怨分解为四个可诊断、可应对的具体机理——上下文工程的最后一步永远是把它翻译成用户可操作的策略。

## 5.19 延伸：压缩与检索的边界——"记不住"的正确答案

最后补一个容易混淆的边界问题：模型"忘了"某段信息时，责任在压缩还是在检索？判据是**信息是否曾经进入过上下文**——进过而后被摘要稀释（5.13 的保真衰减）是压缩问题，从未进过或需要重新获取是检索问题（13.14 的四条路径）。两者的应对完全不同：压缩问题调预算与降级策略（5.3、5.5），检索问题调工具使用（让模型重新 grep、重新 read）。工程上的启示是把"记忆"分层对待：**持久事实写文件或 todo**（外部化——不占窗口预算且永不失真）、**工作事实留在会话层**（压缩管）、**可重取事实靠检索**（每次需要时重新获取——上下文里不长期占用）。三层的划分让"上下文里该放什么"有了清晰的决策树：能外部化的外部化，必须留的留，其余靠检索。这个决策树也解释了 OpenCode 众多设计的协同逻辑——todo 工具、AGENTS.md 指令、快照、检索四路径各自服务一层，压缩只是其中一层的守门员。上下文工程的完整图景至此闭合：**它不是一个模块，而是一组机制对"记忆"的分工**。

## 5.20 本章小结

本章把"上下文管理"从玄学还原为工程：三个约束（硬容量、软成本、缓存杠杆）定义问题；水位线（15%/16k）定义触发；预计算（60k 提前量）利用缓存做套利；deliver 的 85/70/50/35 定义失败退让；flatten 的五级阶梯定义价值排序；组装侧的三层堆叠（系统提示、指令、历史）定义增量。所有常量（15000 的 keep、200k 的默认窗口、1500/2000 的多媒体折算）都在"不对称误差往便宜方向偏"的原则下取值。读完本章应当能回答：为什么压缩不能等到满了再做？为什么摘要要提前算？为什么降级要从最旧的信息开始？——这三个问题的答案分别是：压缩本身也是模型调用、缓存热度是套利机会、边际价值随时间递减。下一章转向循环的另一半：工具——模型的手，以及约束这只手的运行时。
