# 第十六章 · 诊断、可观测性与故障排查

## 16.1 可观测性的第一性原理：事件即日志

传统应用的可观测性靠三件套（日志、指标、追踪），OpenCode 的可观测性有一个结构性优势：**系统的一切有意义状态变化本来就是事件**（第四章 Bus 的持久化事件），因此"可观测"不需要额外的埋点体系——事件流本身就是最完整的日志。这个优势的来源是架构性的：三端一致（第二章）要求一切状态变化经 Bus 广播，广播即落库（4.4），于是"发生过什么"在库里永远可查。event-logger.ts（core/src/event-logger.ts，routes.ts 装配清单中）承担事件日志的专门职责（持久化与检索面）。事件即日志的推论还有：**日志的结构化是免费的**（事件本来就过 schema 校验，天然结构化——grep 一段 JSON 日志的痛苦在这里不存在）；**日志与回放统一**（排障时重放事件序列就是重放故障现场，4.9 的回放协议直接可用）。当然也有事件日志覆盖不了的面：进程内的决策细节（为什么选了这个 provider）、性能剖面（哪一步慢）、进程外世界（子进程的 stdout）——这些由 16.2 的追踪与 16.3 的状态面补充。可观测性设施的分层可以概括为：**事件流管"发生了什么"，追踪管"为什么这么久"，状态面管"现在什么状态"，模拟面管"能不能重现"**。

## 16.2 请求追踪：跨层的因果链

一次用户操作横跨 TUI → server → core → ai → provider，排障的第一问题是"这条链上哪一环出的问题"。request-tracing.ts（server/src/request-tracing.ts，11.5 提过）的职责就是给请求分配追踪标识并沿调用链传播——handler 日志、core 服务的错误、ai 层的错误记录都携带同一标识，事后按标识聚合出完整因果链。追踪与事件的配合是诊断的常用组合拳：事件流给出"什么时间发生了什么"（会话视角），追踪给出"这个请求经过了谁、每步多久"（请求视角）——两者按会话与时间窗关联，可以拼出完整的故障叙事。ai 层的错误分类（7.10 的决策表）在追踪链的末端给出结构化结论（错误类别与恢复标记），把"模型调用失败"这类模糊症状翻译成可归因的类别。追踪的边界也要诚实：进程外段（provider 内部、MCP 服务器的内部）不可见，只能从协议层的表现推断——这是任何客户端系统的可观测性天花板，MCP 的 stderr 收集（10.2 的 EXIT_WAIT 遗言机制）是把天花板往上顶一点的努力。

## 16.3 状态面：服务健康的一站式观察

排障的第二类信息是"当前状态"（区别于"历史事件"）。状态面的设施清单：service-status.ts（server/src/service-status.ts——服务健康状态，CLI 的 opencode service status 的后端）；server-info.ts（server 信息——地址、版本、形态）；handlers/debug.ts（调试端点——运行时的内部状态检查面）；service 发现与凭据注入（根 AGENTS.md 的 live TUI 测试一节描述的 opencode service get password——开发期 TUI 直连已装服务的通道）。状态面的设计要点是**分级暴露**：连接状态（server 活着吗、我连的是谁）、装配状态（Location 树里哪些服务在、哪些失败——AppNodeBuilder 的构建结果可查）、领域状态（MCP 连接池的连接健康、插件激活的 Generation 与 Failure、会话的 drain 状态）。分级的价值在排障路径上：先看连接（最外层故障最常见——server 没起、密码不对）、再看装配（服务没起来——插件失败、迁移没跑）、最后看领域（业务层的具体问题）。前端对状态面的消费：TUI 的 dialog-status（12.6 的状态对话框）、dialog-mcp（连接池健康）、migration-overlay（迁移进度，第四章）。状态面与事件面的关系是互补而非重复：事件面是流（历史），状态面是快照（现在）——"现在"永远可以从"历史 + 投影"推导，但直接读快照比推导便宜得多。

## 16.4 常见故障模式与排查路径表

把前十四章的机制串成一张"症状 → 机制 → 排查路径"的对照表，这是本章最实用的一节：

| 症状 | 涉及机制 | 排查路径 |
| --- | --- | --- |
| TUI 连不上 server | ServerAuth、配对 | service status 看进程 → 密码/配对（11.5）→ 端口与 CORS |
| 会话画面不同步 | 事件回放 | 检查订阅端点的 seq（4.9）→ Bus 落库 → 前端投影 |
| 模型调用失败 | 错误分类 | 按 7.10 决策表归类 → 传输层标记 → 凭据/限额（7.6） |
| 模型反复做同一件事 | 步数、续写 | 检查 max-steps 与续写阈值（3.4/3.6）→ 指令是否就绪（9.14） |
| 工具被莫名拒绝 | 权限求值 | 规则来源分层（8.11 的可解释性）→ 托管策略（8.9）→ 保存规则（8.4） |
| 配置改了不生效 | 合并与热更 | 优先级矩阵（9.10）逐层查 → 热重载事件（9.5）→ 来源标记（9.11） |
| MCP 工具不出现 | 汇入管线 | 连接健康（10.3）→ 汇入校验 errors（6.1）→ snapshot 过滤（6.2） |
| 启动变慢 | 渐进加载 | 启动路径（12.13）→ 插件激活区 → 模型目录刷新 |
| 升级后数据异常 | 迁移 | migration 状态（4.5）→ v1-migration 进度 → database-migration 测试口径 |
| 内存增长 | 内存治理 | 15.5 三类对号（上限、弱引用、生命周期）→ Location 泄漏 |

表的用法建议从上往下走（连接问题优先，业务问题殿后——外层故障的表象常常伪装成内层问题）。表的深一层的价值是**把排障知识编码为机制对照**：每个症状背后都是某个章节的机制在特定配置下的行为，理解机制比记住路径更重要——机制懂了，表里没有的故障也能推出路径。

## 16.5 崩溃取证：从遗留状态重建现场

进程崩溃后的取证流程（第三章陈旧结算的后半程）值得完整描述。崩溃留下的现场特征：库里有一批 status=running 的消息与工具调用、可能有未完成的压缩、PTY 子进程可能还活着、收件箱里有未消费输入。取证的读法：事件日志的尾段给出崩溃前的最后动作序列（4.1 的结构化事件——比核心转储友好得多）；陈旧结算的改判结果（interrupted 标记）标出"崩在哪儿"（哪些调用未完成）；收件箱的未消费输入说明"用户最后想干嘛"；persistent-pty 的票据说明"还有哪些子进程可寻回"（13.6）。取证的产出通常是一份"崩溃时刻的会话快照叙事"：做到哪一步、哪些结果已落库、哪些在途——这个叙事既是恢复的依据（重启后 drain 从结算后的状态继续，3.8）也是事后分析的素材。取证流程的顺利运转依赖第三章的核心公理（状态先行落库），它可以反过来表述为一条设计检验：**任何在崩溃后会丢失的信息，都是架构没有承认的信息**——如果排障时发现某个关键状态"当时有但库里没有"，那是持久化设计的 bug，不是取证工具的不足。

## 16.6 调试面：开发者的一等公民

最后看调试体验本身。开发者（包括贡献者与插件作者）的调试面有三层。**运行时调试**：dialog-debug 与 devtools-bar（TUI 的调试面板，12.6）、debug handler（16.3）、AI 层的 testing 设施（14.2 的伪 LLM 流——本地复现"模型说了什么"不用打真 API）。**重现调试**：simulation 模式（routes.ts 的动态替换，14.2）让故障在受控环境重现；http-recorder 的录制回放让 provider 交互逐字节重现；事件回放让会话级故障重演（4.9）。**降级调试**：浏览器与桌面形态的 devtools（packages/desktop 的 Electron 开发者工具）、TUI 的日志面。三层调试面的共同理念：**故障重现的保真度决定排障效率**——事件回放保真度最高（同一事件序列必然同一投影），录制回放次之（同一响应序列），模拟最低（受控近似）。调试面的还有一个隐性收益：调试设施的存在倒逼架构的整洁——能在 simulation 里跑的系统必然边界清晰（外部依赖全部可替换），调试体验与架构质量在这里形成正反馈。至此，性能（15 章）与诊断（16 章）两个工程横切面完成，## 16.7 三种用户视角下的诊断能力差异

诊断能力的可用性因用户角色而异，把三种视角的差异列清楚（它们决定了 16.3 状态面该暴露什么）。**终端用户视角**：能感知的是现象层（连不上、没反应、行为怪异），可用的工具是 CLI 状态命令（service status）、界面上的状态指示（TUI 的状态对话框与重连提示）、以及会话事件本身（界面显示的就是事件投影——"画面不对"本身就是诊断线索）。**插件与集成开发者视角**：能感知的是契约层（钩子没触发、连接被拒、权限断言意外），可用的工具是注册错误日志（6.1 的 errors）、Failure 与 Generation 查询（10.4）、模拟环境（14.2 的 simulation 加 testing 流）。**贡献者视角**：全量可用——事件日志的直接查询（第四章的表结构对贡献者透明）、request-tracing 的标识、kernel 测试的复现能力、database 直查（SQLite 文件可开）。三种视角的诊断能力递增，设计含义是**状态面的暴露要按视角分级**：给用户的现象层指示必须自解释（"连接已断开，正在重连"而不是错误码），给开发者的契约层信息必须可查（哪条规则拒绝了、哪个插件失败了），给贡献者的底层必须可开（库、日志、追踪）。可观测性的"用户分级"与第十二章的渐进披露同源：不同角色看不同深度的世界，但看的是同一个世界。

## 16.8 观测数据的保留与生命周期

观测数据本身是数据，也要服从第四章的生命周期治理。**事件日志**：持久事件按聚合落库（会话事件的保留与会话一致——删会话删其事件；瞬时事件不落库）。**追踪标识**：request-tracing 的数据是短命的（排障窗口内有效），不进长期存储——追踪的价值在"当时"，过期即弃。**服务状态**：快照型数据（service-status 的响应）无保留价值，读时现算。**错误记录**：结构化错误随事件落库的部分长期保留（16.5 取证依赖），进程内日志的部分滚动覆盖。**注册错误与 Failure**：插件失败记录保留到下次重载（Generation 切换时刷新——10.9 的占位语义），历史代的失败不堆积。保留策略的共同原则与 4.7 的数据治理一致：**按"谁在什么时候还需要它"定保留期**——事件与错误面向"事后审计与取证"（长保留），追踪面向"当下排障"（短保留），状态面向"现在"（零保留）。数据治理在观测面上的应用还有一个隐私维度（13.19 的立场）：事件与错误可能携带工作区内容片段（工具调用参数、错误上下文），它们的保留期与会话数据一致、不出本机——观测数据不出于隐私策略的特殊通道。

## 16.9 故障案例推演：三则复合故障的分析

用三个复合故障的推演把本章方法完整走一遍（案例为教学构造，机理全部来自前文机制）。**案例一：连接风暴**。症状：TUI 反复重连，server CPU 高。推演路径：先看 server 日志的追踪标识分布（16.2）——大量短连接；查 service-status——server 活着；回放事件流——无异常事件。归因方向转向客户端：TUI 的重连逻辑（12.2）在什么条件下会风暴？——回放协议的缺口补发（4.9）若遇 seq 异常（4.8 的水位回退——不该发生）会导致客户端无限重连。结论：先查 EventSequenceTable 的水位（4.8 论证过禁止回退），再查中间层代理对 SSE 的缓冲超时（传输面，11.3）。**案例二：压缩风暴**。症状：会话成本陡增，大量摘要调用。推演：按 15.2 的账本对账——发现是"压缩-再溢出"循环（5.10 的抖动）：水位线触发了压缩，但压缩后的目标占用仍高于水位（keep 预算过大或窗口估计偏小），下一步立即再触发。应对：核对 Settings 的 keep 与窗口元数据（models.dev 的目录是否过期——7.2）。**案例三：插件抖动**。症状：MCP 工具时有时无。推演：查代切换频率（10.16 指标五）——频繁 Generation 切换；查配置对比（10.3 的 isDeepStrictEqual）——某插件配置里的时间戳字段让每次对比都不相等。三则案例的共同方法论：**症状归资源（15.1）、资源归机制（前十六章）、机制归参数或代码**——每一步都有观测证据支撑，没有一步靠猜。

## 16.10 可观测性反模式

以反模式清单收尾（与 15.9 的风格一致）。**反模式一：日志与状态双轨漂移**——日志说 A、状态说 B（观测数据不同源），排障者被迫选边——OpenCode 的"事件即日志"（16.1）从结构上消灭了这个模式。**反模式二：埋点依赖自觉**——可观测性靠开发者记得打日志，漏打即盲区——事件驱动的架构把"打点"变成"发布事件"的副产品（第二章的三端一致需求强制了一切状态变化走 Bus）。**反模式三：排障要重现环境**——问题只在"某人的机器"上出现且无法复现——回放协议加录制回放（14.2）的目标就是让"重现"降级为"重放"。**反模式四：错误信息含糊化**——"操作失败，请重试"式的错误把归因成本转嫁给用户（6.13 的可行动反馈原则同样适用于服务端错误）。**反模式五：观测数据无主**——日志文件无限增长没人清理（16.8 的保留策略反例）。**反模式六：诊断工具比故障罕见**——出事时才发现没有现成的状态面（16.3 的设施必须平时就有、常态使用）。反模式的共同根源是把可观测性当"附加功能"而不是"架构性质"——OpenCode 的对立做法是把可观测性焊死在架构上（事件必须落库、错误必须分类、状态必须可查），让它成为"不实现就无法工作"的一部分。这是本章也是全书工程立场的最后一次重申：**好的架构让正确的事情成为唯一容易的事情**。

## 16.12 诊断工作流：把设施组装成流程

设施（16.1-16.6）与流程（16.4 的对照表）之间还差一层"工作流"——把设施按排障阶段组织成标准动作序列。**阶段一：界定现象**（谁观察到什么、何时开始、能否复现）——用事件流的最近窗口（回放协议补最后 N 分钟，4.9）与用户描述对齐时间线；**阶段二：分层定位**（16.4 的表从连接层往下走）——每一层用对应设施：连接层看 service-status、装配层看节点构建结果、领域层看事件与状态；**阶段三：证据收敛**（多源证据指向同一归因）——追踪标识聚合（16.2）、事件序列（16.1）、状态快照（16.3）三源交叉；**阶段四：假设检验**（最小复现）——simulation 重放（14.2）或最小化输入复现，证伪或证实假设；**阶段五：修复验证**（同一口径的前后对比，15.7 的第五步）与**阶段六：沉淀**（把新故障模式补进 16.4 的表、必要时补测试——14.9 的金字塔加一层）。六阶段工作流的本质是把排障从"艺术"变成"流程"——每次排障都产出两类资产：故障的修复与新故障模式的沉淀。对照 16.10 的反模式六（诊断工具比故障罕见），工作流的存在保证了设施被常态使用——**设施不用则腐，流程在用则常新**。

## 16.13 面向用户的诊断沟通：错误消息与自助路径

诊断不只是工程侧的事，用户侧的自助能力同样是可观测性的一部分。**错误消息的设计**——用户看到的每一条错误都应当包含四要素：发生了什么（现象）、影响了什么（范围）、用户能做什么（动作）、更多细节在哪里（入口）——TUI 的 dialog-error-details（12.6）展开细节、SDK 的异常携带结构化字段（11.12 的错误契约），都服务这四要素。**自助路径的分级**——常见问题（连不上、配置不生效、模型调用失败）给出一步式自助（service status、9.18 的五步路径、7.10 的类别对照），深水问题给出证据收集指引（如何导出事件、如何截图状态面）——自助路径的本质是把 16.4 的对照表翻译成用户语言。**升级路径**——自助无效时的最后一步是"带着证据求助"：事件导出、状态快照、复现步骤的标准化模板，让求助者与被求助者共用同一证据格式。用户侧诊断的深层价值：**每一次成功的自助都是一次信任积累**——用户对系统的可靠感来自"出了问题我知道从哪里看"，而不是"从不出问题"（后者不可能）。这与 8.17 的打扰成本论呼应：系统的透明性（可观测、可自助）是用户长期信任的基础设施。

## 16.14 观测体系的演进策略

观测体系自身要随系统演进（新机制出现、旧机制退役），演进策略有三条。**策略一：事件 schema 的演进服从全局契约纪律**（第九章的归一化加第十一章的别名保兼容）——新事件类型向后兼容地加入 Event 定义，消费者对未知事件类型宽容处理（投影的纯函数性质让未知事件可安全跳过）。**策略二：度量点的验收纳入机制验收**（15.14 的度量点清单）——新机制合入时自检"它的状态变化是否走 Bus、它的错误是否分类、它的容量是否有界"——观测性质是机制验收的一部分而不是事后补丁。**策略三：对照表的活文档化**——16.4 的故障对照表随新故障模式持续补充（16.12 阶段六的沉淀动作），表本身放在仓库内维护（与 specs 的治理作用一致，14.13）。演进策略的共同立场与 9.16 的配置演进一致：**观测体系是系统的一部分，它的演化也要有工程载体**。最终检验观测体系的成熟度可以用一个反问：如果明天系统出现一种全新的故障，从事件流到复现到归因的路径是否已在既有设施内？答案为是，则观测体系合格；答案为否，缺口就是下一笔观测投入的位置。

## 16.16 一次完整排障的叙事样例

用一段连续叙事把六阶段工作流（16.12）走一遍（叙事为教学构造，机理全部来自前文）。背景：用户报告"昨天下午起，我的会话经常卡在工具执行，改文件特别慢"。**界定现象**：时间窗（昨天下午起）、现象（工具执行阶段卡顿）、范围（单用户单仓库）——先回放该会话昨日下午的事件窗口（4.9 的补发），发现工具调用从"毫秒结算"变成"数秒结算"。**分层定位**：连接层正常（service-status 健康，16.3）；装配层正常（节点图无重建）；领域层聚焦——卡顿的是 edit 类工具。**证据收敛**：事件里 edit 的写授权从"静默放行"变成"每次弹窗等待"——用户此时不在窗口前，弹窗无人响应，工具在等批准（8.4 的 ask 分支阻塞）。为什么放行失效了？查权限事件与 PermissionSaved——昨天下午有一条 deny 规则被加入托管策略（8.9），其位置在保存的 allow 之前但匹配更宽，最后匹配生效（8.11 的求值），把原来的放行覆盖成了 ask。**假设检验**：用 simulation 重放该会话（14.2）加同样规则集，复现卡顿；去掉该规则，恢复流畅。**修复验证与沉淀**：与策略管理员确认规则意图（本意是 deny 某个具体目录而非全量 ask），修正规则的 resource 模式（8.5 的路径通配语义）；把"宽 resource 意外覆盖窄放行"补进 16.4 的对照表（16.12 阶段六）。叙事的读点：六阶段每一步都落在既有设施上（回放、状态面、事件、simulation），**没有一步需要超能力**——这正是可观测性体系成熟的判据（16.14 的反问句通过）。

## 16.17 诊断面的分寸：观测不变成监控

一个容易被忽略的分寸问题：诊断（排障导向）与监控（持续告警导向）是两种不同的观测姿态，OpenCode 的观测体系偏向前者（16.1 的定位），这个选择值得论证。诊断导向的特征：证据在本地、按需查询、面向"出事之后"；监控导向的特征：指标持续采集、阈值告警、面向"出事之前"。OpenCode 的选择理由：其一，单机本地产品没有运维团队盯仪表盘，持续告警没有接收方（注意力资源，15.1）；其二，事件即日志（16.1）已经把"事后可查"做到结构化极限，诊断导向的边际收益更高；其三，隐私立场（13.19）倾向数据不出本机，云监控与本地优先冲突。但分寸不是绝对——组织部署（17.10）可能需要监控姿态，此时的正确路径是**在诊断设施之上构建监控**（事件流的下游订阅者做聚合与告警），而不是改造成监控本体——分层的架构让两种姿态可以共存而不互染（Bus 的订阅者模型天然支持多消费者，4.4）。分寸的总结：**观测体系服务于它的用户**——个人开发者要的是"出事能查清"，组织要的是"异常能预警"，两者共享同一套底层事件，姿态在上层分化。

## 16.19 观测数据的查询形态：事件流的"人读"界面

事件流是机器友好的（结构化、schema 化），但排障的人需要"人读"形态。查询形态的候选与取舍（作者分析）：**形态一：过滤视图**——按会话、时间窗、事件类型过滤事件流（事件字段已 schema 化，过滤是纯粹的查询问题——SQLite 直查或 server 端的调试端点，16.3 的 debug handler 是现成挂点）；**形态二：时间线合并**——把多源数据（事件、追踪、错误）按时间轴对齐成一条叙事线（16.2 的关联键在这里兑现价值）；**形态三：投影复用**——前端的会话视图本身就是最强的"人读"界面（12.3 的渲染），排障时的"打开会话看现场"往往比任何专用工具都直接。三个形态的成本递减、收益递增——**复用投影作为诊断界面的思路最符合本仓库的性格**（事件即日志，投影即视图）。查询形态的一个设计警告：专用诊断 UI 容易演化成第二事实源（自己解析事件、自己的聚合逻辑，与前端投影漂移）——防御手段是诊断视图与前端视图消费同一份投影逻辑（session/projector 之类的共享层，4.12 的三段管线）。

## 16.20 与外部工具的衔接：诊断不出闭环

本地诊断有时需要外部工具衔接（数据库直查、网络抓包、系统级观测），衔接面值得明确。**数据库层**：SQLite 文件可被任何工具打开（4.13 的可直读性）——用 sqlite3 CLI 查消息表、事件表是贡献者的常规操作（库结构自描述：schema.sql.ts 与 drizzle 定义即文档）；**网络层**：provider 交互的抓包受 TLS 限制，更现实的路径是 http-recorder 的录制（14.2——在应用层记录而不是网络层）；**系统层**：进程级观测（CPU、内存、fd 数）用操作系统的常规工具，persistent-pty 的子进程关系可从票据推导（13.6）；**日志层**：server 的进程日志与事件日志互补（进程日志管启动与崩溃，事件日志管领域行为）。衔接面的统一原则：**OpenCode 不试图自建全部诊断工具，而是保证每一层数据都有标准的"出口格式"**（SQLite 是出口、录制文件是出口、事件流是出口）——外部工具只要会说这些格式就能接入。这个原则与开放协议的哲学（17.5）同构：对内是事件流，对外是标准格式，诊断生态因此可以借力整个工具箱而不必发明轮子。

## 16.21 本章小结

本章把证据源系统化：事件即日志的架构优势、追踪的因果链、状态面的分级暴露、十大故障对照表、崩溃取证协议、三层调试面、三种用户视角的分级观测、观测数据的生命周期、三则复合故障的完整推演，以及六条可观测性反模式。至此，工程横切面的前两个（性能、诊断）完成，它们与前十六章的关系是"透镜"关系——同一套机制，用性能透镜看是资源账本，用诊断透镜看是证据链。最后一章换最宽的透镜：把 OpenCode 放进行业生态坐标系，讨论形态谱系、差异化特征与适用场景。
