# 第三章 · 会话引擎与主循环

## 3.1 会话是什么：先定义，再实现

"会话"这个词在日常语境里模糊——一次打开窗口算一个会话吗？切换模型后还算同一个会话吗？压缩过历史之后呢？要在引擎层面工作，必须给出严格定义。OpenCode 的会话（session）是**一个带持久身份的执行容器**：它有自己的 ID（SessionSchema.ID）、消息历史（追加式）、输入收件箱、压缩检查点序列、权限状态与一组附属资源（快照、子代理会话、后台作业）。用户感知中的"一段对话"对应一个会话；但一个会话的存续远长于任何一次"模型响应"——模型响应只是会话历史上的一步。

这个定义立刻推出会话引擎必须回答的四个子问题：输入从哪里进、循环怎么驱动、每一步怎么执行、崩溃后怎么恢复。本章按此展开，四个子问题分别对应 3.2、3.3、3.4 与 3.8。引擎的全部代码集中在 packages/core/src/session/（七十多个文件）与 session/runner/（主循环与步执行），持久化在 session/sql.ts，事件定义在 session/event.ts。

还有一层结构值得先交代：会话是 Location 的成员。第二章讲过，每个 Location（工作目录实例）有自己的服务子树，其中就包括一组会话及其运行器。切换工作目录或 worktree 时，看到的是不同 Location 的不同会话组；会话迁移（move/transfer）则把一个会话从一个 Location 搬到另一个，涉及服务实例的转移与历史的延续——这些控制项会在 3.3 的主循环里以"步间检查"的形式再次出现。

## 3.2 收件箱模型：输入不直接打断循环

用户在模型正在干活时又输入了一句话，系统应该怎么办？这是 agent 引擎的第一个并发设计难题。天真的做法是立刻打断当前执行去处理新输入，但这会破坏"循环在良定义切点转移状态"的原则——工具执行到一半被打断，状态可能不一致；而且用户的新话可能是对当前任务的补充说明（"顺便也把测试跑了"），并不想打断。

OpenCode 的答案是收件箱（inbox）模型。所有进入会话的输入——用户新消息、手动压缩指令（/compact）、会话迁移请求——都先落进收件箱并持久化（输入收件箱的事件溯源化见第四章的 event_sourced_session_input 迁移），投递时分为两种模式：**steer**（转向）与 **queue**（排队）。steer 表示"这条输入要影响当前正在进行的目标"：引擎会在当前步结束后的安全切点把消息注入上下文，让模型在下一步自然接收到，不打断已派发的工具，也不丢弃模型已完成的部分工作。queue 表示"这条输入是下一轮的新任务"：等当前任务完全结束后再消费。

两种模式的区分本质上是对"用户意图影响范围"的建模。实现上，主循环每拿到一步结果就回头检查收件箱，收件箱条目的消费时机、顺序与投递方式都由引擎而非前端决定——前端永远只做"投递"，这保证了任何客户端（终端、Web、桌面、SDK 脚本）投递的输入都走同一条被测试覆盖的路径。收件箱还解决了另一个隐蔽问题：**输入的持久化先于消费**。用户消息一旦入箱即落库，哪怕进程此刻崩溃，重启后输入仍在收件箱里等待被消费，不会凭空消失。这是"可恢复"原则在输入侧的体现。

## 3.3 Drain 主循环：排空收件箱，直到无事可做

主循环的实体是 SessionRunner.drain（接口签名 packages/core/src/session/runner/index.ts:31-42，实现 packages/core/src/session/runner/llm.ts:64-221，服务标识 "@opencode/SessionRunner"，index.ts:44）。"drain（排空）"这个名字取得精确：循环的唯一使命是把收件箱里的输入变成完成的步骤，排空之后循环退出，会话进入空闲。每次有新输入入箱，都有机制唤醒 runner 重新 drain——一个会话的活跃期就是"drain 不断被触发"的时期。

drain 的骨架分两段。外段是循环外壳：拿到一个 Ready 状态就执行 runStep，然后步数加一，继续外层循环（llm.ts:212-220），直到 drain 以某种结果结束。返回值是可辨识联合 DrainResult（index.ts:23-28），有 Complete（排空完成）、Moved（会话已迁移走）、Reloaded（配置或定义重载需要重来）三种出口——循环不是简单布尔结束，而是"以可区分的方式结束"，调用方据此决定后续动作。

内段是 advanceToStep（llm.ts:82-210）：在真正进入一步之前，循环处理所有"控制项"，直到收件箱状态为 Ready。控制项包括：手动压缩请求（llm.ts:130-174，用户显式要求总结历史，处理方式与自动压缩不同——它不是"为下一步腾地方"而是"立即重写历史"）；会话迁移（llm.ts:125-129，move 到其他 Location 时 drain 直接以 Moved 结束）；空闲钩子（llm.ts:179-186，experimental.idle 插件钩子允许插件在会话空闲时注入行为）。控制项与普通输入分离的意义在于：普通输入变成对话内容，控制项改变**循环自身的走向**——压缩改写历史，迁移改变会话归属，钩子改变空闲语义。把它们放进同一个 advanceToStep 函数集中处理，等价于把"循环元状态"的所有转移收敛到一个函数里，审查与测试都有了单一入口。

还有一个细节精妙：指令就绪门控。指令基线（AGENTS.md 等）的装载是异步的（第五章展开），若输入到达时指令尚未就绪，已准入的输入会保持 pending（llm.ts:228 附近调用 InstructionState.prepare），等指令装载完成后再放行。这避免了一种难查的竞态：会话第一条消息发出时项目指令还没读完，导致模型在没有项目约定的状态下开始干活。

## 3.4 RunStep：步间策略层

runStep（llm.ts:233-380）是"步与步之间"的策略层，它不执行模型调用，而是决定这一步要不要打、怎么打。三个决策点：

**决策一：要不要先压缩**。第 $k$ 步发出前估算上下文占用，若已逼近自动压缩阈值（245 行附近），先触发压缩再继续。压缩本身是一次模型调用，因此这一步会变成"先压缩后对话"的两段式。第五章完整推导触发条件与预算公式。

**决策二：步数是否超限**（252 行附近，配合 max-steps.ts）。这是第一章 1.2 节"无内建终止"性质的对症药。步数上限是兜底而非目标——正常任务远早于上限收敛，上限捕获的是模型陷入循环（反复读同一个文件、反复执行失败命令）的病理状态。

**决策三：请求如何组装、钩子如何注入**（260-285 行）。SessionModelRequest.primary 负责把系统提示、指令基线、历史与收件箱输入组装成一次请求（第五章详述组装算法）；组装前后有请求级插件钩子可供改写。模型解析结果（SessionRunnerModel.Resolved，runner/model.ts）携带 route、limit、cost、capabilities 四类元数据，供步执行与压缩模块消费——上限（limit）参与 3.4 决策一的预算计算，能力（capabilities，如是否支持图片、是否原生压缩）参与组装决策。

策略层与执行层的分离是经典的两阶段设计：策略层做"要不要、怎么做"的决策且可以重试整个策略，执行层做"一次干净的尝试"。这种分层让重试语义异常清晰——Retry 结局回到 runStep 重来，而不是在执行层内部复杂地"续"。

## 3.5 SessionStep.attempt：一步之内的微观世界

真正执行一步的是 SessionStep.attempt（packages/core/src/session/runner/step.ts:71-295）。它做的事可以分解成四个并行的视角。

**流视角**：provider 的响应是一条 LLMEvent 事件流（textDelta、tool-call、stepFinish、finish 等，packages/ai 定义，第七章）。attempt 逐事件消费（step.ts:110-135），事件翻译由 createLLMEventPublisher 完成（publish-llm-event.ts），把"模型协议层的事件"投影成"会话事件"——投影是单向且保序的，前端因此能看到逐 token 的流式输出。

**并发视角**：每个本地工具调用 fork 一个独立 fiber 并发执行（step.ts:120-131）。模型在一次响应里经常发出多个相互独立的调用（同时读三个文件），串行执行是白白浪费时延；fiber 并发让它们并行跑，而事件发布仍然保序——并发执行与顺序呈现并存，是"调度上激进、呈现上稳定"的组合。工具之间若有依赖，靠的是模型自己在下一轮响应里的编排，引擎不做隐式依赖分析。

**中断视角**：收尾段放在 uninterruptibleMask 里（step.ts:138）。中断屏蔽区的语义要精确理解：它不是"禁止中断"，而是"屏蔽区内的代码即使面对中断也执行完毕"。用户在工具执行中途按 Esc，正在跑的 fiber 会被打断，但**已发生的工具调用必须被结算**——成功者记成功、失败者记失败、未完成者记中断，否则历史里会留下永远"运行中"的幽灵调用。3.8 节的崩溃恢复协议正是这个保证在网络/进程级别的对偶物。

**结果视角**：一步的结局是六种 Outcome 之一（step.ts:30-41）：Completed（正常完成）、Retry（整体重试，回到 runStep）、Continue（断流续写）、RecoverFull（传输层恢复后整体重来）、Compacted（上下文溢出触发压缩后重来）、OutputLimit（输出上限触发续写）。六种结局共同构成一个小的状态机，Retry/RecoverFull 向上回到策略层，Continue/OutputLimit 在步内或紧邻步间续写，Compacted 重走压缩流程——状态机图如下：

```
                    ┌──────────┐
        组装请求 ──►│  attempt │
                    └────┬─────┘
        ┌───────┬────────┼────────┬──────────┐
        ▼       ▼        ▼        ▼          ▼
   Completed  Retry   Continue  RecoverFull  Compacted/OutputLimit
        │       │        │        │          │
        ▼       ▼        ▼        ▼          ▼
      结束   回 runStep 续写   传输恢复后   压缩/裁剪后
                        │      重来        重来
                        ▼
                      结束
```

## 3.6 智能续写：把"失败"降级成"分两半"

六种结局里有三种值得单独解释，因为它们体现了同一设计哲学：**能恢复的错误不当作失败**。

Continue（断流续写）：模型流因网络抖动或超时中断，但任务没做完。引擎不是简单重试整步——重试会重发全部上下文、浪费已生成的 token——而是携带一段续写提示词（定义在 llm.ts:37-41 的三类智能续写提示词），告诉模型"从断点继续"，让已生成的部分成为有效的上下文前缀。这与第七章的传输层重试（RecoverFull）形成层次分工：传输层能恢复的（连接重试、key 轮换）不惊动会话层；会话层能续写的（断流）不浪费整步。

OutputLimit（输出上限续写）：模型的单次输出被长度上限截断，最典型的场景是模型试图一次性写出一个超长文件。第一次截断会触发"把剩余部分拆开继续写"的提示；若连续两次仍截断，引擎判定任务本身不适合单步完成，放弃并明确失败（llm.ts:339-369）——"两次"这个数字是经验阈值：一次可能是偶发，连续两次说明结构性超限。

RecoverFull：传输层错误经 packages/ai 的错误分类（第七章）判定可恢复后，整体重来一步。它与 Continue 的区别在粒度：Continue 复用已生成前缀，RecoverFull 丢弃半成品从头再来——因为传输层错误意味着流本身不可信。

这套续写体系的统一思想是把**时间轴上的失败转化为空间轴上的分段**：不追求一次流到底，而是承认流会断，把"断"变成切点。工程上它的收益是节省 token 与时延，语义上的收益是模型体验连续——用户看到的不是"重试中"，而是持续输出。

## 3.7 步间的协作者：retry、max-steps 与 run-coordinator

主循环周围还有三个小模块各司其职。SessionRunnerRetry（runner/retry.ts）实现会话级重试决策：什么错误值得整步重试、退避多久、重试几次上限——它与 packages/ai 的传输级决策（route/decision.ts）分层，第七章会对比两层重试的职责边界。max-steps.ts 实现步数上限的配置读取与判定，上限可由 agent 配置指定（第九章 agent 配置），默认值兼顾"复杂重构需要几十步"与"病理循环不该无限烧钱"。run-coordinator.ts（session/run-coordinator.ts）处理更外层的问题：多个客户端同时请求同一个会话运行时怎么办？协调器保证同一会话同一时刻只有一个 drain 在跑，其余请求要么合并要么拒绝——没有它，两个终端窗口对同一会话各发一条消息会引发两个并发 drain 互踩收件箱。background.ts（session/background.ts）则管理会话的后台活动（转后台的 shell 作业完成后的唤醒等），与第六章 shell 工具的 notifyWhenDone 衔接。

## 3.8 崩溃恢复：把"意外"变成"可结算的历史"

任何长期运行的 agent 引擎都会崩溃：进程被杀、机器断电、升级重启。OpenCode 对崩溃的态度不是"尽量不崩"，而是"崩了之后历史仍然自洽、执行可以从断点继续"。实现是一对"陈旧结算"（stale settle）协议，在每次 drain 开始时执行。

结算一：settleStaleCompactions（llm.ts:382-410）。压缩是一个多步过程（发起模型调用、写检查点、替换历史），若进程在中间崩溃，数据库里会留下 status=running 的压缩消息。结算逻辑把这些遗留压缩全部改判为 interrupted——压缩没有完成，历史保持原样，下次照常压缩。判定依据不是猜，而是数据库里的状态字段加 json_extract 查询（llm.ts:387-399 展示了对消息 JSON 的直接查询用法）。

结算二：settleStaleToolCalls（llm.ts:412-435）。同理，工具调用可能停在 streaming 或 running 状态。结算把它们改判为中断；特别地，对子代理调用（subagent），恢复逻辑会带上其子会话 ID（llm.ts:420-421），使子会话的已有产出不被丢弃——主循环崩溃不连坐子代理的成果。

两个结算共用一个前提：**所有"进行中"的状态都必须先落库**。running 状态、工具调用的中间态、压缩的进度，都在进入时写库、完成时更新——这是第四章持久化设计的动机。有了这个前提，"崩溃恢复"退化成一个幂等的批处理：扫出所有 running 状态，改判，继续。Continuation = { step }（index.ts:21）记录会话执行到哪一步，配合数据库历史，新进程可以从任意一步续跑。整套协议没有一个分布式事务，靠的就是"状态先行落库 + 幂等结算"两个朴素原则——这是值得迁移到任何长任务系统的设计。

## 3.9 多会话与子代理的编排

最后把镜头拉远看并发结构。一个 Location 里可以有多个会话并行 drain（不同会话互不共享收件箱）；一个会话内部可以派生子代理会话（subagent-job.ts、subagent-completion.ts 管理子代理作业与完成回执）：主循环发出 subagent 工具调用，子代理在自己的会话里跑完整循环，完成后把总结作为工具结果回给主循环。控制流上这是一棵树：根是主会话的 drain，节点是子代理会话的 drain；持久化上这是外键关系：子会话记录父调用，崩溃恢复时（3.8 结算二）父子关系用于找回未完成的子代理。此外 SessionTransfer（session/transfer.ts）支持会话跨 Location 迁移，affinity.ts 管理会话与 Location 的亲和关系——多目录、多会话、多子代理三个维度叠起来，构成 OpenCode 的并发拓扑，而这一切都建立在"每棵 drain 子树有独立的收件箱与锁"这个简单规则上。

## 3.10 收件箱的语义细节：投递、消费与可见性

3.2 引入的收件箱模型值得再往深挖三层。第一层是**投递语义的精确化**：steer 与 queue 的区别不是"快慢"而是"作用范围"——steer 影响当前正在进行的意图（下一轮模型请求就会看到），queue 只影响下一轮的起点。同一条消息理论上可以按两种模式投递，选择权在投递方（用户界面或 API 调用者），但消费权始终在引擎——投递方不能要求"立刻打断工具"，它只能表达意图，引擎在安全切点兑现。这个"表达与兑现分离"是并发系统里常见的正确模式（与中断请求 irq 类似）。第二层是**消费的原子性**：收件箱条目从 pending 到 consumed 的转移与"条目内容进入模型请求"在同一事务语义下完成（第四章事件溯源化的存储保证），不存在"消息显示已读但模型没收到"的窗口。第三层是**可见性**：收件箱状态是会话状态的一部分，经事件广播给所有前端——用户在 Web 端发的消息，终端立刻可见（排队中、已注入），多端协同因此有统一的"输入面板"语义。三层合起来，收件箱不是简单的队列结构，而是"输入的完整生命周期"（到达、持久化、可见、消费、生效）的状态机载体。

## 3.11 发布管线：并发 fiber 的事件如何汇成保序流

3.5 说工具 fiber 并发执行而事件保序发布，这在工程上是个有趣的汇流问题：多个并发的执行单元各自产生事件（工具开始、输出块、工具结束），汇成一个流时必须保序——保什么序？OpenCode 的答案是**按会话语义序而不是按墙钟序**：每个工具调用在模型响应里有确定的声明顺序（第几个调用），其事件以声明序为键排布；同一调用内部的输出块自然按产生顺序。实现上，publish-llm-event.ts（publish-llm-event.ts 的 createLLMEventPublisher）承担翻译与排布：LLM 层事件（textDelta、tool-call 等）被投影为会话事件并携带排序键，Bus 按 key 序发布（第四章 EventSequenceTable 的聚合序列号提供持久层的有序保证）。这个设计的微妙之处在于：**不追求全局时间序**——两个并发工具的真实完成时间无法也不需要排序，引擎只承诺"模型视角的事件次序不变"，前端的渲染因此稳定（工具卡片的出现顺序与模型声明一致，哪怕实际执行次序相反）。汇流问题在流式系统里普遍存在（日志聚合、消息队列的分区排序），这里的解法提供了一个清晰的参照：先定义"业务序"，再让传输层服从业务序，而不是让业务迁就传输序。

## 3.12 参数化护栏：重试、步数与预算的配置面

3.4 与 3.6 提到的护栏（步数上限、重试次数、续写阈值）不是硬编码，而是配置面。agent 定义里可以指定步数上限（第九章的 agent 配置，max-steps.ts 读取）；重试策略由 SessionRunnerRetry 结合模型解析结果（limit 元数据）与传输层错误标记决定；续写的"连续两次 OutputLimit 判失败"是经验常数（llm.ts:339-369）。这些参数的共同特点是：**上限的存在保护的是用户，而不是引擎**——步数上限保护钱包与时间，重试上限保护不被限流循环拖死，续写阈值保护不被无限截断消耗。护栏参数化的产品含义：不同 agent 可以有不同的冒险偏好（CI 代理可以步数上限高一些，交互代理低一些），但护栏本身不可关闭——配置面只允许调松紧，不允许拆掉。护栏设计的通则由此可以总结：上限值可调、上限存在不可调；阈值可调、阈值语义不可调。任何 agent 系统的参数面板都值得用这条通则审一遍。

## 3.14 并发场景矩阵：谁在什么粒度上互斥

会话引擎的并发正确性分散在多个机制里（收件箱、run-coordinator、fiber 并发、文件锁、KeyedMutex），整理成一张"互斥粒度矩阵"可以看清全貌：

| 并发场景 | 协调机制 | 互斥粒度 | 出处 |
| --- | --- | --- | --- |
| 同会话两个 drain 请求 | run-coordinator | 会话级（合并或拒绝） | 3.7 |
| 新输入 vs 进行中的步 | 收件箱切点消费 | 步边界（steer 在切点注入） | 3.2/3.10 |
| 同步多个工具调用 | 每调用一个 fiber | 调用级（无锁并发） | 3.5 |
| 同文件的并发编辑 | 文件锁 | 文件级 | 6.6 |
| 同聚合的事件写 | KeyedMutex | 聚合键级 | 4.4 |
| 插件激活 | Semaphore | 激活区串行 | 10.4 |
| 跨会话共享缓存 | shared-cache | 缓存键级 | 13.8 |

矩阵的读法：**互斥粒度与冲突半径严格对应**——冲突只发生在同会话内就用会话级锁，只发生在同文件内就用文件级锁，绝不用粗粒度锁掩盖细粒度冲突。矩阵还揭示一个"无锁区"：工具调用之间刻意不加锁（3.5 的并发执行），因为模型声明的调用默认相互独立，真有依赖由模型在下一轮编排——把"顺序性"的判断权交给决策者（模型）而不是锁机制，这是 agent 并发与线程池调度的哲学差异。矩阵空白处也值得注意：**会话与快照**（第十三章）之间没有显式锁——快照的原子性由内容寻址（append-only 对象库）保证，无锁并行写安全，这再次显示"不可变数据是并发的终极解药"。

## 3.15 与通用工作流引擎的对照：agent 循环的特异性

把会话引擎与经典工作流引擎（Airflow、Temporal 类）对照，能看清 agent 引擎的特异需求在哪。相同点：都有持久化状态、崩溃恢复、重试语义、后台活动管理。三点本质差异：其一，**决策者是概率性的**——工作流的每步逻辑是人写的确定代码，agent 的每步决策来自模型，因此 OpenCode 需要"智能续写"（3.6，给模型写提示让它继续）这种工作流里不存在的机制；其二，**步的内容不可预先声明**——工作流的 DAG 在部署时确定，agent 的下一步取决于上一步的观察，因此"步数上限"取代了"DAG 深度"成为终止保障（3.4）；其三，**用户在环内**——工作流的交互点是预定义的人工任务节点，agent 的打断与转向随时发生，因此需要收件箱的双投递模式（3.2）而不是固定的审批节点。这三点差异解释了为什么 OpenCode 不复用现成工作流引擎而自研循环：复用会在每一处差异点上扭曲（用审批节点模拟随时打断、用 DAG 模拟开放决策），自研的循环虽然小，但每个机制都是为概率性决策者量身定制的。反过来说，第三、四章的持久化与恢复设计又大量借鉴了工作流引擎的成熟结论（状态先行落库、幂等结算、补偿语义）——**控制流自研、基础设施借鉴**，这是对"什么时候造轮子"的一个范例式回答。

## 3.16 本章小结

本章走完了引擎主干：输入经收件箱两种模式（steer/queue）进入；drain 排空收件箱，advanceToStep 集中处理控制项；runStep 做步间策略（压缩、步数上限、请求组装）；SessionStep.attempt 在事件流上并发执行工具并用中断屏蔽保证结算；六种 Outcome 与三种智能续写把可恢复错误降级为分段；一对陈旧结算协议让崩溃恢复成为幂等批处理。贯穿全章的原则有三：状态先行落库（结算的前提）、切点转移状态（收件箱的前提）、可恢复错误不失败（续写体系的前提）。下一章深入这些原则赖以成立的地面——消息模型与 SQLite 持久化，看看"落库"到底落成什么形状。
