# 第十五章 · 性能与资源管理

## 15.1 Agent 的三种资源：token、时间与注意力

前十四章按功能解剖系统，本章换一个剖面：性能。先定义 agent 系统的三种稀缺资源，因为"性能优化"只有对准资源才有意义。**资源一：token**（模型窗口与费用）——第五章已系统处理（压缩、预计算、裁剪），本章做全局汇总。**资源二：时间**（用户的等待）——agent 的时延结构与传统应用完全不同：模型推理是秒级到分钟级的巨块时延，工具执行是毫秒到秒级的小块，前端渲染是毫秒级——优化的重点因此与 Web 应用相反：省下一个渲染帧毫无意义，省掉一次模型往返收益巨大。**资源三：注意力**（人的带宽）——多会话并行时人的注意力是瓶颈（第十二章 12.12 的注意力分配），系统设计要最小化"人必须介入的时刻"（权限弹窗聚合、后台完成唤醒、注意力提示）。三种资源的稀缺性排序随场景变化：交互会话里时间最稀缺，CI 批处理里 token 最稀缺，多会话工作流里注意力最稀缺——性能工程的第一步永远是识别当前场景的瓶颈资源。

## 15.2 Token 经济学的全局账本

把散落各章的 token 治理机制汇总成一本账。**收入侧**（省 token 的机制）：Code Mode 把 $n$ 次往返折叠成一次（第六章，二次律下收益随任务复杂度增长）；工具输出的规范化与裁剪（图片转码、行截断、折叠降级，第六、五章）；压缩与检查点（第五章，截断历史的线性增长）；工具描述与权限前置过滤（6.2——不可用工具的定义不占窗口）；指令的按语境激活（9.14——子目录指令只在相关时进入）。**支出侧**（花 token 的机制）：系统提示与指令基线（固定层）；每次请求的历史重发（二次律的主体）；压缩本身（一次摘要调用的成本）；智能续写（续写提示的少量额外 token 换取不重发全历史）。**缓存侧**（折扣杠杆）：prompt 缓存的前缀命中（相邻步高度重叠）——预计算（5.3）是缓存视角的主动套利。把三方合起来可以给出一个定性结论：**OpenCode 的 token 策略是"结构省 token，缓存省成本"**——结构机制（Code Mode、压缩、裁剪）降低 token 总量，缓存机制降低单位成本，两者独立生效、互不替代。账本的诊断用法：会话成本异常时按层排查——是历史没压缩（检查水位线与压缩设置）、是工具输出失控（检查裁剪与规范化）、还是缓存失效（检查前缀稳定性——频繁的指令变更或消息改写会破坏缓存）。

## 15.3 时延预算与流水线结构

把一次用户输入到第一次可见响应的时延拆开。设 $T$ 为用户感知时延，主要分量：$T = T_{transport} + T_{inbox} + T_{assemble} + T_{first\_token} + T_{render}$。传输与收件箱开销（毫秒级）；组装开销（毫秒级，但指令未就绪时门控会拉长——9.14）；首次 token 时延（秒级，provider 侧，不可控但可缓存——prompt 缓存命中的会话首 token 显著更快）；渲染开销（毫秒级）。结构结论一目了然：**$T_{first\_token}$ 占绝对大头**，其余分量在优化上接近无关紧要——这与 15.1 的判断一致。工程上对 $T_{first\_token}$ 的杠杆有两个：缓存热度（预计算保持前缀稳定）与流式呈现（TUI 的逐 token 渲染让"等待"变成"看着它打字"——主观时延大幅下降，虽然客观时延没变）。流式呈现是 agent 产品的一个普遍设计共识：**时延不可消除时，用可见性兑换感知**。另一个时延场景是工具执行的时延：单工具快（毫秒级），并发工具（fiber 并发，3.5）把总时压到最慢者而非总和；长工具（测试、构建）转后台（6.5 的作业化）让会话不被阻塞——时延管理的完整策略链是"并发缩短、后台隐藏、流式稀释"。

## 15.4 并发度管理：信号量、队列与背压

agent 系统的并发面比传统应用宽（模型流、多工具、多会话、子进程、MCP 连接），并发度的治理设施分散在几处，汇总如下。**会话级**：同一会话单 drain（run-coordinator，3.7）；不同会话并行无锁（独立收件箱）。**工具级**：fiber 并发无上限但有自然上限（模型一次声明的调用数有限）；工具内部的子进程并发受 Location 的资源约束。**传输级**：MCP 的出站队列容量 64 是显式背压（10.2——OUTGOING_CAPACITY，消费不动就反压发送方）；PTY 缓冲 2MB 上限是输出侧背压（13.6——BUFFER_LIMIT 超限裁旧）。**进程级**：Effect 的 fiber 调度器管理协作式并发（第二章 2.4），Semaphore 在敏感区串行化（插件激活 10.4、vcs 刷新 13.4）。背压设计的通则：**队列有界、超限有策略（反压或丢弃）、丢弃有信号**——无界队列是内存事故的头号来源，OpenCode 的每个长时面（PTY、MCP、事件流）都有显式容量。并发度还有一个特殊的维度：**模型请求的并发**——同一 provider 的并发请求数受限流约束（429，7.10 的退避），多会话并行时 provider 侧的并发是全局资源，usage-limits 的限额跟踪（7.6）提供了全局视角的余量感知。

## 15.5 内存治理：上限、弱引用与生命周期

长驻进程的内存治理靠三类设施。**显式上限**：PTY 缓冲 2MB、退出会话保留 25 个（13.6）、ripgrep 的 stderr 8KB 与行截断（13.2）、patch 总字节上限（13.4）——上限参数的共同形态是"够用且封顶"，防单点失控。**弱引用防泄漏**：tool/runtime.ts 的 JSON Schema 编解码缓存用 WeakMap 而非 Effect Cache（6.1 提过——每个缓存项持有查找 fiber，强引用会让被驱逐 Location 的服务无法回收）——这是一个教科书级的案例：缓存的对象图持有了执行栈（闭包里有 Location 服务引用），强缓存等于把已死 Location 钉在内存里；弱引用让"缓存失效"与"对象回收"解耦。**生命周期对齐**：Location 级状态随 Location 释放（第二章的两级树——子树的资源在 Scope 里登记，树倒即释放）；全局级状态（模型目录缓存、KV）随全局作用域释放。三类设施的判定法则：上限防"单物巨大"、弱引用防"缓存钉死"、生命周期防"作用域泄漏"——内存问题的诊断先归类再对症。多 Location 长时运行是最严苛的内存场景（每棵服务子树都有状态），这也是 Location 模型在性能侧的隐藏代价与收益：代价是状态的份数多，收益是释放粒度干净（关一个目录即整树回收）。

## 15.6 启动与常驻：两个性能场景的特殊处理

启动性能（TUI 的首屏，12.13）与常驻性能（服务的长期运行）适用不同的优化逻辑。启动的逻辑是**延迟一切非首屏工作**：MCP 连接池不阻塞首屏（连接在后台进行，工具陆续出现）、模型目录缓存异步刷新（ModelsDev 的缓存优先展示旧值）、插件激活排队进行（Semaphore 串行化的激活区不阻塞 UI）——首屏只依赖"连接与主题"，其余全部渐进。常驻的逻辑是**稳态收敛**：内存有上限（15.5）、缓存有失效策略（配置变更失效 Code Mode 目录缓存，6.1 的 notify）、事件有保留策略（4.7 的保留与清理）、进程有看护（persistent-pty 的恢复、 supervisor 的插件治理）——长时运行的健康度取决于"泄漏源是否全部封堵"。两个场景共享一个测量纪律：性能优化必须先有测量（15.7），没有测量的优化是猜测。值得强调的一个反直觉点：agent 系统的"启动"其实有两级——进程启动（秒级，Bun 快）与会话就绪（指令装载、MCP 握手、模型解析，亚秒到秒级）——12.13 的渐进策略针对的是两者的总和感知，TUI 把第一级藏进 logo 与 spinner，把第二级藏进输入框就绪（打字可以先开始，发送前的门控自动等指令就绪——第三章的 pending 机制在体验上是"无感等待"）。

## 15.7 性能诊断方法论：分层定位的固定流程

给出一个可复用的性能诊断流程，对应本章的全部机制。**第一步：识别资源**（15.1）——症状是慢（时间）、贵（token）、卡（内存/渲染）、还是烦（注意力）？**第二步：定位层**——时间问题按 15.3 的时延公式逐项排除（传输、组装、首 token、渲染）；token 问题按 15.2 的账本逐层对账（历史、工具输出、缓存命中率）；内存问题按 15.5 的三类对号（单物巨大、缓存钉死、作用域泄漏）。**第三步：隔离变量**——用 simulation 模式排除真模型变量（14.2）、用最小配置排除插件变量（禁用插件对比）、用单 Location 排除多租户变量。**第四步：证据优先**——事件日志（第四章 Bus 落库的时间线）、请求追踪（request-tracing 的标识串联，第十一章）、服务状态面（service-status）是三大证据源，第十六章专门展开诊断面。**第五步：量化复验**——改动前后必须有同一口径的测量（同任务、同数据、同硬件），否则优化退化为玄学。## 15.8 各子系统的性能剖面

把全书机制按性能特征逐个画剖面，形成一张"子系统性能卡"。**会话循环**：单步时延由模型主导（秒级），引擎自身开销（组装、结算、落库）毫秒级——优化重心在减少步数与提高缓存命中，而非引擎微优化。**工具执行**：CPU/IO 型工具（read、glob）毫秒级；进程型工具（shell）秒级到分钟级，作业化（6.5）是它的性能救命稻草；并发工具互不阻塞（3.5），最慢者决定这一步的时延。**压缩**：一次性秒级模型调用，预计算把它移出关键路径（5.3）；被拒后的逐级收缩（5.4）最坏情形是多次串行调用——预算余量（15% 加 16k）就是为避免这个最坏情形。**事件流**：写入侧毫秒级（单事务双表），回放侧与历史长度线性（游标加索引压到可接受，4.12）；高频瞬时事件走内存通道不落库（4.4 的通道选择）。**MCP**：首次连接贵（子进程加握手，秒级），池化后摊薄（10.3）；工具调用一次跨进程往返（毫秒到秒级，取决于服务器实现），Code Mode 编排减少往返次数。**前端**：token 流的渲染批处理（12.3）、折叠降级（12.9）、多会话降级（12.12）。性能卡的读法：每张卡的"贵操作"都已经被对应的机制保护（池化、预计算、批处理、降级）——性能工作的常态不是发明新优化，而是**守住既有保护不被侵蚀**（比如有人改了组装顺序破坏缓存前缀，15.15 的分层规则立刻示警）。

## 15.9 性能反模式清单

与 15.8 的正面剖面相对，列出 agent 系统里反复出现的性能反模式（多数在前文的机制讨论中作为"反例"出现过，这里正名收拢）。**反模式一：把高频内容放进上下文前部**——时间戳、动态状态混进系统提示，缓存全废（5.15 的分层口诀）。**反模式二：无界缓冲**——任何"先攒着"的队列不设上限都是内存定时炸弹（15.5 的显式上限原则；MCP 的 OUTGOING_CAPACITY 与 PTY 的 BUFFER_LIMIT 是正面示范）。**反模式三：串行化本可并行的独立操作**——模型声明了多个独立工具调用却逐个 await（3.5 的 fiber 并发是解）。**反模式四：失败后的盲目重试**——没有错误分类的重试会把确定性失败也重试到上限（7.10 的决策表）。**反模式五：用粗粒度锁掩盖设计模糊**——"先全锁上再说"的并发治理杀死吞吐（3.14 的粒度矩阵）。**反模式六：渲染跟随数据源**——高频事件直接驱动重绘（12.3 的批处理与 15.1 的时延结构都指向：渲染要跟帧率走，不跟事件走）。**反模式七：把性能优化押在单个魔法参数上**——阈值调参（水位、keep、重试次数）是微调不是优化，结构性收益来自机制（Code Mode、压缩、缓存），参数只是机制的旋钮。清单的用法：做性能评审时逐条对照，命中即立项修复；新增机制时反向自检（我有没有引入其中某一条）。反模式清单比优化清单更稳定——优化随技术演化，犯错的方式千年不变。

## 15.10 性能与功能的取舍决策框架

性能工作最终要回答"这个优化值不值得做"，给出一个决策框架。第一问：**瓶颈在哪个资源**（15.1 的三资源）——省 token 的优化对 CI 批处理是头等大事，对交互会话可能不如省时延。第二问：**收益是结构性还是参数性**——结构性收益（改机制：预计算、Code Mode）通常数量级大且一次到位；参数性收益（调阈值）通常百分比小且要反复调。第三问：**成本付给谁**——预计算多花一次调用换触发时的免费（5.3 的账），Code Mode 换走调试直观性（6.3 的代价）——**性能成本经常不是钱，是复杂度或可调试性**，这类交易要格外谨慎地记账。第四问：**有没有回退路径**——优化上线后若环境变化（provider 改缓存政策、模型降价），能否退回旧行为（State 的配置开关让 precompute 可关，5.3）——不可回退的性能优化是赌博。第五问：**测量是否闭环**（15.7 的第五步）——没有前后对比的优化不做合入决策。框架的输出是一个简单的决策矩阵：结构性收益加可回退加测量闭环 → 做；参数性收益加不可回退 → 缓。这个框架刻意保守，因为性能优化的失败模式（引入 bug、增加复杂度、随环境失效）比收益更持久——**性能工作的复利来自少做错事，不来自多做聪明事**。

## 15.12 Token 费用的治理策略：分级、路由与预算上限

在 15.2 的账本之上补三个费用治理的进阶策略。**策略一：模型分级**——不同任务绑定不同价位的模型（9.7 的 agent 配置体系支持绑定）：探索与检索类任务用廉价模型，实施类任务用强力模型——子代理机制（6.15）让分级落地，因为子代理有独立的模型绑定，主循环可以派一个便宜的分身去做扫描。**策略二：任务路由**——同一任务内的请求也可以分级：压缩摘要（5.3 的预计算调用）对推理能力要求低于代码生成，可以路由到更经济的模型——路由的落点是 SessionModelRequest 的组装层与 route 层的选择。**策略三：预算上限**——会话级的用量上限（usage-limits 跟踪限额，7.6）配合步数上限（3.4）构成双保险：步数限制次数、用量限制金额，两者相乘出会话的成本上界——$$C_{\max} \approx \text{steps}_{\max} \times \text{cost}_{\max per step}$$。三个策略的共同前提是 7.13 的结构化元数据（价格、能力、窗口都可查），没有元数据，分级与路由就没有决策依据。费用治理的产品含义：**agent 的成本可控性是采用决策的一部分**——组织评估时会问"最坏情形一个会话花多少"，预算上限的存在让这个问题有确定答案。

## 15.13 长时运行的稳态：泄漏面清单与收敛条件

常驻服务的内存稳态（15.5 的展开）可以写成一份泄漏面清单与它的收敛条件。**泄漏面一：会话与消息**——历史随使用累积，收敛条件是保留策略（4.7 的 file-retention 与 blob 清理）与用户清理路径；**泄漏面二：Location 子树**——目录关闭时整树释放（Scope 资源登记，2.5），收敛条件是所有 Location 级状态都登记在树的作用域内（弱引用缓存的反例——6.1 的 WeakMap 教训——就是"状态逃出作用域"的形态）；**泄漏面三：PTY 与子进程**——退出会话有保留上限（13.6 的 EXITED_LIMIT），收敛条件是票据可回收；**泄漏面四：事件与日志**——按聚合保留（16.8），收敛条件是与会话生命周期绑定；**泄漏面五：缓存**——模型目录、schema 编解码、fff 索引，收敛条件是失效策略存在且被 State 的 notify 链触发（9.6）。五个泄漏面共用一个收敛判据：**每一个分配点都必须能回答"谁负责释放、什么时候释放"**——回答不了的就是泄漏候选。这个清单的用法与 15.5 一致：长时运行的内存曲线若不平稳，按清单逐面对号。稳态的验收标准可以量化：连续运行 N 天后，空闲内存回到基线附近（缓存合理占用的水平）——不收敛即有泄漏面未被覆盖。

## 15.14 度量点设计：性能数据从哪里来

15.7 的诊断流程依赖度量，度量点的选取值得设计。**度量点一：循环计时**——每步的组装、首 token、工具执行、结算四段的耗时（事件流已携带时间戳，4.4——度量不需要新埋点，从事件推导）；**度量点二：token 计量**——每步的输入输出 token（usage 数据，7.6 的用量统计），按会话累计即成本曲线；**度量点三：缓存命中**——provider 返回的缓存命中指示（可从响应元数据读取），前缀稳定性的直接证据；**度量点四：队列水位**——MCP 出站队列、PTY 缓冲的占用（容量常量的观测面，10.2/13.6）；**度量点五： GC 与内存剖面**——运行时层面的周期采样（Bun/Node 的内存统计），定位 15.13 的泄漏面。五个度量点的共同设计原则：**优先从既有事件推导，其次才考虑新增埋点**——事件驱动架构的度量成本本来就低（一切状态变化已是结构化事件，16.1），另起炉灶的度量体系反而制造第二事实源。度量数据的呈现面（TUI 的状态对话框、debug handler）与保存面（事件落库）都有了，缺的只是消费视角的组织——这正是第十六章诊断工作流的入口。

## 15.16 会话级的性能画像：把度量变成日常可见

15.14 的度量点如何变成用户可感知的性能画像？设计一个"会话画像"的呈现逻辑（作者分析，基于既有数据面）。画像的最小集合：**步数与成本曲线**（每步 token 用量的柱状分布——usage 数据直接可得，成本陡增的步一眼可见）；**缓存命中率趋势**（前缀稳定性的健康度——命中骤降往往对应指令变更或压缩发生，与事件时间线对照即可归因）；**工具耗时分布**（哪些工具是时间大头——shell 长命令该转后台、网络工具该关注超时）；**压缩时间线**（几次压缩、各次的目标与实际效果——5.4 逐级收缩的次数反映预算余量是否合理）。画像的意义不是炫技，而是**把性能从"出问题才查"变成"常态可见"**——15.7 的诊断流程第一步（识别资源）在画像面前自动完成。呈现面的候选是既有设施：TUI 的状态对话框（12.6 的 dialog-status）与 debug 面板、server 的状态端点（16.3）。数据全部来自既有事件与 usage（16.1 的"事件即日志"红利），不需要新的埋点体系——性能画像因此是"低成本高价值"的改进候选，也是本套文档读码分析可以直接推导出的一个产品建议。

## 15.17 性能与正确性的边界：不拿正确性换性能

以一条原则收束性能章：**任何性能优化不得破坏正确性性质**，而"正确性性质"在 OpenCode 里有一份明确清单（来自前文）：结算必须完成（uninterruptibleMask，3.5）、事件先落库再分发（4.4）、断言按快照求值（8.11）、权限缺省拒绝（8.2）、压缩原子替换（5.8）、恢复幂等（3.8）。对照可见，OpenCode 的重要性能机制全部设计在性质的"安全侧"：预计算提前算但换入是原子的（5.8）、Code Mode 折叠往返但部分成功可表达（6.13）、并发工具但事件保序（3.11）、批处理渲染但投影纯函数（4.9）。这印证了 15.10 框架里的隐含前提：性能决策的第五问（测量闭环）之前还有第零问——**这个优化会不会改变任何一条正确性性质**？会改，就必须先证明等价或放弃。性能与正确性不是天然对峙，但每一次具体的优化都是一次潜在的交易——清单让交易显式化。性能章到此收束：三资源、账本、时延、并发、内存、稳态、度量、画像、反模式、决策框架，最后是这条底线。

## 15.19 多 Location 场景的资源份额与公平性

多 Location 并存（第二章的两级树）引出一个资源份额问题：一个目录的重会话会不会把共享资源吃光，饿死其他目录？共享资源的清单：CPU 与子进程并发（工具执行）、provider 的速率配额（全局共享，7.10 的限流）、事件流的发布吞吐（Bus 的 KeyedMutex 按聚合分轨——不同 Location 是不同聚合，写互不阻塞）、fff 索引与文件监听的 IO。现状的公平性来自"自然分片"：会话互斥是会话级（3.14）、事件写是聚合键级（4.8）、MCP 连接按 Location 独立——资源竞争主要出现在 **provider 配额**与**机器 IO**两个全局面上。provider 配额的公平性由 usage-limits 的全局视角感知（7.6），机器 IO 由运行时调度自然竞争。这个现状的评估（作者分析）：对"单用户多目录"的主场景，自然分片够用（用户本人就是调度器——注意力分配决定哪个会话活跃，15.1）；对"无人值守多任务"场景（CI 并发、定时任务并发），provider 配额的竞争是真实瓶颈，缓解手段是任务错峰（schedule 的调度面，13.8）与模型分级（15.12 的路由）。资源份额的设计启示：**公平性机制的成本要与并发的真实烈度匹配**——为不存在的竞争先建调度器是过度设计，为已存在的竞争不建调度器是事故温床；OpenCode 的现状处在"竞争可见、调度按需"的合理点上。

## 15.20 给开发者的性能守则

以六条守则收束性能章（面向在 OpenCode 上做二次开发或贡献的读者，每条对应前文的机制）。**守则一：新增机制先报预算**——它每步消耗多少 token、多少次调用（5.12 的四级预算里占哪一层）；**守则二：新状态必须选通道**——持久还是瞬时（4.4 的双通道），高频抖动禁止落库；**守则三：新队列必须有界**——容量、超限策略、丢弃信号三件套齐备（15.4 的背压通则）；**守则四：新缓存必须答释放**——谁负责失效、何时回收（15.5 的收敛判据），拿不准就用弱引用；**守则五：新请求必须可中断**——流式消费、超时、退避三选三（2.4 的 Effect 原语），不可中断的长操作要放进 uninterruptibleMask 并说明理由；**守则六：优化必须过第零问**——不破坏 15.17 的正确性清单，且测量闭环（15.7）。六条守则的共同精神与全书一致：性能不是事后优化，而是每个机制出生时的体检项——**在正确的位置做正确的事，性能是副产品；在错误的位置做聪明的事，性能是安慰剂**。

## 15.21 本章小结

本章以三个资源（token、时间、注意力）为纲，汇总了全书分散的性能机制：token 的全局账本（结构省量、缓存省成本）、时延的公式与流式稀释策略、并发与背压的设施清单、内存治理的三法则、启动与常驻的分场景策略、子系统性能卡与反模式清单，最后给出性能决策的五问框架。性能横切面的总结论与全书一致：**OpenCode 的性能立场是结构性的**——重要的性能收益都来自架构决策（事件流的落库回放、Code Mode 的往返折叠、压缩的预计算、Location 的资源回收粒度），而不是热点代码的微调。下一章把本章反复引用的证据源（事件流、追踪、状态面）系统化为诊断方法论，回答"系统不对劲时怎么查"。
