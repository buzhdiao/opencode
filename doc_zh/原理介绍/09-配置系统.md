# 第九章 · 配置系统

## 9.1 双层配置：告诉 agent "能用什么"与"该怎么干活"

OpenCode 的配置分两层，语义完全不同。第一层是**机器配置**（opencode.json 或 opencode.jsonc）：provider 与模型、agent 定义、权限规则、MCP 服务器、插件、快捷键、主题、压缩参数——它回答"这个 agent 安装里有什么、边界在哪"。第二层是**指令配置**（AGENTS.md 等 markdown）：构建命令、架构说明、代码规范——它回答"在这个项目里该怎么干活"。两层分开的原因是**变更主体与生命周期不同**：机器配置多由安装者或组织设定，变化频率低、语义是能力边界；指令配置由项目作者维护、随项目演化、语义是行为约束。混在一层会让"升级工具"与"改项目约定"互相牵连。

本章沿配置数据的一生展开：发现（哪里的文件算配置）→ 解析与归一化（怎么读、怎么兼容旧格式）→ 合并（多来源怎么叠加）→ 变量展开（引用怎么求值）→ 分发（各子系统怎么拿到自己的配置）→ 热更（改了怎么生效）。这条链的主代码在 core/src/config.ts 与 config/ 子目录（normalize.ts、discovery.ts、variable.ts、watch.ts、integration.ts、managed.ts），模式地基在 core/src/state.ts。

## 9.2 发现与解析：从文件到文档

发现逻辑的入口是 ConfigDiscovery（core/src/config/discovery.ts），文件名候选是 opencode.json 与 opencode.jsonc（discovery.ts:12 的候选表，jsonc 允许注释——配置文件允许注释是面向人类编辑者的基本礼貌，jsonc-parser 的 parse/applyEdits/modify 三个函数在 config.ts 的导入清单里，分别承担解析、程序化修改与编辑生成）。加载阶段（config.ts 476 行附近）从候选目录里挑最后一个存在的配置文件——"最后一个"对应优先级最低的全局目录到优先级最高的项目目录的搜索顺序。解析后的文档不是裸对象，而是带来源标记的 Config Document（Directory、Document、Info、Patch、Entry 等类型来自 @opencode/schema/config）：每份文档记得自己从哪来（全局、项目、还是程序生成），来源信息在合并与诊断（"这条规则是谁定的"）时都要用。

解析的第二阶段是**归一化**：ConfigNormalize（config/normalize.ts，八百多行）负责版本迁移、键归一化与旧键兼容。兼容的具体例子：lsp 配置键——v2 已移除内置 LSP（doc_zh/components/04 专文分析），但 normalize.ts:11 仍导入 ConfigLSP、501-504 行仍解析 opencode.json 里的 lsp 键，让老配置文件不报错地被接受。归一化层的存在让 schema 可以干净地演进：schema 定义"现在是什么"，normalize 定义"过去怎么变成现在"——两份代码各管一个时间方向，互不污染。版本迁移的具体手法（改键名、拆合字段、单位变换）都在这一层，带测试覆盖（packages/core/test/config/ 目录）。

## 9.3 合并模型：有序文档与"最后者胜"

多来源配置的合并是配置系统最容易出错的地方（全局说 A、项目说 B，听谁的？）。OpenCode 的模型是把所有文档排成一个有序序列，查询时**从后往前找最后一个定义了该字段的文档**——config.ts 的 latest() 函数就是这个语义（entries.findLast 找 type 为 document 且该字段非 undefined 的条目）。序列的顺序即优先级：全局（$HOME/.config/opencode/）在前、项目在中、Location 实例在后，后者的字段覆盖前者。"最后一个非 undefined"的精确语义还要注意 undefined 与"显式设为空"的区分：显式值总是覆盖，未定义才透传——这让"项目想恢复全局关闭的某项"成为可能（显式写 true 覆盖全局的 false，而省略则继承）。

Location 级的配置来源更细：server 装配时 Config.node 按 options 替换配置来源（routes.ts:137-144），来源有四种——project（项目配置）、claude（从 Claude 类工具的配置迁移来的兼容来源）、file（直接给文件）、content（直接给内容字符串）。四种来源覆盖了所有部署形态：桌面应用可能直接给 content（用户在界面里编辑的配置文本），CI 环境可能给 file，正常 CLI 用 project。**配置来源的抽象让"配置从哪来"与"配置是什么"解耦**，测试也因此可以直接注入 content 而不必造文件。

合并的一个特殊领域是权限规则（第八章）：权限不取"最后者胜"而是**规则集拼接**——agent 规则、项目规则、保存的规则、托管策略按序求值，因为权限语义是"最后匹配生效"而不是"最后定义生效"，拼接顺序决定求值顺序。同为"多来源合流"，普通配置用覆盖语义、权限用求值语义，两种合流策略并存说明：**合并策略必须服从领域的语义**，不存在万能合并函数。

## 9.4 变量展开与环境引用

配置里可以引用环境与变量：ConfigVariable（core/src/config/variable.ts）负责在解析后展开 {env:VAR} 之类的引用。展开的时机是加载期而非使用期——配置文档一旦加载就是**求值后的静态事实**，子系统拿到的配置不需要再理解变量语法。这个时点选择有安全与语义双重理由：使用期展开意味着同一份配置在不同环境里语义漂移（难以诊断）；加载期展开让"配置是否合法"在加载时一次性判定，变量缺失立即报错而不是在某个深夜的工具调用里炸开。环境相关的注入（如会话 ID 注入子进程）不属于配置系统——那是工具层的行为（shell 工具给子进程加 OPENCODE_SESSION_ID，第六章），配置系统只管**静态求值**，运行时上下文走别的通道。

## 9.5 热重载：改配置不用重启

配置是文件，文件会被用户随时编辑，编辑必须生效——热重载由 ConfigWatch（config/watch.ts）与文件监听设施（core/src/filesystem/watcher.ts 的 Watcher 服务、file-watch.ts 的 FileWatch）实现：文件变更事件触发配置重新加载，重载后的新配置经合并管线生成新的生效视图，再通过 State 模式（9.6）推给各消费者。config.ts 的实现细节里能看到 FiberMap 与 Semaphore 的使用（并发重载的去重与串行化——连续保存十次文件只触发一次有效重载），以及 PubSub（变更通知的发布）。热重载的语义约束（第八章末已提）：规则收紧对新断言立即生效，进行中的调用按断言时刻的快照走——重载不制造"一步之内规则漂移"的中间态。

## 9.6 State 模式：core 的配置消费范式

core 里几乎所有可配置子系统都遵循同一个模式，由 core/src/state.ts 提供：

```ts
State.create<Settings, Editor>({ name, initial, editor, notify })
```

四个部件各司其职：initial() 给默认值（压缩模块的 { auto: true, keep: 15000, precompute: false }，compaction.ts:269）；editor 是受控修改接口（谁能改、改哪些字段、改的时候做什么校验）；notify 是变更后的副作用（tool.ts:232-244 的例子：配置变更让 Code Mode 的目录缓存失效并打印注册错误）；transform/reload 支持插件在事务里改配置并热重载。这个模式的价值在**语义一致性**：默认值集中在一处（initial），修改有单一入口（editor，可审计），变更副作用统一声明（notify，不会散落各处的监听器），重载可测试（reload 是纯函数式的重新求值）。没有这个模式，每个子系统自己发明"默认值加散落的 setter"，配置语义的演化会失控——State 模式是配置系统的**消费者侧纪律**，与 9.2-9.5 的**生产者侧管线**合起来才是完整的配置故事。

State 模式还有一层并发语义：State 是不可变值容器，消费者拿到的是快照，修改经 editor 产生新快照——这与第八章"断言时刻的规则快照生效"呼应：**快照读**让并发消费不需要锁。effect 里 State 的变更通知走 notify 副作用而非订阅者列表，简化了生命周期（没有"取消订阅"的泄漏问题）。

## 9.7 Agent 配置：能力的声明式封装

配置系统最丰富的对象是 agent 定义（第九章主语中的"agent"）。core/src/agent.ts 定义 Info（agent.ts:20-22）与 Editor 注册表（可增删改），defaultID = "build"（agent.ts:10）指定默认代理。一个 agent 定义封装了模型选择、步数上限（max-steps，第三章）、权限规则集（第八章）、提示词定制、工具可见性等——**agent 是配置项而不是代码分支**（第八章 8.6 已论证）。用户在 opencode.json 里定义自己的 agent（例如"只能跑测试的 CI 代理"），运行时经 Editor 注册、按需切换（Tab 键在 build/plan 间切换只是两个内置 agent 的快捷方式）。agent 配置的 schema 在 @opencode/schema，归一化在 normalize 层，热更走 State——与其他配置对象完全同构。

## 9.8 Wellknown、workspace 与托管配置

三个派生机制补全配置版图。WellKnown（core/src/wellknown.ts）处理"well-known 风格"的约定位置发现——某些集成物放在约定路径上（类似 .well-known 的 Web 惯例），配置系统按约定自动发现而不必逐个声明。Workspace（core/src/workspace.ts）是项目下的多工作上下文概念（第四章迁移史里的 workspace 系列就是它），每个 workspace 有自己的配置视图与会话组。托管配置（config/managed.ts 与 ManagedPolicy，core/src/managed-policy.ts）承接第八章的组织策略：受管安装的规则下发、优先级压过用户配置、不可覆盖。这三者的共同点是**配置来源的再扩展**：发现机制（约定路径）、作用域机制（workspace）、信任层级机制（托管）都在"多来源有序合并"的框架内实现——框架的可扩展性正是 9.3 有序文档模型的红利。

## 9.9 指令系统：AGENTS.md 的发现与注入

指令配置的载体是 markdown。发现逻辑在 core/src/instruction-discovery.ts：全局、项目、嵌套目录级（子目录的 AGENTS.md 在处理该目录下文件时生效）多级发现；文件支持 frontmatter（gray-matter 解析，core/package.json:124 的依赖），frontmatter 里可以声明作用域、引用其他规则源（官方文档 rules.mdx 提及可复用 Cursor/Copilot 的规则文件）。装载与状态在 core/src/instructions/ 与 session/instruction-state.ts；注入走 SessionModelRequest.baseTranscript（第五章 5.6）；就绪门控（InstructionState.prepare，第三章 llm.ts:228）保证指令层要么完整要么显式缺失。指令与 /init 命令的关系：/init 扫描仓库并生成或改进 AGENTS.md（rules.mdx 的 Initialize 一节）——指令本身也可以由 agent 来写，形成"项目约定的自举"。

## 9.10 优先级的完整矩阵：一张表看懂"谁覆盖谁"

9.3 的"最后者胜"在多层来源下容易记混，这里把优先级关系整理成矩阵（顺序即优先级，从低到高；字段级覆盖指同一配置字段，规则级拼接指权限规则集）：

| 来源层 | 普通字段 | 权限规则 | 指令 |
| --- | --- | --- | --- |
| 全局目录（$HOME/.config/opencode/） | 基线 | 基线 | 全局 AGENTS.md |
| 项目目录（opencode.json） | 覆盖全局 | 拼接求值 | 项目 AGENTS.md |
| 嵌套目录 | 覆盖上层 | 拼接求值 | 目录级生效 |
| 会话保存（PermissionSaved） | —— | 拼接（用户批准） | —— |
| 托管策略（managed policy） | 不可覆盖 | 最高优先、不可撤销 | —— |
| Location 实例（四种来源） | 运行时覆盖 | 运行时拼接 | 实例注入 |

矩阵揭示的不对称值得注意：普通字段走"覆盖"（一处定义生效），权限走"拼接"（多处规则共同求值）——8.3 已论证这是权限语义的必然；托管策略在权限列的"最高优先"来自 8.9 的组织信任边界。矩阵还有一个容易忽略的行间关系：**会话保存的规则介于项目与托管之间**——用户当场批准的"always"成为持久规则后，其效力高于项目默认，但永远压不过托管策略（组织的 deny 不可被用户的 always 覆盖）。这张矩阵是排障的第一工具：配置不生效时，按列找"这个字段/规则"在哪一层定义了更高优先的值。

## 9.11 配置错误的诊断面

配置系统的用户体验一半在"配错了能不能快速定位"。OpenCode 的诊断面有四个支点。其一，**加载期一次性判定**（9.4 的加载期变量求值）——变量缺失、schema 违规在启动时报告，错误消息带来源（哪份文档哪一层）；其二，**归一化的兼容报告**——normalize 对旧键的接受是"静默兼容"还是"提示迁移"，决定用户是否被老配置悄悄困住（lsp 键这类残留的静默接受是刻意的：不为已失效功能打扰用户，但 schema 演进中的破坏性变更必须显式报错）；其三，**文档来源标记**——2.3 与 9.2 的 Document 携带来源（project/claude/file/content 四种，routes.ts 的 Config.node 注入），诊断消息能说"来自哪个文件哪一层"；其四，**热重载的事件化**——配置变更经 Bus 广播（9.5），前端可以展示"配置已重载、改了什么"，TUI 的 dialog-config 呈现生效配置。四个支点的共同理念：**配置错误是开发错误，要用开发错误的工具链对待**——快速定位、来源明确、变更可见，而不是让用户的配置静默失效。这也呼应了第二章"类型即文档"的立场：schema 校验错误的消息本身就是配置系统的 API 文档。

## 9.13 一个配置文档的逐段走读

把第九章的机制落到一份典型的 opencode.json 上逐段走读（字段名基于 schema 的可配置面：provider、agent、permission、mcp、keybinds、theme、plugin、compaction 参数等）。**provider 段**：声明自定义 provider（provider.ts 的注册表消费），可给 base_url、模型列表、鉴权引用——变量展开（9.4）在加载期把 {env:} 引用换成真值，所以配置文件里不该出现明文 key（凭据走 Credential，第七章）。**agent 段**：定义或修改 agent——内置的 build/plan 可被覆盖（Editor 注册表），自定义 agent 声明模型绑定、步数上限、权限规则集（第八章 8.6 的"能力即数据"）；归一化层对 agent 字段做版本迁移。**permission 段**：规则数组按 8.2 的三元组书写，顺序有意义（最后匹配生效），项目级的谨慎规则（deny 外发域名、ask 破坏命令）写在这里；托管策略会在求值时压过它们。**mcp 段**：服务器清单（stdio 的命令或 http 的地址），Mcp 连接池按它管理连接（第十章），变更触发前缀对齐重建。**keybinds 与 theme 段**：纯前端消费（TUI 的键位与主题），但走同一配置管线——同一份发现、归一化、合并逻辑。**compaction 参数**：Settings 的 auto/keep/precompute/buffer（第五章 5.3），State 模式消费（9.6）。走读的结论：一份配置文档的每一段都有明确的消费服务、明确的优先级行为、明确的错误报告路径——配置的"可理解性"不是靠文档堆出来的，而是靠消费链路的规整性长出来的。

## 9.14 指令系统的作用域语义与加载时序

指令（AGENTS.md）与机器配置的作用域语义有微妙差异，值得单独精确化。机器配置的层级是"覆盖或拼接"（9.3），指令的层级是**按语境叠加**：全局 AGENTS.md 管一切会话，项目 AGENTS.md 管本项目会话，嵌套目录的 AGENTS.md 只在模型操作该目录内容时生效（instruction-discovery.ts 的发现逻辑按路径匹配激活）——同一条指令的适用范围由文件位置决定，这与编辑器世界的 rules 文件语义一致（官方 rules.mdx 的定位）。叠加不是覆盖而是**累加**：处理子目录文件时，全局加项目加子目录三级指令同时在场——因为指令是"行为约束"而不是"参数值"，约束的叠加天然合规（约束 A 与约束 B 可以同时成立）。加载时序（第九章与第三章的交界）重述一遍完整链：会话创建 → 发现层扫描出指令清单 → 装载层读文件解析 frontmatter（gray-matter）→ instruction-state 记录就绪状态 → runner 的输入门控（InstructionState.prepare）在未就绪时保持 pending → 就绪后 baseTranscript 注入（5.6）。时序里最重要的一环是门控：它把"指令装载是异步的"从一个竞态隐患变成一个显式状态——第三章 3.3 的 pending 机制消费它。指令与配置还有一个工程差异：指令是**自然语言**，无法 schema 校验，其质量只能靠 /init 的生成规范与人类的评审——这是配置系统里唯一"不可形式验证"的层，也是它在 prompt 工程意义上最敏感的层。

## 9.16 配置的演进策略：向前兼容作为第一约束

配置系统面对的长期问题是：用户的配置文件写于半年前，要能被今天以及一年后的代码正确理解。9.2 的归一化层处理"过去到现在"，这里把演进的长期策略补全。策略一：**schema 只加不改**——新字段可加，旧字段语义不变；语义变化通过"新键加旧键别名"实现（normalize 对旧键的兼容解码——lsp 键的静默接受即此策略的实例）。策略二：**破坏性迁移显式化**——确需改变语义时，normalize 的版本迁移承担转换，且迁移逻辑要过测试（packages/core/test/config/ 的覆盖面）。策略三：**未知的宽容**——配置里出现当前版本不认识的键时的取舍：报错（严格，用户立即发现拼错）还是忽略（宽容，向前兼容优先）。OpenCode 的取向从 normalize 对旧键的静默兼容可以看出偏宽容——但宽容有代价（拼错的键静默失效，用户以为配置生效了），因此 9.11 的诊断面（来源标记、生效视图）是宽容策略的必要补偿：**宽容接受加可见报告**，两者合起来才完整。策略四：**配置与代码的同步发布**——新配置项随支持它的代码同版本发布，文档与 schema 同步（web 站点的 docs 与 packages/schema 同源演进）。这套策略的深层立场与第四章的迁移体系一致：**用户数据（配置也是数据）的演化路径必须永远有工程载体**，靠"发个公告让用户改文件"不算载体。凡是允许用户写持久声明（配置、规则、指令）的系统，都值得在第一天就把这四条策略立起来——演化成本是复利，晚立一年贵十倍。

## 9.18 配置排障的实战路径

把 9.11 的诊断面与 9.10 的优先级矩阵合成一条实战排障路径（"我配了 X 但没生效"的标准流程）。**第一步：确认文件被看见**——发现层找的是固定候选（discovery.ts:12 的 opencode.json/jsonc），先确认文件名、位置（全局还是项目目录）正确；JSONC 的注释语法错误会让解析失败（jsonc-parser 的报错会带位置）。**第二步：确认字段走对了层**——按 9.10 矩阵查该字段是否存在更高优先的定义（全局有没有？托管策略有没有？），权限类问题还要按 8.11 检查规则顺序（最后匹配生效）。**第三步：确认值通过了归一化**——旧键被静默兼容时（lsp 类），行为可能与直觉不同；变量引用（{env:}）在加载期求值，环境变量缺失会在此报错。**第四步：确认热重载发生**——文件监听是否覆盖该路径（9.5 的 Watcher），变更事件是否触发了 State 更新（9.6 的 notify 链），进行中的调用按快照语义不追溯（8.9）。**第五步：确认消费方在用**——有些字段只在特定时机被消费（agent 定义在会话创建时读取，改了之后新会话才生效——这是语义而非 bug）；消费方的 State 是否实现了 reload。五步走完仍未解决，剩下的可能就是 bug——此时带着前四步的证据（来源标记、生效视图、变更事件）去查代码，比盲查快一个量级。这条路径的一般化：**配置问题的排查永远是"发现—合并—求值—分发—消费"五段管线的逐段验证**，管线思想（9.1）在排障时同样成立。

## 9.20 指令写作的工程化：AGENTS.md 的质量观

指令是自然语言，但它的写作可以有工程化的质量观（作者分析，基于 9.9 的机制）。**原则一：写可验证的事实**——"测试用 bun run test 跑"是模型可执行的事实，"代码要保持整洁"是模型无法操作的空话——指令的每一句都应该能映射到一个工具调用或一个判断准则。**原则二：结构稳定**——构建命令、架构地图、约定分节，模型检索指令时依赖结构（5.6 的注入位置固定，结构稳定让模型的"指令感"可预期）。**原则三：保持精炼**——指令进每一轮请求的半永久层（5.15 的第二层），冗长的指令是永久性的 token 税与注意力稀释，每句都值得问"模型没有这句会做错什么"。**原则四：作用域下放**——只与子目录相关的约定写进子目录的 AGENTS.md（9.14 的语境叠加），全局文件保持全局性。**原则五：与 /init 协作**——生成是起点不是终点，/init 扫描生成初稿（rules.mdx 的行为），人工修订的事实密度决定其价值。**原则六：版本化**——AGENTS.md 随仓库进 git（它就是代码库的一部分），指令变更走 review——模型的行为契约应当与人享同等的变更纪律。六条原则的底层逻辑是同一个：**指令是写给"一个能力很强但缺乏上下文的读者"的操作手册**——这个读者的特点（无常识、零记忆、字面执行）决定了好的指令长什么样。指令质量是 agent 输出质量的第一杠杆，而它完全是项目方可控的免费变量。

## 9.21 本章小结

配置系统的全链路：发现（discovery 的候选与 wellknown 约定）→ 解析归一化（normalize 的版本迁移与旧键兼容）→ 有序合并（latest 的最后者胜与权限的求值语义分野）→ 变量展开（加载期静态求值）→ State 消费范式（initial/editor/notify/transform/reload 四件套）→ 热重载（watch 与快照语义）。它的设计立场可以概括为一句话：**配置是声明式的状态机输入，加载是求值，消费是快照，修改是受控事件**。下一章离开单机内部，看两个把 OpenCode 接入外部世界的扩展面——MCP 与插件，它们是"配置"声明的能力如何被真正连进来的故事。
