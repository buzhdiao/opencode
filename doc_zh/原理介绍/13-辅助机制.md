# 第十三章 · 辅助机制

## 13.1 卫星系统：能力半径由它们决定

主循环（第三、五章）、工具（第六章）、模型（第七章）、权限（第八章）构成了 agent 的躯干，但 agent 的**能力半径**——它能感知什么、能记住什么、能回到哪里——由一圈卫星系统决定。本章逐个解剖：检索（ripgrep 与全文搜索）、快照与回滚（snapshot）、版本控制（vcs 与 worktree）、伪终端（pty 与 persistent-pty）、语音与搜索（voice、websearch）、作业与调度（job、schedule）、以及底层杂项设施。这些模块的共同形态是"core 里的一个独立文件或子目录、一个 Context.Service、挂进 Location 或全局树"（第二章的服务模式），差异在各自面对的领域难题。

## 13.2 检索：ripgrep 适配器的分层哲学

ripgrep.ts（core/src/ripgrep.ts）是"执行适配器"的教科书案例。它自我注释明确："核心内置的 ripgrep 执行适配器，刻意只暴露面向进程的原始行数据，不做模型文本或权限行为处理；搜索功能将这些行映射为文件系统结果，展示与权限提示由叶子工具负责。"这句话宣布了一个严格的职责切分：ripgrep.ts 管"怎么跑 rg 进程并可靠地拿到结构化结果"，grep/glob 工具（tool/plugin/）管"结果怎么变成模型可见的文本、要不要弹权限"。

适配器的工程细节对应真实故障模式：stderr 捕获上限 8KB（ERROR_BYTES——失控的 rg 不该用错误输出淹没内存）；单行子匹配上限 100（MAX_SUBMATCHES——病态正则的一行可以产生无限捕获组）；单行文本上限 2000 字符（MAX_LINE_CHARS——超长行截断，模型的上下文不该被一行压缩日志吃掉）。输出解析走 rg 的 JSON 模式（RawMatch schema 定义 type=match 行的结构），schema 校验保证"进程输出的任何一行都是类型化数据"而不是裸字符串。进程的定位由 ripgrep/binary.ts（RipgrepBinary 服务）负责——平台差异、内置二进制与系统二进制的择优；执行用 effect 的 ChildProcess，经 Environment 服务（core/src/environment/）决定进程在哪里跑（本地或远端执行环境——Environment 是"执行位置"的抽象，多 Location 与远程执行的可能接缝）。

检索还有第二条路径：filesystem/search.ts（FileSystemSearch，注释里的"fff"是全文检索引擎的代称）提供**语义化/全文的文件搜索**（区别于 rg 的正则行匹配），routes.ts 装配清单里的位置说明它是应用级服务。两条路径的分工：rg 管精确模式匹配（工具 grep/glob 的后端），fff 管"我忘了这个函数在哪"式的模糊检索——TUI 的 @ 引用补全（第十二章 autocomplete）就是它的高频消费方。

## 13.3 Snapshot：让"撤销"成为可能

snapshot.ts（core/src/snapshot.ts）实现文件状态的快照与恢复，四个操作（错误类型 Error 的 operation 字段明示）：capture（捕获）、files（列文件）、diff（比较）、restore（恢复）。比较接口 CompareInput 接受两棵快照树的 ID（from/to）——"两次快照之间的差异"是 agent 工作汇报的基本单元（这个会话改了什么）。实现机制有一个关键设计：**快照建立在内部 Git 之上**（snapshot.ts 导入 Git 服务——core/src/git.ts 的封装，配合 Hash 工具为 worktree 生成稳定短哈希，FSUtil 处理文件操作）。快照不是"复制文件树"而是 git 的对象存储：文件内容进对象库、快照 ID 指向树对象——增量天然（未变的文件不重复存储）、恢复即 checkout、diff 即 git diff。用现成的版本控制原语实现快照，是把领域问题翻译成已有 solved problem 的典范。

快照的消费时机（第六章、第八章的场景）贯穿工具执行：写类工具（edit/write/patch）执行前捕获，执行后可比较可回滚——**回滚是 agent 失控的最后保险**。会话的 revert（session/revert.ts）与 move（session/move.ts）也依赖快照语义。快照存储在用户数据目录（Global 服务，第四章的数据目录布局），与主仓库的 git 历史**完全隔离**——快照不污染用户的暂存区与提交历史，这是一个容易做错的细节（直接在用户仓库建提交会让用户 git log 变脏），内部独立 worktree/对象库的隔离方案是正确解。

## 13.4 VCS：状态聚合与 patch 协议

vcs.ts（core/src/vcs.ts）比 snapshot 高一层：它聚合**当前工作区相对版本控制的全部状态**——Mode（git/none 等）、Info、BranchList、FileStatus、Untracked、Base（基线）等视图（schema 来自 @opencode/schema/vcs），经 VcsEvent 广播变化（前端的状态栏与"文件变更"面板的来源）。实现用 Semaphore（状态刷新的串行化——git status 的调用不该并发挤在一起）与 FiberSet（后台刷新 fiber 的容器）。插件侧有 VcsDefinition 与 VcsEditor 契约（@opencode/plugin/effect/vcs）——vcs 的实现可被插件替换（对接非 git 的版本系统）。

vcs/patch.ts 定义补丁协议的常量与工具：emptyPatch、MAX_TOTAL_PATCH_BYTES（补丁总字节数上限——超大的变更不该被一次性塞进上下文或权限弹窗）、PATCH_CONTEXT_LINES（patch 的上下文行数——diff 的紧凑性与可读性权衡）。patch 的消费者链：edit/write 工具产出变更 → diff 预览（第八章）→ TUI 的 patch-diff.tsx 渲染（第十二章）→ GitHub 集成的 PR（doc_zh/components/07）。**patch 是"变更"这个概念在系统里的通用语言**，从工具到 UI 到外部集成都说这门语言。

## 13.5 Worktree：并行世界的管理

worktree.ts（core/src/worktree.ts）管理 git worktree——一个仓库的多棵工作树，是"并行 agent 任务"的物理基础：两个会话同时改代码，互不踩脚的办法是各占一棵 worktree。worktree 服务的实现结合了 Git 封装、数据库持久化（drizzle 表——worktree 的元数据在库里，第四章的 add_workspace_id 系列迁移与之相关）、Slug 生成器（util/slug.ts 生成目录名——工作树目录如 .opencode 下的短名）、FSUtil 与 Location 服务的配合（新 worktree 即新 Location 的候选——第二章 Location 模型的动态面）。Worktree 与 workspace 的关系：workspace 是逻辑分组，worktree 是物理工作树，worktree 输入输出 schema（@opencode/schema/worktree）覆盖创建、列表、切换与事件。

## 13.6 PTY：伪终端与崩溃可恢复

pty.ts（core/src/pty.ts）管理伪终端会话：BUFFER_LIMIT = 2MB（输出缓冲上限，超过裁剪旧内容——长跑的守护进程输出不该吃光内存）；EXITED_LIMIT = 25（已退出的会话保留上限，注释明言避免被遗弃的终端无限累积）；原生实现按需加载（lazy(() => import("#pty"))，#pty 是运行时差异的导入映射——Bun/Node 的 PTY 原生绑定差异）；订阅者接口 onData/结束回调；ShellSelect 决定默认 shell。pty 事件经 Bus 广播（schema 来自 @opencode/schema/pty），TUI 的终端面板与会话渲染消费。

persistent-pty.ts（core/src/persistent-pty.ts）是关键增强：**持久伪终端**——PTY 子进程的生命周期独立于引擎进程，引擎重启后凭票据（pty/ticket.ts 的 PtyTicket）重新附着。"持久"的价值链：shell 工具的转后台作业（第六章）跑在 PTY 里 → 引擎崩溃重启 → 作业还在跑 → 恢复协议找回输出与退出状态 → notifyWhenDone 的唤醒仍然发生。没有 persistent-pty，第三章的崩溃恢复对"正在跑测试"的会话就是残缺的（进程死了，恢复无从谈起）。这是"可恢复"原则从会话状态延伸到子进程的完整闭环，也是第十三章与第三章互文的最好例子。

## 13.7 Voice 与 WebSearch：两个外部能力面

voice.ts（core/src/voice.ts）实现语音会话：基于 @opencode/ai/experimental 的 Realtime 抽象（RealtimeSession、RealtimeTransport 与传输类型列表），模型信息 ModelInfo 含 supported transports 与"服务器是否具备启动该模型的凭证"（available 字段——语音能力依赖 provider 凭据，Credential 与 RequestExecutor 参与，Integration 服务对接集成面）。语音是实验面（experimental/），传输类型的多态（WebRTC/WebSocket 等）由 RealtimeTransportType 表达。

websearch.ts（core/src/websearch.ts）实现网页搜索：Provider 抽象（多家搜索后端）、Input/Event schema、KV 存检索状态（第四章 KV 的消费例）、HTTP 429 的专门处理（HttpClientError——限流是搜索 API 的常态，退避与 provider 轮换的消费逻辑在此）。websearch 作为工具（tool/plugin/websearch.ts）暴露给模型，也可被插件定制（core/src/plugin/websearch/ 的编织点）。

## 13.8 Job 与 Schedule：后台活动的通用框架

job.ts（core/src/job.ts）是后台作业的通用框架：shell 转后台（第六章）、子代理后台运行、长时间工具——都以 Job 为载体，统一"启动、进度、完成、唤醒"的生命周期。schedule.ts（core/src/schedule.ts）是调度面（定时任务——agent 的会话可以被定时触发，server 的 handlers/schedule.ts 暴露管理端点）。两者的分工：Job 管"这个活动怎么追踪"，Schedule 管"什么时候启动什么"。配套的杂项设施快速清点：kv.ts（键值存储，第四章）、shared-cache.ts（跨会话共享缓存）、event-logger.ts（事件日志）、form.ts（表单体系——MCP elicit 与权限交互的结构化输入）、artifact.ts 与 image.ts、mime.ts（媒体识别）、formatter.ts（格式化器——代码格式化工具的接缝，CONTRIBUTING 里"formatters"是与 LSP 并列的贡献面）、reference.ts（引用）、generate.ts（生成面）、integration.ts（集成管理）、console-access.ts（控制台访问——packages/console 云端的对接）、usage-limits.ts（限额）、flag.ts（特性旗标）、instruction-discovery.ts（指令发现，第九章）、file-mutation.ts 与 file-write.ts、file-retention.ts（文件写入与保留，第四章）、repository.ts 与 repository-cache.ts（仓库缓存）、workspace.ts（第九章）、wellknown.ts、skill.ts（技能）、location 系列文件（location-lifecycle、location-activity、location-services、location-service-map——第二章 Location 生态的实现细节）。

## 13.9 卫星系统的共同设计模式

清点完毕，提炼共性。模式一：**适配器收窄**（ripgrep 只给原始行数据、Git 只给封装原语）——外部世界的能力进 core 时先过一道"职责收窄"的闸，展示与策略留给上层。模式二：**状态先行落库**（worktree 元数据、job 状态、pty 票据）——卫星系统的状态同样服从第四章公理，崩溃恢复才可能闭环到子进程级。模式三：**事件化**（VcsEvent、pty 事件、McpEvent、权限事件）——一切状态变化走 Bus，卫星系统没有"只有自己知道"的状态。模式四：**可替换实现**（vcs 的插件契约、Environment 的执行位置、PT 原生绑定）——卫星系统是"策略与机制分离"的持续践行区。四个模式叠加的净效果：卫星系统可以多、可以换、可以崩，主循环的视角里它们只是"会发事件的服务"。

## 13.10 快照的数据结构：树 ID、短哈希与增量存储

13.3 说快照建在内部 Git 之上，这里补数据结构。快照 ID 指向一棵**树对象**（tree object——git 的目录快照原语），ID 本身是内容哈希的短形式（Hash 工具为 worktree 生成稳定短哈希，snapshot.ts 的导入可见）。树 ID 的内容寻址性质带来三个免费性质：**去重**（相同内容的内容哈希相同——两次快照间未变的文件天然共享存储）、**完整性**（ID 变了即内容变了，检测篡改免费）、**并行安全**（两个并发快照各自生成树，互不干扰）。CompareInput（from, to）两棵树的 diff 由 Git 原语直接给出——"这个会话改了什么"的答案就是 from 与 to 的树差异。存储布局在用户数据目录（Global）与用户主仓库隔离（13.3 已论证不污染用户 git 历史）。恢复（restore）是 checkout 语义：把树对象写回工作区——**回滚的原子性由 git 的对象完整性保证**，中断的 checkout 重跑即可（幂等）。这套设计可以总结为"用版本控制的原语实现版本控制之上的功能"——不自建对象库、不自算哈希、不自写 diff，把领域问题完全翻译到已有原语上。

## 13.11 执行位置抽象：Environment 与远程化的接缝

13.2 提到 Environment 服务（core/src/environment/）决定"进程在哪里执行"，这个抽象值得单独展开，因为它是 OpenCode 未来"远程执行"（agent 在云端容器跑，界面在本地）的架构接缝。Environment 的当前实现是本地执行（子进程在本机 spawn），但它的接口把"执行位置"从各工具的实现里抽了出来：shell 工具不直接 spawn，而是向 Environment 请求执行；ripgrep 适配器同样经 Environment 跑 rg（13.2）；MCP 的 stdio 传输也经它创建子进程（10.2 的 ChildProcess 导入经 environment/index.js）。一旦执行请求全部收口到 Environment，"换一个执行位置"（容器、远端机器、沙箱）就变成提供另一个 Environment 实现——工具与协议层零改动。这与第二章的替换机制（AppNodeBuilder 的 replacements）是同一模式的两个尺度：节点替换换"服务实现"，Environment 换"世界位置"。session/environment.ts（session/ 目录同名文件）则处理会话维度的环境语义（会话执行环境的快照与描述）。审视这个抽象的正确性可以问一个问题：哪些能力是"本地执行"隐含假设的？文件系统的共享（edit 工具直接读写）、PTY 的可附着、信号的可投递——远程化时这些都要重新落实（文件经同步或远端 fs、PTY 经持久终端协议转发、信号经消息通道）。Environment 收口的价值正在于：这些假设从"散落在每个工具里"变成"集中在抽象的文档与测试里"，未来接缝清晰可见。

## 13.14 三条检索路径的分工与对比

13.2 出现了三种检索（rg 正则、glob 文件名、fff 全文），把它们与"读取"并置成一张分工表，这是模型检索策略与工具设计的对照基础：

| 路径 | 工具 | 匹配对象 | 强项 | 弱项 |
| --- | --- | --- | --- | --- |
| 内容正则 | grep（rg 后端） | 行内容模式 | 精确定位、正则表达力 | 不知语义（同义改写找不到） |
| 文件名模式 | glob | 路径通配 | 结构性发现（找配置、找测试） | 不看内容 |
| 全文检索 | fff 后端 | 词项与相关度 | 模糊定位（忘了名字记得概念） | 无精确保证 |
| 定点读取 | read | 具体文件 | 完整上下文 | 需先知道路径 |

四条路径构成模型的"检索工作流"：glob 找候选、grep 定内容、fff 兜模糊、read 取全文——工具描述（6.9）对四者的互相指涉让模型能自主编排。工程上的互补性来自**索引结构的本质差异**：rg 是扫描器（无索引、实时、精确），fff 是索引器（预建索引、快、模糊），glob 是文件系统遍历的过滤——没有哪条路径在所有维度占优，所以三条并存而非互相替代。权限与展示的分层（ripgrep 适配器只出原始行，工具层做映射与提示）在这张表下更清晰：四条路径共享同一个"原始数据 → 工具映射 → 权限提示"的三段结构，差异只在第一段的数据源。

## 13.15 媒体与附件管线：从字节到上下文

图片、音频、文件附件的进出走一条专门的媒体管线，串联 core 的几个小模块。**入口侧**：用户粘贴或拖入的附件经 TUI 的 local-attachment（12.4）上传到 server 的 media handler（handlers/media.ts 与 media-uri.ts——媒体 URI 的约定），存储进 blob 侧（4.2 的行外存储），消息引用媒体 URI。**识别侧**：mime.ts 做类型识别（魔数与扩展名的双重判定），image.ts 处理图片的元数据（尺寸、格式），编码换算参与第五章的 token 折算（1500/2000 的估算输入）。**模型侧**：能力位检查（capabilities 的图片支持，第七章）决定附件能不能进请求——不支持图片的模型收到的是文本化的描述而不是原始数据。**出口侧**：工具产出的媒体（image-generate 的生成图、截图）走 normalizeImages 的转码压缩（6.4）再进上下文或落盘；artifact.ts（core/src/artifact.ts）承载"工件"语义——会话产出的可引用物（生成的图、导出的报告）有稳定 ID 与生命周期。管线的架构要点：**媒体的物理存储、逻辑引用、上下文呈现三个层始终分离**——存储决定"放哪"，URI 决定"怎么指"，呈现决定"给模型看什么"，任何一层的技术替换（存储引擎、媒体格式）不影响其他两层。

## 13.17 卫星系统的启动与依赖次序

卫星系统众多，它们之间的初始化依赖构成一张次序图，值得梳理（对理解 routes.ts 装配清单的排列有帮助）。底层优先：Global（数据目录）先行——一切持久化的前提；Database 与 KV 随后——库文件的打开与迁移（第四章）必须在任何持久化消费者之前；Bus 依赖 Database（事件落库），因此紧随其后；Credential 独立（平台安全存储）但被 OAuth 与 voice 依赖。中层：Config 依赖文件监听（Watcher）；Mcp 依赖 Config（服务器清单）与 ChildProcess（Environment）；Permission 依赖 Agent（规则解析）与 PermissionSaved（依赖 Database）；Session 家族依赖 Database、Bus、Tool、Permission——几乎汇聚所有中层。上层：TUI 与前端只依赖 server 的端点面，不感知 core 的内部次序。次序图的工程意义：**装配顺序错误会以"服务缺失"的运行时错误暴露**（Effect 的 Context 缺依赖是显式错误——第二章 2.8），而 AppNodeBuilder 的节点清单加依赖声明让次序由图自动求解（拓扑序），开发者只声明"依赖谁"，不用手工排序——这是图式装配相对手工构造在正确性上的又一红利。次序图还有一个运维视角：启动日志按拓扑序打印服务就绪，卡在哪个服务一目了然（16 章的状态面读的就是这张图的实时版）。

## 13.19 检索与文件访问的权限隐私面

第十三章的卫星系统里有几处"能看见用户数据"的能力（检索、快照、vcs 状态），它们的权限与隐私面值得单独明确。**检索面**：ripgrep 与 fff 扫描的是用户工作区的内容，检索结果进模型上下文——权限语义是"读"（6.12 光谱的低危险档），但隐私语义更高（内容会离开本机去往模型 provider——7 章）。**文件访问的边界**：file-access.ts 的界内界外判定（8.5）约束工具的路径可达范围，Location 外目录的读取需要显式授权——检索工具同样服从这个边界（ripgrep 适配器刻意不管权限，但工具层管，13.2 的职责切分）。**快照的隐私**：快照对象库存的是工作区内容副本（13.10），留在本地数据目录——与主库同级的本地资产（4.13 的可移植性论述覆盖它）。**vcs 状态的暴露**：分支、文件状态、未跟踪文件列表经事件广播（13.4），这些元数据的可见范围同样是本地订阅者。整面的立场可以概括为：**检索与可见性能力默认本地闭环，出网的部分（模型调用、websearch、webfetch）由独立的动作类别治理**——用户评估"agent 会把什么带出我的机器"，答案是：只有显式配置的模型请求与明确批准的外发动作，检索与快照不出本机。这个答案的可信度建立在结构上（权限的动作类别划分，第八章）而不是承诺上。

## 13.21 检索质量的调试：从模型抱怨到设施参数

检索是模型行为质量的隐形地基（找不到代码 → 改错地方），它的调试路径值得单列（作者分析）。**症状归因**：模型"没找到该找的东西"有三种机理——检索面缺失（目标内容不在索引范围：新文件未入 fff 索引、忽略规则误伤）、查询面失当（模型的检索词太窄或太宽——工具描述的引导问题，6.9）、呈现面截断（结果被 13.2 的行截断或分页吃掉了关键行）。**对应手段**：检索面问题查 ripgrep 适配器的调用参数与 binary 定位（13.2）、查 fff 的索引范围与 file-access 边界（13.19）；查询面问题修工具描述（一行字符串的变更，6.9 的第四条原则）或引导模型组合路径（13.14 的工作流）；呈现面问题调截断常量与结果排序（MAX_LINE_CHARS 这类参数是可调的治理点，但调整要过 15.17 的第零问——放宽截断就是放宽 token 预算）。**回归防护**：检索行为的回归用"固定查询加期望命中"的 fixture 表达（14.2 的录制思想在检索面的应用），rg 的版本升级（binary 的替换）尤其要过这层回归——外部工具的版本漂移是检索质量的隐形变量。检索调试的通则：**"模型找不到"从来不是单一故障，它是三条链（索引—查询—呈现）中某一环的退化**——链式归因同样适用于任何"模型行为退化"类的模糊抱怨。

## 13.22 本章小结

本章清点了一圈卫星系统并提炼了它们的共同模式：检索的双路径（rg 精确、fff 模糊）与适配器收窄；快照的内部 Git 实现与"撤销保险"；vcs 的状态聚合与 patch 通用语言；worktree 的并行物理基础；pty 的缓冲治理与 persistent-pty 的崩溃闭环；voice/websearch 的外部能力面；job/schedule 的后台框架。至此，系统的纵向剖析完成：循环、架构、会话、存储、上下文、工具、模型、权限、配置、扩展、传输、前端、卫星——十四章的机制全部展开。最后一章做两件事：看质量与构建面如何保障这一切持续演化，然后做全书的设计复盘。
