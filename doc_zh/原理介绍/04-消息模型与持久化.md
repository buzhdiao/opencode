# 第四章 · 消息模型与持久化

## 4.1 为什么是嵌入式 SQLite：一次存储选型的完整论证

第三章反复出现"状态先行落库"这句话，本章回答"库是什么、怎么落"。OpenCode 的选择是嵌入式 SQLite，配 drizzle-orm 做类型化查询、配 Effect 封装（packages/effect-drizzle-sqlite，核心类 EffectDrizzleSqlite，见 packages/core/src/database/drizzle.ts）。这个选择值得完整论证，因为候选方案其实很多：纯文件（JSON/NDJSON）、浏览器式 IndexedDB、客户端-服务器数据库（Postgres）、键值存储（LevelDB/RocksDB）。

纯文件方案最先出局：会话状态是高频小事务（每步要更新消息状态、追加事件、推进序列号），多进程并发写（server 进程、迁移、调试工具）需要文件锁，而文件锁在崩溃时的一致性是著名难题。客户端-服务器数据库出局的理由更直接：OpenCode 是单用户桌面级产品，让用户为了本地历史装一个数据库服务不可接受。键值存储缺乏结构化查询——第三章的陈旧结算需要"扫出所有 running 状态的工具调用"，压缩模块需要按会话范围读历史并做 json_extract，这些需求天然是关系查询。SQLite 恰好卡在需求集中点上：嵌入式（零部署、单文件、随数据目录迁移）、支持完整 SQL 与事务、有成熟的崩溃恢复（WAL）、且**三种运行时都有绑定**——database/sqlite.bun.ts、sqlite.node.ts、sqlite.workerd.ts 三个文件分别是 Bun、Node、Cloudflare workerd 的后端实现，配合 supportsForeignKeyToggle（migration.ts 对运行时能力差异的探测）处理各运行时外键行为的差异。这就是第二章"server 可嵌入 workerd"承诺在存储层的兑现：同一个内核换个 SQLite 绑定就能跑进边缘运行时。

选型还有一个容易被忽略的维度：**数据属于谁**。OpenCode 的会话历史是用户的本地资产（存在用户数据目录，由 Global 服务提供路径），不是云上租户数据。SQLite 单文件天然契合"本地资产"的语义：可拷贝、可备份、可被第三方工具直接打开检查。这决定了产品的隐私姿态，也决定了第五章快照与回滚可以放肆地本地化实现。

## 4.2 消息模型：历史是追加式的日志，不是可变的文档

进入表结构之前，先确立消息模型的数学形状。会话历史在引擎内的角色是**append-only 日志加受控投影**：消息一旦写入，其文本内容不可变；变化的是**状态字段**（pending/running/完成/中断）与派生投影。这个形状不是审美偏好，而是第三章恢复协议的要求——结算逻辑必须能区分"内容是什么"（不可变，可直接信任）与"状态是什么"（可变，崩溃后需改判）。若内容本身可变，崩溃后就没有可信的基线。

表结构由 drizzle 定义在 packages/core/src/session/sql.ts（会话、消息、收件箱、压缩记录、用量等表），事件序列表在 core/src/event/sql.ts（EventTable 与 EventSequenceTable）。查询入口在 session/store.ts 与 session/history.ts：store 提供"取一条消息、更新一个状态"的原子操作，history 提供"按会话读取有序历史"的投影操作。stored.ts 与 blob.ts 处理一个实际问题：消息体里可能有大对象（图片、长工具输出），表列存 JSON 序列化后体积膨胀，因此大二进制走 blob 侧存储、消息行留引用——这是"行内存要义、行外存重物"的经典布局。投影索引有专门的迁移照顾：session_message_projection_indexes 与 session_message_projection_order 两个迁移（packages/core/src/database/migration/ 目录下）为"按会话读有序消息"这一最高频查询建立了索引与排序保证——读路径的性能在 schema 层就被固化了。

消息之上还有一层**游标**抽象：session_message_cursor 迁移引入消息游标，使"从某个位置继续读历史"成为 O(1) 定位而非全表扫描。游标在两个消费方出现：压缩模块从游标处计算旧历史与新近原文的分界（第五章），事件回放从游标处向客户端补发缺口（4.4）。游标把"历史是流"的观念落到了存储层。

## 4.3 收件箱的事件溯源：从"字段"到"事实"

第三章说输入先入箱再消费，本章看收件箱在库里的形态。这里有一个值得解剖的架构演化：迁移列表里能看到 session_input_inbox 与 event_sourced_session_input 两个相邻迁移——收件箱最初只是会话表上的输入字段，后来被改造成**事件溯源**（event sourcing）形态。

改造的理由要从并发与恢复两头讲。字段形态下，"投递输入"与"消费输入"是对同一行的读改写，两个并发投递者（用户输入与 /compact 指令几乎同时到达）需要行锁保护，且消费过程崩溃后"哪些输入已被消费"不可精确判定。事件溯源形态下，每次投递是一条不可变的输入事实（带类型：用户消息/控制项；带投递模式：steer/queue；带序列号），消费是推进一个指针而不是删改事实。于是：并发投递变成追加写，天然安全；消费进度变成游标推进，崩溃后重放未消费的事实即可恢复；审计变成遍历事实流，谁在何时投了什么一目了然。第三章收件箱的两种投递模式、3.8 节的幂等恢复，在这个存储形态下都是自然性质而非小心维护的约定——**存储形态决定并发语义**，这是本套文档反复出现的主题。

事件溯源还有一个次生收益：**投影可重建**。历史投影（前端看到的消息时间线）可以从事实流重新推导，投影索引迁移（projection_indexes/projection_order）本质上是"为最常用投影建的物化视图"。当投影逻辑升级（比如消息渲染格式的修订），可以离线重放事实流重建投影而不动原始事实——这与第四章 Bus 的事件回放（4.4）是同一思想在不同层的实例。

## 4.4 Bus：持久化事件总线的设计

core/src/bus.ts 是全仓库的事件中枢，它的自我注释精确概括了职责："持久化事件（durable event）的发布/订阅中枢——事件落库、按聚合（aggregate）排序，支持实时订阅、按聚合的历史回放（log）与跨进程重放（replay）"。注意它不是进程内的 PubSub 简单加个落库，而是三个能力的乘积：实时分发（PubSub）、历史查询（log）、以及**缺口重放**（replay）——订阅者可以带着"我最后看到的序列号"来订阅，Bus 负责先补发缺口再接续实时流。

实现要点有四。其一，**序列号按聚合分配**：latestSequence（bus.ts 顶部）读取某聚合当前已持久化的最大序列号，无记录返回 -1；reserveSequence 以插入或取 max 的方式推进该聚合的序列水位，注释特别说明"供分叉聚合继承前缀"——会话被 fork 或迁移时，新聚合可以继承旧聚合的序列前缀，事件历史的连续性跨聚合保持。其二，**表结构双轨**：EventTable 存事件本体，EventSequenceTable 存每聚合的水位，两者在同一事务里更新，保证"事件可见时水位必然一致"。其三，**并发正确性靠 KeyedMutex**（bus.ts 导入）：同一聚合的写操作按键互斥，不同聚合并行——这是"键分片锁"模式，比全局锁吞吐高、比无锁安全。其四，**事件类型有溯源标记**：Durable 与 SessionEvent、SessionLegacy 等 schema（来自 @opencode/schema）区分持久事件与瞬时事件（ephemeral，MCP 模块的导入可见 ephemeral 构造器），不是所有事件都值得落库——光标闪烁类的高频瞬时事件走内存通道，状态变更类事件走持久通道，通道选择本身就是一次存储成本决策。

Bus 的上层消费者有两个方向。向内，core 的各服务互发事件（例如权限请求事件、MCP 工具列表变更事件）；向外，server 的 event-feed.ts 把 Bus 流接到 HTTP 订阅端点（第十一章），前端订阅后本地投影。**Bus 是"三端一致"承诺的物理实现点**：因为事件先落库再分发，任何订阅者无论何时接入（包括崩溃重连的 TUI），都能通过 log/replay 拿到完整且有序的历史——订阅者的位置在时间轴上是任意的，而看到的世界是一致的。

## 4.5 迁移体系：让 schema 的演化像日志一样可追加

数据模型必然演化：新功能要新列、性能问题要新索引、历史包袱要清理。SQLite 的 schema 演化机制是 migration，OpenCode 把它做成了一套纪律严明的体系，全部在 packages/core/src/database/ 下。

体系的第一特征是**物理布局**：migration/ 目录下每个迁移是一个按时间戳命名的独立文件（如 20260127222353_familiar_lady_ursula.ts、20260213144116_wakeful_the_professor.ts——时间戳加随机名，杜绝并发分支撞名），migration.gen.ts 自动生成按时间戳排序的迁移清单（migration.ts 的导入可见"自动生成的迁移列表（按时间戳排序）"），schema.gen.ts 则是**初始 schema 的一次性建表产物**——新库直接建出当前全量表结构，再逐个跑增量迁移追平；老库从零跑起。这种"快照加增量"双轨是迁移体系的常见成熟形态：新用户不付全量重放的时间成本，老用户不丢演化路径。

体系的第二特征是**执行协议**。migration.ts 的实现要点：迁移在事务里执行（Transaction 类型即 Database.transaction 回调句柄）；执行前探测运行时能力（supportsForeignKeyToggle——SQLite 的外键开关在全库层面切换，迁移期间通常要关闭以允许表重建，跑完恢复）；每个迁移只跑一次的判定依赖库内记录的已执行清单。值得注意 V1Migration（database/v1-migration.ts，配 v1-migration.bun.ts 与 v1-migration.noop.ts 两个运行时变体）：这是跨大版本的数据迁移层——v1 的数据形态与 v2 不同，v1-migration 负责把旧版数据目录导入 v2 的库，且作为路由层的一部分随服务挂载（routes.ts 的导入可见"v1 → v2 数据库迁移层（与 API 一起挂载）"），server 还提供专门的 migration handler（handlers/migration.ts）供前端展示迁移进度与状态。跨版本迁移被当作一等公民而不是"一次性脚本"，理由是用户升级的时间是任意的，迁移必须在产品运行时可用。

体系的第三特征是**可测试性**：database-migration.test.ts 与 database-drizzle.test.ts、database.test.ts 三个测试文件（packages/core/test/）覆盖迁移正确性——迁移是数据安全事故的高发区（一条坏迁移能毁掉用户全部历史），OpenCode 把它纳入与其他代码同级的测试纪律。第十四章展开测试方法。

## 4.6 迁移案例研究：从迁移名读产品史

迁移目录本身就是一部压缩的产品演化史，选几个有代表性的拆解。

**workspace 系列**（20260225215848_workspace.ts、20260227213759_add_session_workspace_id.ts、20260303231226_add_workspace_fields.ts、20260410174513_workspace-name.ts、20260507164347_add_workspace_time.ts）：workspace 是"一个项目下的多个工作上下文"概念，五次迁移覆盖了引入、关联会话、补字段、命名、时间线——一个特性的存储面分五步长出来，每步独立可回溯，这正是增量迁移相对"大爆炸改表"的价值。

**input inbox 系列**（20260603141458_session_input_inbox.ts、20260604172448_event_sourced_session_input.ts）：4.3 节的演化在这里留下物证——先建收件箱表，再溯源化。两步而非一步，说明演化本身也是渐进的：先加实体，再改语义。

**性能系列**（20260603001617_session_message_projection_indexes.ts、20260603040000_session_message_projection_order.ts、20260312043431_session_message_cursor.ts）：纯性能迁移不引入业务字段，只建索引、定序、加游标。把性能改动与功能改动放进同一条迁移流，保证任何环境的库结构都唯一确定——不存在"性能补丁打没打"这种歧义状态。

**数据治理系列**（20260601010001_normalize_storage_paths.ts、20260511000411_data_migration_state.ts、20260309230000_move_org_to_state.ts）：路径归一化（存储路径格式修订后的存量数据清洗）与数据迁移状态表（迁移自身也需要状态追踪，长跑迁移可断点续跑）。**迁移也需要迁移**——当迁移多到本身成为状态机时，为它建状态表，这是体系自指成熟的标志。

从案例里提炼的方法论：迁移命名时间戳化防撞车；每迁移一件事；性能与功能同流；存量清洗显式化；迁移自身可观测。这套纪律对任何带本地存储的产品都可直接套用。

## 4.7 数据的生命周期与边界

最后补全存储全景的三个外围。其一，**数据目录与多级存储**：全局数据目录由 Global 服务提供（@opencode/util/global），库文件、日志、快照、模型目录缓存分层放置；core/src/kv.ts 提供轻量键值存储（KV 服务），服务于"不需要 SQL 的小状态"（如 websearch 的检索状态、各服务的杂项配置），避免"什么都塞主库"的表膨胀。其二，**保留与清理**：file-retention.ts 管理文件级数据的保留策略（工具输出的大文件、旧附件），配合 blob 侧存储控制库文件无限膨胀；退出会话的 PTY 缓冲也设了保留上限（core/src/pty.ts 的 EXITED_LIMIT = 25，注释明言"避免被遗弃的终端无限累积缓冲"）——保留策略分散在各子系统内、遵循同一模式：定上限、裁旧者、可显式清除。其三，**跨 Location 的归属**：会话表带 workspace 与路径字段（add_session_workspace_id、add_session_path 迁移为证），数据的 Location 归属在存储层就有列级表达，服务层（location-service-map）的按目录查找与之呼应——第二章 Location 模型的存储对偶。

## 4.8 序列号的并发论证：为什么"预留"是对的

4.4 的 reserveSequence 用"插入或取 max"推进聚合的水位，这个看似简单的操作值得一次并发论证。场景：同一聚合的两个写者（比如会话的两个事件几乎同时产生）都要分配下一个序列号。方案 A（读-改-写）：读当前水位 $s$、写 $s+1$——两个写者都读到 $s$，都写 $s+1$，序列号冲突。方案 B（行锁串行化）：对聚合行加锁再分配——正确但引入锁竞争，聚合多了之后锁管理复杂。方案 C（KeyedMutex，Bus 的实际选择）：按聚合键互斥，同键串行、异键并行——正确性与吞吐兼顾。方案 D（数据库原子自增）：依赖 SQLite 的 AUTOINCREMENT——但序列号要按**聚合**分轨（每个会话自己的 1,2,3...），全局自增不满足语义，还得回读。Bus 选择 C 并且让 reserveSequence 在互斥区内执行"插入或 max 推进"——语义是"水位只进不退"：哪怕写者崩溃在写事件之前，预留的号码也已占坑，后续事件不会复用该号（序列号有洞没关系，**重复与倒退才是致命的**，因为订阅者的重放协议依赖"号大即为新"的单调性）。这个论证的结论可以一般化：凡是"按实体分轨的单调号"场景，正确策略都是"互斥区内预留、允许有洞、禁止回退"，日志系统的心跳序号、分布式 ID 的号段模式同属此族。

## 4.9 回放协议：客户端视角的一致性世界

4.4 说了 Bus 支持"带着上次序列号来订阅，先补缺口再续实时"，这里把客户端视角的协议完整写一遍，因为它定义了三端一致性的可验证含义。设客户端最后处理到聚合 $A$ 的序列号 $k$。重连后客户端声明 $(A, k)$；服务端从 EventTable 取 $seq > k$ 的全部事件按序补发，随后把实时流接入；从此客户端收到的每一事件都有连续递增的 seq。一致性世界的三个可验证性质：**无缺口**（任何 $seq \le k$ 的事件不会再出现，$k < seq \le$ 当前的事件全部送达一次）、**无重排**（同聚合内 seq 严格递增送达）、**幂等可重放**（客户端用本地最后 seq 重新连接，行为与首次连接一致）。这三条性质让前端的投影逻辑可以写成纯函数：`project(events) → view`，任何时刻的视图只取决于已见到的事件序列，而与"怎么连上的"无关。TUI 重连、桌面休眠恢复、浏览器刷新在这个协议下都是同一种平凡情形——重新投影而已。值得对比的是"拉取式"设计（客户端定期全量拉会话状态）：实现简单但一致性弱（拉取间隙的变化靠 diff 猜）、带宽差、时延差。事件流加回放的设计在复杂度上略高，换来的是实时性与严格一致——对一个"三端同时看一个会话打字"的产品，这笔账毫无悬念。

## 4.10 迁移编写的规范与禁忌

4.6 从历史迁移里提炼了方法论，这里反向把它写成操作规范（供任何维护 SQLite schema 演化的团队参考）。规范五条：一、**一个迁移只做一件事**（加列、建表、建索引、数据清洗不得混编——回滚与诊断都需要单义）；二、**迁移必须幂等可判定**（执行与否有库内记录，执行体不假设"第一次跑"之外的环境状态）；三、**数据清洗与结构变更分离**（normalize_storage_paths 类的清洗单独成迁移，出问题可单独重跑）；四、**外键与表重建走标准流程**（SQLite 改表结构的稳妥路径是新建-拷贝-改名，期间按 supportsForeignKeyToggle 控制外键开关）；五、**迁移要过测试**（database-migration.test.ts 的存在说明迁移是被测对象）。禁忌三条：禁止在迁移里读应用层逻辑（迁移只能依赖库与世界）；禁止用"先删后建"处理有数据的表（数据丢失不可逆）；禁止依赖迁移之间的隐式执行顺序（依赖只能建立在已发布迁移上，不能建立在同批次未合入的兄弟迁移上——分支合并会打乱顺序）。这套规范在 OpenCode 的 migration/ 目录（几十个时间戳文件）里得到了长期执行，其可行性已被产品史验证。

## 4.12 读路径的投影优化：从行到视图的三段管线

写路径（追加、状态转移）讲完了，读路径同样有架构含量。会话历史的读取不是一条 SQL，而是三段管线。第一段**取行**：按会话 ID 与游标范围取消息行（4.2 的投影索引与排序保证这一段是索引扫描而非全表扫）；第二段**解码**：行里的 JSON 列按 schema 解码（第二章 2.3——存储中的数据过 schema 才可信），大 blob 按 4.2 的行外引用取回；第三段**投影**：按消费方的需要裁剪变形——runner 组装要的是"模型的输入形态"（含检查点替换、工具输出裁剪后的文本），前端投影（session/projector.ts 一类的投影器）要的是"渲染形态"（消息卡片、时间线、状态标记），回放协议（4.9）要的是"事件形态"（seq 排序的增量）。三段管线的架构含义：**一个物理事实，多个合法视图**——视图由消费方定义，事实只有一份。优化也因此有了明确的下手处：第一段建索引（两个 projection 迁移干的事），第二段缓存解码结果（session 层的 store 与历史缓存），第三段各视图自算（视图之间不做相互缓存，避免视图耦合）。性能的总体判断：会话历史是读多写少的追加流，热点在读路径的投影段而非写路径，因此优化投资的优先级是索引与投影缓存——这与 4.6 里两个性能迁移（indexes、order）出现在后期（产品成熟、数据量上来之后）的时间线一致。

## 4.13 数据的可移植性：备份、搬迁与隐私

本地 SQLite 的选择（4.1）给数据可移植性带来一组值得明说的性质。**备份**：单文件加 WAL，停写复制或用 SQLite 的备份接口即可获得一致快照——备份操作不依赖 OpenCode 在线；**搬迁**：数据目录整体拷贝到新机器（第四章 Global 提供的目录布局是搬迁清单），配合机器级的凭据重录（keychain 数据不随文件走，安全设计使然）；**隐私**：会话历史不出本机（除非用户使用云端集成——console-access 的对接是显式行为），用户可以用任何 SQLite 工具直接检查自己的数据——"你的数据你能读懂"是本地优先产品的隐私底气；**清理**：file-retention 的保留策略（13.8）与用户的手动清理共同控制体积，blob 侧的大对象清理有专门路径。可移植性还有一个工程侧面：**版本兼容**——老库在新代码上打开（迁移体系保证）、新库在老代码上打开（会报版本错误而不是静默错读，schema.gen 的初始表与迁移记录让库结构自描述）。综合起来，存储选型的完整账单：SQLite 给了事务性、嵌入式、三运行时、可移植、可直读五个性质，代价是跨机并发（多机器同时写一个库）不支持——而 OpenCode 的单机定位恰好绕开了这个代价。选型论证至此完全闭环：**不是 SQLite 万能，而是需求的五边形恰好能被它覆盖**。

## 4.14 本章小结

本章确立了持久层的四个设计公理并逐一兑现：**选 SQLite 因为嵌入式、事务性、三运行时可移植**（4.1）；**消息内容不可变、状态可变**，为恢复协议提供可信基线（4.2）；**收件箱事件溯源化**，让并发投递与崩溃恢复成为存储形态的自然性质（4.3）；**Bus 先落库再分发**，使任意时刻接入的订阅者看到一致世界（4.4）。迁移体系（4.5-4.6）则展示了 schema 演化的工程纪律。至此，"状态先行落库"这句话有了完整的物理含义。下一章进入全仓库单文件最复杂的模块之一——上下文压缩，它站在本章的存储之上、第一章的资源必然性之下，是 agent 引擎里最典型的"资源管理器"。
