# 第六章 · 工具体系与运行时

## 6.1 工具是什么：一个被严格约束的行为单元

工具（tool）是模型的手：模型不直接操作世界，只能"声明"一次工具调用，由引擎执行后把结果回灌。因此工具的接口设计直接决定 agent 的能力边界与安全边界。OpenCode 对工具的定义包含五个部件：名称（供模型引用）、描述（供模型理解何时用）、输入 schema（供模型构造参数，Standard Schema 规范）、执行体（Effect 函数）、权限元数据（供权限系统断言，第八章）。这五个部件中前四个面向模型，最后一个面向引擎——**同一份工具定义同时是模型协议对象与运行时受控对象**，这个双重身份是整个工具体系的枢纽。

全部工具——内置、插件、MCP 提供——统一注册进 Tool 服务（packages/core/src/tool.ts）。注册时的校验规则透露了设计者的防御深度：名称只允许字母数字下划线连字符（tool.ts:400-401）；名为 execute 的工具被保留给 Code Mode 元工具（tool.ts:403-404，6.4 节解释为什么一个名字值得预留）；输入必须是 Standard Schema 实现（tool.ts:406-409，zod、ArkType 等任何实现该规范的库都可用）。特别值得学的是校验失败的处理方式：**不抛异常**，而是记入 errors 列表并打日志（tool.ts:364-379）。理由是注册发生在服务装配期，来源是各类插件——一个坏插件不能拖垮整个服务实例，其他工具与 Location 必须照常工作。错误被收集、暴露、可查（tool.ts:232-244 的 notify 让注册错误打印出来），但故障被隔离在"那个插件不可用"的粒度上。这是插件架构的第一生存法则：**宿主的可用性优先于插件的成功**。

## 6.2 Snapshot：按权限产出"本轮可用工具集"

每次模型请求前，Tool 服务的 snapshot（tool.ts:251-323）执行一次关键计算：根据当前权限规则（第八章）与 agent 配置，产出**本轮实际暴露给模型的工具定义集合**与统一执行入口 execute。为什么要在请求前过滤，而不是全部暴露、执行时再拦？两个理由。其一是 token 效率：工具定义本身占上下文，暴露模型永远用不了的工具（比如被 plan agent 禁用的编辑工具）是纯浪费。其二是**行为引导**：模型看见什么工具，就会尝试什么方案；把禁用的编辑工具藏起来，模型会自然转向只读方案，而不是"试着编辑然后被拒"——被拒也会消耗一轮往返，且可能诱发模型反复重试。权限的前置过滤因此兼具经济与引导双重意义，这也解释了 plan agent（只读）的设计为什么成立：README 说 plan agent"默认拒绝文件编辑、bash 需批准"，在实现上就是 plan 的规则集进入 snapshot 的过滤计算，而不是工具系统里的特判。

快照的另一个成果是把工具分成两类：**直接工具**（codemode: false，如 bash、edit、read）直接出现在模型可见的工具列表里；**Code Mode 工具**（其余全部）被打包进一个名为 execute 的元工具（CodeModeTool.create，tool.ts:272-278），模型通过写一段 TypeScript 程序来编排对它们的调用。这个双轨制是 OpenCode 工具层最大胆的设计，值得单独一节。

## 6.3 Code Mode：用程序编排工具调用

先算账。模型完成"搜索 + 读三个文件 + 修改一处"的任务，朴素方式是依次发起五次工具调用，每次一个往返：五次模型请求（每次重发全部上下文）、五次工具执行。上下文成本按 1.4 节的二次律累加，时延按往返数累加。Code Mode 的思路是：**把"多次调用"编译成"一段程序"**——模型写一段 TypeScript，程序里连续调用多个工具，引擎在受限解释器里执行整段程序，期间只发生一次模型往返。

packages/codemode 是这个思路的完整实现：codemode.ts 提供 searchSignature 与 toolExpression（签名检索与工具表达式构造——模型需要知道"有哪些工具、签名长什么样"才能写出正确程序）；namespace.ts 把工具组织成命名空间（模型代码里 write() 而不是长名调用）；interpreter/ 是受限的执行器——"受限"是关键词：模型写的程序不能访问网络、不能 import 任意模块、不能死循环（第六章权限与第九章沙箱讨论边界）；stdlib/ 提供程序可用的标准库面；openapi/ 与 scan.ts 负责从工具 schema 生成可调用的接口面；tool-runtime.ts 与 tool-schema.ts 处理"模型代码里的工具调用"到"真实工具执行"的桥接；tool-error.ts 定义程序内可见的错误形态。

Code Mode 的权衡必须诚实呈现。收益：往返数从 $n$ 降到 $1$，token 成本大幅下降（工具定义也只需暴露一个元工具），且程序可以包含本地逻辑（循环、条件、字符串处理）——这些逻辑原本每次都要模型"用 token 想出来"。代价：错误定位变难（程序整体的失败 vs 单次调用的失败，引擎必须把程序内的部分成功部分失败如实回灌）；模型的程序能力成为新瓶颈（写不好程序的模型反受其害）；调试面变大（解释器是新的故障面）。OpenCode 用"双轨"折中：高频、原子、需要精细权限的工具（bash、edit、read）保持直接暴露；编排类、批量类的走 Code Mode，且插件可以调整归类（mcp-codemode-defaults，core/src/plugin/ 下可见 MCP 工具默认进 Code Mode 的配置点）。

## 6.4 执行管线：executeTool 的四个阶段

无论是直接工具还是 Code Mode 内的调用，最终都走 executeTool（tool.ts:131-179）这条管线，四个阶段依次是：

**阶段一：before 钩子**。插件可拦截并改写工具入参（core/src/plugin/hooks.ts 的钩子契约）。典型用途：审计、参数修正（tool-input-repair，core/src/plugin/ 下有专门模块——模型产出的参数偶有格式瑕疵，修复比拒绝更省钱）。

**阶段二：工具体执行**。工具的 Effect 函数运行，内部可能发子进程、写文件、调网络。第八章会讲权限断言发生在这一阶段的入口处。

**阶段三：after 钩子**。插件可改写工具结果。典型用途：结果裁剪、脱敏、注记。

**阶段四：内容规范化**。normalizeImages（tool.ts:92-119）把结果里的 data URL 图片转码、压缩，失败则剔除并附计数提示——工具输出直接进入模型上下文，图片若不规范化，一次结果就能吃掉大量窗口预算（第五章按 1500 token/图折算），或者一个坏 data URL 污染整条消息。规范化的失败处理同样体现"不致命原则"：剔除坏图、告知模型、会话继续。

管线的形状是一个**双向可插拔管道**：模型侧的输入、世界侧的输出，两端各有一个插件可介入的变形区。加上 6.1 的注册隔离与 Code Mode 的编排层，工具体系有三层防御与三层效率结构——防御（注册校验、权限断言、规范化）与效率（Code Mode 编排、输出裁剪、图片压缩）在同一管线上并存。

## 6.5 深读 shell：作业化与崩溃找回

shell 是最危险也最有用的工具，它的实现（core/src/tool/plugin/shell.ts）覆盖了 agent 场景下"跑命令"的全部难题。执行链：ShellParse.scan 先解析命令串，找出其中每一条具体命令与涉及的目录（一条 bash 命令行可能含管道、&&、子 shell，权限断言必须针对**每一条真实执行的命令**而不是整串文本）；access.authorizeExternal 校验涉及目录是否在 Location 之外（出界目录需要额外授权）；然后逐条 permission.assert（shell.ts:114-142）弹授权——用户可批准、拒绝或记住。这条链体现的原则是：**权限的粒度等于真实执行的粒度**，字符串级别的黑名单（比如"禁止 rm"）在 && 与变量展开面前不堪一击，解析到命令级才有意义。

shell 的另一个特色是**作业（Job）化**。长命令（测试套件、构建）不该阻塞会话：前台执行时阻塞等待是默认，但可以把作业转后台（shell.ts:241-253），会话继续干活；后台作业完成后 notifyWhenDone（shell.ts:144-176）自动向会话发一条合成消息唤醒模型继续——"转后台"对模型是透明的，它收到的是一次正常的唤醒而不是特殊的调度事件。崩溃找回：进程崩溃时正在跑的 shell 作业凭 recovery 信息重新关联（shell.ts:226-239）——子进程的存活独立于引擎进程，恢复的关键是记录"哪个作业对应哪个子进程"的映射并持久化。环境注入：shell 工具给子进程加 OPENCODE_SESSION_ID（shell.ts:200-203），使命令行脚本可以感知自己运行在哪个会话里（CI 脚本、hook 脚本据此做会话级日志）。子进程环境还经过 shell/select.ts（ShellSelect）选择合适的 shell 解释器。

## 6.6 深读 edit：字符串编辑的工程化

edit 工具（core/src/tool/plugin/edit.ts）做"精确替换"，看似简单，工程难点密集。难点一：**换行符**。仓库可能混有 CRLF 与 LF 文件，模型给出的 old_text 通常是 LF 视角。edit 的解法是 matchView（edit.ts:168-188）：在文件的 LF 归一化视图上做匹配，命中后把偏移回映射到原始文件——匹配在规范化世界、写入在真实世界，两者经偏移映射桥接。难点二：**近似匹配**。模型抄的原文可能与真实文件有细小出入（行尾空白、排版字符）。edit 提供三级降级：精确匹配失败后尝试排版字符归一化匹配，再失败尝试行级忽略行尾空白匹配。每一级降级都收窄"什么算相同"的严格度，同时保持"绝不模糊到改错位置"的底线——与第五章 deliver 的退让链同构。难点三：**失败的可诊断性**。三级都失败时，missHint（edit.ts:199-241）用"投票法"找出文件里与模型意图最接近的行，告诉模型"你想改的可能是这一行"——把一次失败的编辑变成一次可纠正的反馈，模型下一轮通常能自我修复。难点四：**并发**。同一文件的连续编辑用文件锁互斥（edit.ts:355），防止两个并发工具调用交错写入。写授权与 diff 预览：edit 走 permission: "edit" 动作（edit.ts:321），写授权的请求携带 diff，用户在批准前看到将要发生的改变。此外源码顶部留有 LSP TODO（edit.ts:256-258）：写入提交后发 didChange 并收集诊断——这是未来接缝的活文档（doc_zh/components/04 有专文分析）。

## 6.7 工具家族一览

tool/plugin/ 下的其余工具按功能分组：文件系（read、write、edit、glob、grep、patch、file-diff、read-filesystem、search——检索类走 core/src/tool/search.ts 与 ripgrep 适配，第十三章）、网络系（webfetch 网页抓取、websearch 搜索）、交互系（question 向用户提问、todo 任务清单）、编排系（subagent 子代理、schedule 定时任务、skill 技能调用）、媒体系（image-generate）、集成系（mcp-resource 读取 MCP 资源、artifact 工件）。每个工具都遵循 6.1 的五部件定义与 6.4 的管线，差异只在执行体与权限元数据。这个同构性让"新增一个工具"变成低风险事件：实现五个部件、注册、测试——不需要碰引擎。工具输出的流式形态由 tool-output.ts（core/src/tool-output.ts）承载：长输出的工具（shell、read）边执行边产出，前端实时可见（第十二章的渲染依赖这一点），而上下文注入发生在结算时。

## 6.8 工具声明与权限元数据的结合部

第六章开头说工具定义有五个部件，其中权限元数据与 snapshot 的关系值得单独展开。工具在注册时声明自己的权限特征（需要什么动作类别、资源模式怎么从入参提取——bash 提取命令与目录、edit 提取文件路径），snapshot 计算本轮工具集时同时产出"执行时的断言计划"：哪些动作要 assert、资源模式怎么求值。这个"声明一次、两处消费"的结构（模型侧见定义，引擎侧见断言计划）避免了权限信息与工具定义的漂移——若权限特征写在工具实现代码深处，工具描述与权限行为的同步就只能靠纪律；写进注册声明后，两者由同一份数据驱动。结合第八章的规则求值，一次工具调用的完整权限路径是：注册声明提供动作类别与资源提取器 → snapshot 决定可见性（deny 即隐藏）→ 执行入口 assert 求值（allow/ask/deny 三分支）→ ask 走批准流。四个环节由同一条声明链串起，这是"权限系统作为工具系统的一等维度"而不是外挂检查器的结构证据。

## 6.9 工具描述的提示词工程

工具的 name 与 description 是给模型读的"文档"，它们的措辞质量直接影响调用质量——这是工具体系里最容易被低估的工程面。写好工具描述有几条从实现里可归纳的原则：其一，**描述行为而不是实现**——"读取文件内容，可指定行范围，超长会截断"是行为（模型据此决策），"内部使用 sed"是实现（对模型无用）；其二，**明示边界与失败模式**——"文件不存在会返回错误""二进制文件不适合此工具"让模型避免无效调用；其三，**区分同类工具的使用时机**——grep 与 glob 的描述必须互相指涉（"找内容用 grep，找文件名用 glob"），模型在近义工具间的选择错误是最常见的浪费；其四，**参数 schema 的字段描述同等重要**——模型构造参数时读的是字段级描述。工具描述的修改成本极低（一行字符串）而行为影响极大，因此它的变更值得与代码变更同级的评审与测试（fixture 里对工具描述的回归不是小事）。从系统视角看，工具描述是"模型接口面"的源代码——引擎质量的一半在执行体，另一半在这层提示词工程里。

## 6.10 输出的流式与结算：两个世界的交割

工具输出的时间形态有两段：执行中的**流式段**（shell 边跑边吐输出，前端实时可见，TUI 的工具卡片滚动）与结束时的**结算段**（结果整体定形、回灌上下文、状态落库）。两段的交割有明确的规则：流式段的内容是**瞬态视图**（不进上下文、不参与决策、可以被折叠截断），结算段的内容才是**事实**（进历史、进模型、可恢复）。交割点的意义在于把"展示的实时性"与"决策的正确性"解耦：前端可以展示 10k 行滚动输出而不污染上下文（结算时按规则裁剪——第六章管线的规范化与第五章的预算治理只作用于结算段）。第五章 compaction 的 flatten 降级（"裁工具输出→去工具输出"）作用的正是历史里的结算段事实。core/src/tool-output.ts 承载流式段的通道管理（tool-output.ts 的流式输出设施），而结算的写入与状态转移服从第三章的落库公理。理解两段式，就理解了为什么"屏幕上看到的"与"模型看到的"可以合法地不同——前者是面向人的流式视图，后者是面向决策的结算事实。

## 6.12 工具家族的能力光谱：危险度与治理强度的对应

把第六章出现的工具按"能力危险度"与"治理强度"排成一张光谱表，可以看出权限设计的一致性（治理强度对应第八章的动作类别与默认效果）：

| 危险度 | 工具 | 副作用形态 | 典型治理 |
| --- | --- | --- | --- |
| 高 | shell | 任意进程、任意文件 | 命令级解析授权、目录出界校验、ask 默认 |
| 高 | edit / write / patch | 工作区内容变更 | diff 预览授权、文件锁、执行前快照 |
| 中 | webfetch / websearch | 网络外发与外部内容引入 | 独立动作类别、注入风险提示 |
| 中 | subagent | 派生执行（继承并收窄权限） | 子会话隔离、权限单调收窄 |
| 低 | read / glob / grep | 只读 | 通常 allow，路径可见 |
| 低 | todo / question | 会话内元数据或人机交互 | 无需断言或轻量确认 |
| 特殊 | skill / schedule / mcp-resource | 能力委托 | 按被委托内容的危险度定级 |

光谱表的构造规则是**治理强度随不可逆性上升**：只读操作可逆（错了再读一次），文本修改半可逆（快照可回滚），进程与网络操作弱可逆（影响外部世界），因此治理依次加强。表里还有一个"特殊"档值得解释：skill 与 schedule 这类"能力委托"工具的危险度取决于被委托的内容而非工具本身——skill 执行的是项目定义的流程（内容来自 AGENTS.md 体系，第九章），schedule 触发的是未来的会话，它们的治理按委托内容动态定级，这是"工具危险度是函数不是常量"的例子。光谱表的反向用途是审计：新工具接入时先定位危险度档位，治理配置跟着档位走——定位错了档（把网络工具配成只读档）是权限事故的常见起点。

## 6.13 工具失败的三种形态与反馈回路设计

工具失败不是单一事件，OpenCode 区分三种形态并分别设计反馈回路。**形态一：确定失败**（文件不存在、命令返回非零）——失败信息作为工具结果回灌，模型据此调整下一步；反馈回路要求失败消息**可行动**（报错内容里含"哪个文件没找到"而不是裸的 exit code，shell 工具把 stderr 尾部带回——与 MCP stdio 的 EXIT_WAIT 收集遗言是同一思想）。**形态二：部分成功**（批量操作部分完成、编辑命中但替换异常）——结果里明确标注已完成与未完成的边界，模型可以只补救未完成部分而不是全部重做；Code Mode 场景尤其重要（6.3 的错误定位难题），tool-error 的结构化错误（tool-error.ts）把部分成功表达为程序内可捕获的值。**形态三：不确定状态**（超时但进程可能还在跑、网络中断结果未知）——反馈回路升级为"状态存疑"语义：工具结果标注不确定，引擎保留后续查证手段（job 查状态、shell 转后台后 notifyWhenDone 补报结果，第六章 6.5）。三种形态的划分标准是**引擎对世界状态的知悉程度**：知悉（确定失败）、半知悉（部分成功）、不知悉（不确定状态），反馈回路的精度与知悉程度匹配。这条设计的深层原则：**模型是靠反馈学习的决策者，反馈的信息量决定下一轮决策的质量**——工具系统的"报错文化"因此与库设计的"异常文化"不同：前者追求信息丰富可行动，后者追求类型精确可捕获。

## 6.15 工具与子代理的边界：能力委托的两种形态

第六章多次出现 subagent 工具（subagent.ts），这里把"工具执行"与"子代理派生"的边界讲清楚，因为它是工具体系里最容易混淆的一对概念。普通工具是**函数式委托**：调用、执行、返回结果，执行在引擎的 fiber 里，结果就是一段内容。子代理是**会话式委托**：subagent 调用打开一个完整的子会话（有自己的收件箱、历史、压缩、权限上下文），子代理在里面跑自己的完整循环，跑完把总结作为工具结果返回。两者的分界判据是**是否需要独立循环**：单次操作（读文件、跑命令、改代码）用工具；需要"探索-决策-再探索"的多步自主过程（复杂检索、大范围调研）用子代理。会话式委托的工程含义链很长：子会话是持久实体（崩溃恢复时带回子会话 ID，3.8）、有自己的上下文预算（压缩独立进行，5.7 的"子代理即预压缩"）、有自己的权限收窄（8.14 的单调收窄定理）、有自己的事件流（前端可以观察子代理进度，12 章的渲染面）。general 子代理（README 提到的 @general）是引擎内置的通用型子代理，用户与插件也可以定义专用子代理（agent 配置体系，9.7）。一句话总结：**工具是模型的手，子代理是模型的分身**——手做单件事，分身做一件事的完整过程。

## 6.17 新增工具的检查单：从想法到注册表

给"想给 OpenCode 加一个工具"的读者一份落地检查单，每一条都对应前文的机制（也适用于给任何 agent 系统加工具）。**第一步：定位档位**——按 6.12 的能力光谱判定危险度，治理配置跟档位走；**第二步：写五个部件**——名称（字符集约束，6.1）、描述（6.9 的提示词工程原则）、输入 schema（Standard Schema 实现）、执行体（Effect 函数，执行期间的子进程走 Environment）、权限元数据（动作类别与资源提取器，6.8）；**第三步：设计失败反馈**——按 6.13 的三形态决定报错的信息量，失败消息必须可行动；**第四步：决定归类**——直接暴露还是进 Code Mode（6.3 的判据：编排价值与权限精细度的权衡）；**第五步：处理输出预算**——长输出设计裁剪与折叠语义（6.10 的两段式），多媒体走规范化管线（6.4 的 normalizeImages）；**第六步：注册与隔离验证**——故意注入坏定义验证 errors 隔离（6.1），确认坏工具不影响其他工具；**第七步：测试**——工具级测试加 kernel 级集成（14.2 的 simulation 环境），权限断言路径必须有覆盖；**第八步：文档与描述评审**——描述文本与第六章的原则互查，工具描述的变更与代码变更同评审。检查单的本质是把"加工具"从即兴行为变成受控流程——工具是模型的行为面，每加一个都在扩大 agent 的能力与风险面，流程的意义正是让扩大过程可预期、可回退。

## 6.18 本章小结

工具体系的三条主线：**定义即契约**（五部件、Standard Schema、注册隔离）；**执行即管线**（钩子、断言、规范化，双向可插拔）；**编排即编程**（Code Mode 把多次调用折叠为一次往返，受限解释器保证安全）。shell 与 edit 两个深读展示了"最常用工具"的工程密度：权限解析到命令级、编辑匹配三级降级、失败给可纠正的提示。贯穿的原则仍是那条熟悉的旋律：乐观优先、失败退让、故障隔离、状态可恢复。下一章转到循环的另一端：模型——模型是谁、怎么接入、流怎么解析、错误怎么分类，全部在 packages/ai 的自研协议层里。
