# 第一章 · AI 编码 Agent 的本质与 Agent 循环

## 1.1 三代范式：从补全到代理

要理解 OpenCode 这样的产品为什么长成今天这个样子，必须先看清 AI 辅助编程走过的三代范式，因为每一代范式的技术瓶颈不同，产品的结构重心也就完全不同。

第一代是**补全范式**。以代码补全为代表，模型看到光标前的一段上下文，预测接下来的一小段代码。它的技术本质是单次前向推理：输入是前缀，输出是续写，二者都落在同一个文件甚至同一行内。这一代的全部工程难题都集中在"延迟"上——补全必须在一两百毫秒内出现才有意义，于是行业把精力花在小模型、推测解码和缓存上。补全范式的产品结构极薄：模型被嵌进编辑器的一个文本槽位，不产生任何持久状态。

第二代是**对话范式**。以各种"聊天侧栏"为代表，用户描述需求，模型给出一段代码或一个修改建议，由人来粘贴、审阅、落地。它的技术本质仍然是单轮或少量多轮的文本生成，只是输入从"光标前缀"变成了"自然语言加可选文件"。这一代的核心瓶颈变成了**上下文组装**：把哪些文件、哪些符号放进提示词，直接决定答案质量。于是出现了一整层"检索与引用"的工程，但执行仍然握在人手里——模型说什么，人做什么。

第三代是**代理范式**，也就是 agent。它的定义性变化只有一个：**执行的闭环交给了模型**。模型不再输出"建议"，而是输出"动作"，动作通过工具作用在真实工程上，动作的结果又被回灌给模型，模型据此决定下一个动作，如此往复直到目标达成或被叫停。这个变化看似只是把"人粘贴"换成"程序粘贴"，实则引发了一场工程革命：一旦模型可以亲手执行，系统就必须回答一连串从未如此尖锐的问题——动作出错怎么办？动作越权怎么办？执行到一半崩溃怎么办？上下文被动作的输出撑爆怎么办？谁来看着它执行？这些问题没有一个能在"提示词"层面解决，它们逼出了一整套围绕循环的**执行基础设施**：权限系统、状态持久化、崩溃恢复、上下文管理、并发调度。OpenCode 的全部源码，本质上就是这一套基础设施的实现。

三代范式可以放进一张表里对比：

| 维度 | 补全范式 | 对话范式 | 代理范式 |
| --- | --- | --- | --- |
| 技术本质 | 单次前向推理 | 带检索的多轮生成 | 工具闭环的循环决策 |
| 执行者 | 人（接受/拒绝） | 人（复制/粘贴） | 模型（经工具执行） |
| 核心瓶颈 | 延迟 | 上下文组装 | 安全执行与状态管理 |
| 持久状态 | 几乎没有 | 会话文本 | 会话、消息、工具痕迹、快照 |
| 失败代价 | 忽略即可 | 浪费一轮对话 | 可能破坏工作区 |
| 产品重心 | 编辑器槽位 | 提示词与检索 | 执行环境与治理 |

## 1.2 Agent 的形式化定义

抛开产品外衣，一个 AI 编码 agent 可以形式化为一个五元组构造。设模型为 $M$，工具集为 $T = \{t_1, t_2, \dots, t_n\}$，每个工具 $t_i$ 是一个从输入到可观察输出的确定性或半确定性函数；设环境为 $E$，即工具所作用的真实世界（文件系统、shell、版本库）；设初始状态为 $s_0$（用户消息与项目上下文）。agent 的执行是一个序列：

$$s_{k+1} = E\big(t_{i_k}\big(M(s_k)\big)\big), \quad k = 0, 1, 2, \dots$$

读法是：模型观察当前状态 $s_k$，产出一次工具调用 $t_{i_k}$ 及其参数；环境执行该调用得到新状态 $s_{k+1}$；新状态连同工具结果回灌进模型，成为下一轮观察。这个式子把三个角色分得非常清楚：**模型只负责决策，工具只负责执行，循环只负责把两者缝合**。三者职责的分离，正是 OpenCode 架构分层的源头——第七章的模型接入层只做第一件事，第六章的工具体系只做第二件事，第三章的会话引擎只做第三件事。

这个形式化立刻给出三个值得推导的性质。

**第一是收敛性**。循环没有天然的终止保证：模型可以永远继续调用工具。工程上必须人为加入终止条件，通常有三类：模型显式输出"完成"信号（不再调用工具）、步数上限（OpenCode 的 runner 有步数上限逻辑，见 packages/core/src/session/runner/max-steps.ts 与 llm.ts 中 252 行附近的步间检查）、用户中断（终端里按 Esc）。三类条件在实现上对应三种不同的循环出口，主循环的返回值是可辨识联合 DrainResult（packages/core/src/session/runner/index.ts），正是"循环必然以一种可区分的方式结束"这一类型化表达。

**第二是单调的信息增长**。$s_k$ 中每多一个工具调用，历史就多一条记录，上下文长度只增不减（除非主动删改）。设每步平均注入 $b$ 个 token，$n$ 步后上下文占用约为 $\sum b_k$，而模型窗口 $W$ 是常数，于是必然存在某个步数 $n^*$ 使上下文逼近 $W$。这不是"可能发生"的意外，而是**数学上必然的资源耗尽**，因此上下文管理不是可选的优化，而是 agent 引擎的必备器官——第五章的压缩机制就是为这个必然性准备的。

**第三是环境不可预知**。$E$ 是真实世界：文件可能被并发修改，命令可能挂起，网络可能失败。这决定了 agent 引擎对每一次工具执行都必须有超时、中断、错误分类与恢复策略，也决定了"可恢复"必须下沉到持久化层（第四章）。概言之，循环的三条数学性质——无内建终止、单调增长、环境不可预知——分别对应了步数上限、上下文压缩、崩溃恢复三大机制。**OpenCode 的每个子系统都能在这三条性质上找到存在理由**，这是贯穿全书的主推导线。

## 1.3 Agent 循环的控制流结构

把 1.2 的形式化展开成控制流，一个标准的 agent loop 是这样的：

```
            ┌──────────────────────────────────────────┐
            │                                          ▼
 ┌─────┐    │   ┌────────┐   ┌────────┐   ┌────────┐
 │用户 │───►│   │ 组装   │──►│ 模型   │──►│ 工具   │
 │输入 │    │   │ 上下文 │   │ 流式   │   │ 执行   │
 └─────┘    │   └────────┘   └───┬────┘   └───┬────┘
            │                    │            │ 结果
            │              有工具调用？        │ 回灌
            │                │        │        │
            │              是│        │否      │
            └────────────────┘        ▼        │
                                 ┌────────┐    │
                                 │ 结束   │    │
                                 └────────┘    │
            ◄─────────────（继续下一步）─────────┘
```

图中有三个容易被低估的细节。其一，"组装上下文"不是简单拼接，而是一次资源决策：放多少历史、放哪些指令、要不要换入压缩检查点，每一项都消耗窗口预算。其二，"模型流式"是流而非块：token 逐个到达，工具调用的参数本身也是流式拼出来的，引擎必须在流中实时识别"一次工具调用开始/结束"，并把已结束的调用尽早派发——OpenCode 的 SessionStep.attempt 就在消费事件流的过程中为每个本地工具 fork 独立 fiber 并发执行（packages/core/src/session/runner/step.ts），互不阻塞且保序发布。其三，"结果回灌"不仅包括工具的文本输出，还包括结构化痕迹（调用 id、耗时、元数据），因为下一轮模型需要区分"这是我说过的话"与"这是世界给我的反馈"。

循环还有一个常被忽视的属性：**它是分层的**。主 agent 的循环中可以发起子代理（subagent）调用——子代理有自己的会话与循环，跑完后把总结回给主循环。这在控制流上是一棵递归树：主循环的一个"工具调用"节点，展开后就是一整棵子循环。OpenCode 的 general 子代理即以 subagent 工具形态被调用，崩溃恢复时还会带上其子会话 ID（packages/core/src/session/runner/llm.ts 中对遗留工具调用的结算逻辑），用持久化的父子关系保证递归树在崩溃后仍可重建。

## 1.4 Token 经济学：为什么循环的每一步都要精打细算

agent 的运行成本可以用一个粗模型刻画。设一次会话执行 $n$ 步，第 $k$ 步发送的上下文为 $c_k$ 个输入 token，输出为 $o_k$ 个 token，单价为 $p_{in}$ 与 $p_{out}$，则总成本为：

$$C = \sum_{k=1}^{n} \big( c_k \cdot p_{in} + o_k \cdot p_{out} \big)$$

关键在于 $c_k$ 的结构：每一轮都要重发**全部历史**（自回归模型的条件就是完整前缀），而历史里累积了前 $k-1$ 步的所有工具输出。若工具输出平均 $b$ 个 token，则 $c_k$ 近似为 $k \cdot b$ 量级，成本随步数呈**二次增长**：

$$C \approx \sum_{k=1}^{n} k \cdot b \cdot p_{in} = \frac{n(n+1)}{2} \cdot b \cdot p_{in}$$

这个二次律解释了 agent 工程里几乎所有的"抠 token"设计。压缩机制把 $\sum b$ 的增长截断（第五章）；Code Mode 把"多次工具往返"折叠成"一次代码执行"，相当于减小 $n$（第六章）；工具输出的裁剪与规范化（图片转码、超长截断）直接压低 $b$（第六章的工具输出管线）；而 prompt 缓存利用了 $c_k$ 的前缀重叠性质——相邻两步的上下文高度重合，缓存命中的部分按极低单价计费，这正是 OpenCode 压缩模块宁可"趁缓存还热提前在后台算好摘要"（compaction 的 precompute 机制）的原因：缓存的折扣常常大于提前计算的成本。这不是玄学，而是把二次律、缓存折扣率与窗口余量放进同一个不等式后得出的工程决策，第五章将把这笔账算清楚。

## 1.5 为什么是终端：执行环境的"全景性"

AI 编码 agent 为什么首选终端作为主场？直觉答案是"程序员爱用终端"，但这只是表层。深层原因是**终端是开发环境里唯一的全景接口**：文件系统、shell、git、进程、网络，这五类 agent 需要的操作在终端里都有统一且原子性的入口，而 GUI 里它们散落在彼此隔绝的面板中。形式化一点说，agent 需要的执行环境是一个**小而完备的指令集**，终端恰好提供了这个指令集的最小实现——一个 shell 就能组合出其余一切。

终端的第二个优势是**可观测性的对等性**：模型看到的（工具输出文本）与人看到的核心信息（命令输出）是同构的，不需要在"GUI 视图"与"文本视图"之间做有损翻译。第三个优势是**组合性**：终端天然是脚本化的，因此 agent 产品自身可以被脚本调用、被 CI 调用、被别的 agent 调用——OpenCode 提供 serve 形态与 SDK 形态（packages/sdk），使同一个内核既被人驱动也被机器驱动，第十一章将展开这一点。

当然终端也有代价：交互带宽窄、富内容（图片、长 diff）呈现困难。OpenCode 的应对是双轨的：TUI 内部用组件化渲染把富内容装进终端（第十二章），桌面与 Web 形态则共享同一 server 而获得完整富 UI（README 中列出的三平台下载、packages/desktop 的 Electron 应用）。**形态多样，内核唯一**，这是理解整个仓库布局的第一把钥匙。

## 1.6 OpenCode 对循环的实现：一个真实样本

第一章的理论要在真实代码里落地才算数。OpenCode 的循环实体是 SessionRunner 服务（Context 标识 "@opencode/SessionRunner"，packages/core/src/session/runner/index.ts:44），其主入口 drain 的签名位于 index.ts:31-42，实现集中在 llm.ts:64-221。用 1.2 的语言对照：drain 就是那个 $k \to k+1$ 的迭代器；"用户输入"不直接打断循环，而是投进收件箱（inbox），由主循环在步间消费——这保证循环永远在**良定义的切点**转移状态，是并发正确性的根基；runStep 完成一次"组装 + 模型流 + 工具执行"（对应图中虚线框），其内部的 SessionStep.attempt（step.ts:71-295）逐事件消费 provider 的 LLMEvent 流，为每个本地工具 fork fiber 并发执行，并把收尾结算放进 uninterruptibleMask 保证"即使用户中断，已发生的事实也一定落库"；每步结束写出 DrainResult 可辨识联合（Complete/Moved/Reloaded），六种步内结局（Completed/Retry/Continue/RecoverFull/Compacted/OutputLimit，step.ts:30-41）覆盖正常完成、整体重试、断流续写、传输层重试、溢出压缩、输出上限续写。

把 1.2 的三条数学性质对应到这套实现上：无内建终止 → max-steps 步数上限与 DrainResult 的显式出口；单调增长 → 压缩检查点换入（Compacted 结局与第五章）；环境不可预知 → 两层重试（第七章）、陈旧结算崩溃恢复（第三章）、权限断言（第八章）。**理论模型与代码结构一一咬合**——这正是"原理性介绍"想传达的读码方式：先有模型，再找结构，最后验证咬合。

## 1.7 循环的变体：从朴素循环到工程化循环

1.3 节给出的是朴素循环，工程产品必须在它之上叠加变体。第一个变体是**探索与实施分离**（plan-then-execute）。朴素循环让模型边想边做，代价是探索期的试错直接写进工作区——读错方向就改错文件。OpenCode 的 plan agent（README 明示：只读、默认拒绝文件编辑、bash 需批准）把这个变体制度化了：先用只读模式探索与制定方案，方案确认后切回 build 模式实施。控制论地看，这是把"认知阶段"与"行动阶段"解耦，认知阶段的错误不产生不可逆后果。第二个变体是**边干边变向**（steering）。1.3 图里的循环是单向推进的，而收件箱的 steer 投递（第三章）允许在循环运行中注入新的意图信号——这相当于给闭环控制器加了"运行中改设定值"的能力，而不需要先停下来。第三个变体是**并行世界**（multi-agent + worktree）。多个子代理各自开循环，各自的写操作落在不同 worktree（第十三章）里物理隔离，最后择优合并。三个变体共享一个思想：**朴素循环是单线程的确定性推进，工程化循环把"何时分叉、何时合流、何时改向"变成一等控制项**。OpenCode 的收件箱、agent 体系与 worktree 设施分别承载了这三个变体。

## 1.8 中断的人因学：Esc 的语义分级

循环面对的不只三种终止条件，还有第三方的"人"。用户按 Esc 打断模型，意图可能是：这话说错了想重说（中断当前流）、方向不对想改向（中断并接管）、不想跑了（取消任务）、只是嫌它啰嗦（打断生成）。四种意图共享同一个物理按键，引擎必须把它们归约为有限的、安全的语义。OpenCode 的归约方式值得注意：中断总是**安全的**——收尾结算进 uninterruptibleMask（第三章），已完成的工具调用落库、未完成的标记中断；输入不丢失——新话进收件箱，可以在下一步生效；子代理的成果不丢弃——恢复协议带上子会话 ID。也就是说，中断被设计成"可恢复的暂停"而不是"有损的终止"。这个设计的深层判断是：**打断 agent 的人通常不想丢掉已完成的工作**，因此中断的默认语义应该保留成果、保留上下文、保留时间线，只切断"继续执行"这一个动作。对比传统进程的 SIGINT（默认杀死进程、状态尽失），agent 的中断语义更接近协程的挂起——这是产品形态对交互语义的反向塑造。

## 1.9 常见误区与反模式

围绕 agent 循环有一组反复出现的误解，逐一澄清有助于建立正确直觉。误区一：**把 agent 当聊天窗口**。聊天范式的会话是无状态的（每轮独立），agent 会话是有状态的（历史、快照、收件箱都是持久实体）——在 agent 里"重新问一遍"不等于"新会话"，历史仍在上下文里发挥作用。误区二：**信任无界**。看到模型前三步都做对了，就放任它执行破坏性命令——错误不随正确率衰减，第 100 步仍然需要第 1 步那样的权限断言（第八章的规则集不分步骤、不因历史表现放松）。误区三：**上下文当无限**。在超长会话里期望模型"记得三小时前那个细节"——压缩检查点替换了旧历史（第五章），细节可能已被摘要；需要持久记忆的信息应该显式写入文件或 todo（工具体系的 todo 工具），而不是指望上下文。误区四：**把工具描述当 API 文档**。工具的 description 是提示词工程的产物，它的措辞直接影响模型的使用质量——修改一行描述的行为效果可能超过修改代码。误区五：**重试无界**。对失败的工具调用无限重试，二次律的成本会指数化——OpenCode 的两层重试都有次数与预算上限（第七章），这是必修的护栏而非可选的优化。这五个误区的共同根源是把循环里的某个环节（历史、权限、上下文、描述、重试）当成了免费的或无限的——而循环的工程学恰恰建立在对每个环节做有限性核算之上。

## 1.11 开放问题：循环的能力极限在哪里

工程叙述之外，agent 循环还有一组诚实的开放问题，它们标记了当前架构的能力边界。**问题一：终止性判断的语义化**。步数上限是语法层面的终止（数到就停），但"任务实际上做完了没有"是语义判断——模型自认为完成而实际遗留缺陷的情形（测试没跑、边界没处理）目前主要靠提示词约束与用户验收，引擎层尚无通用解。**问题二：长程一致性**。跨几百步的任务里，模型对最初目标的理解会漂移——压缩检查点保存了摘要但摘要也是模型的转述。检查点机制（第五章）是缓解而非根治；真正的解可能需要"目标的外部锚定"（把目标写成工件并周期性重读），OpenCode 的 todo 工具是这个方向的雏形。**问题三：错误归因**。一步失败时，原因可能在请求组装、模型决策、工具执行、环境干扰四个环节中的任何一个——错误分类（第七章）区分了传输类错误，但"模型决策错误"与"环境干扰"的区分仍依赖模型的自我修正能力。**问题四：评估**。循环的行为空间是开放组合的（工具序列近乎无限），固定的回归用例覆盖不了行为回归——第十四章的 simulation 与录制回放是工程手段，agent 行为的系统化评估仍是行业级难题。列出这些问题不是唱衰，而是给读者一张"已知地图的边界"：读 OpenCode 源码时遇到的每个看似粗糙的设计（步数上限、两次阈值、人工批准），几乎都是某个开放问题在工程上的务实妥协——**架构是开放问题的临时答案集**。

## 1.13 把循环放进更大的系统：agent 与其运行环境的契约

最后从系统论的视角补一个观察：agent 循环从来不是孤立的，它与运行环境之间有一份**隐式契约**，这份契约的条款散布在全书的机制里，值得收拢一次。条款一：**环境是可观察的**——循环依赖工具结果回灌，因此环境必须能被模型"读到"（read/grep/glob 的检索面、ripgrep 的适配、fff 的全文索引，第十三章 13.14 的四条检索路径就是这条条款的实现清单）；条款二：**环境是可修改的**——edit/write/shell 提供写通道，且修改必须可追溯（快照与 patch，13.3/13.4）；条款三：**环境有部分不变性**——权限系统（第八章）保证某些状态不被 agent 触碰，这是"可修改"的边界条款；条款四：**环境有恢复点**——崩溃恢复与回滚（第三、十三章）保证循环的中断不毁坏环境的可用性。四条条款合起来定义了"agent 能安全地在一个环境里循环"的充要条件，任何一条缺失，循环要么瞎（不可观察）、要么瘫（不可修改）、要么狂（无边界）、要么脆弱（无恢复）。用这份契约去审视任何 agent 系统的设计（包括读者自己的项目）都能立刻发现短板：缺检索的循环靠模型记忆硬撑，缺权限的循环靠信任硬撑，缺快照的循环靠运气硬撑。OpenCode 的十四个机制章，本质上就是这份契约的逐条兑现——第一章把它立起来，是为了让后面的每一章都有一个可回指的"为什么"。

## 1.14 本章小结与延伸

本章建立了全书的公理层：agent 是"模型决策、工具执行、循环缝合"的三方构造；循环的三条数学性质（无内建终止、信息单调增长、环境不可预知）分别倒逼出步数上限、上下文压缩、崩溃恢复三大机制；token 经济学的二次律解释了所有抠 token 设计的共同动机；终端的"全景接口"属性解释了产品形态选择。下一章把镜头拉远，看这些机制被安放进怎样的分层骨架里——为什么业务内核要与传输、前端彻底分离，Effect 与 Location 又是如何把"多形态共享同一内核"从口号变成类型系统保证的。

一个留给读者的练习：打开 packages/core/src/session/runner/step.ts，找出六种 Outcome 各自对应的真实触发条件，并对照 1.2 节判断每一种属于"三条性质"中的哪一条的应对。做完这个练习，第三章的很多设计会变得显而易见。
