# 第十八章 · 全流程实战走读

## 18.1 场景走读的方法论

前十七章按机制解剖系统，本章换最后一个视角：**时间线**。选取八个典型场景，把相关机制按真实发生的顺序串成完整走读——每个机制在场景里"何时出现、为何出现、与谁协作"。走读的价值在于验证机制的编排是否自洽：单独看每一章都成立的设计，串起来跑一遍才见真正的架构品质。场景的选取覆盖产品的主要使用面：上手（场景一）、日常工作（场景二）、故障（场景三）、并行（场景四）、自动化（场景五）、扩展（场景六）、长任务（场景七）、贡献（场景八）。走读中的机制引用全部来自前文的已验证事实，场景叙事属于合理还原（标注：叙事细节为作者根据机制的合理推演，非官方演示）。

## 18.2 场景一：新项目上手的一天

用户在终端进入一个陌生仓库，第一次运行 OpenCode。启动链路：CLI 装配（packages/cli）→ server 启动（createRoutes 或内嵌形态，11.3）→ Location 创建（工作目录实例对应一棵服务子树，2.5）→ 数据库打开与迁移检查（4.5 的迁移清单与 v1-migration）→ 配置发现与归一化（9.2——全局配置与项目配置合流）→ MCP 连接池后台初始化（10.3，不阻塞首屏，15.6）→ TUI 首屏（12.13 的渐进加载）。用户输入第一条问题，此时指令门控在工作：instruction-discovery 扫描仓库找 AGENTS.md（9.9），若仓库还没有 AGENTS.md，用户执行 /init——agent 扫描仓库生成项目说明书（rules.mdx 的 Initialize 行为）。第一次模型调用前的装配：模型解析（7.2 的 model-resolver）从配置与目录元数据确定模型与凭据（Credential 的 get，7.7），请求组装按四级预算（5.12）锁定系统提示、指令、历史（空）、输入。整个上手的体验要点：**"环境就绪"的全部复杂性（迁移、配置、指令、连接池）都发生在用户看不见的启动链路里**，用户面对的只有"开始说话"——这是第二章分层架构在体验侧的兑现。

## 18.3 场景二：一次 bug 修复的完整生命周期

用户描述一个 bug："登录接口在并发下偶发 500，帮我修"。走读全程。**探索期**：用户切到 plan agent（Tab 键，8.6 的只读端点），子代理或主循环检索——glob 找路由文件、grep 搜登录关键词、fff 兜模糊检索（13.14 的四路径协作），读代码（read 工具），全程无写权限（规则集 deny，权限零打扰）。**方案期**：plan 输出修复方案，用户切回 build agent。**实施期**：edit 工具动手——写授权弹 diff 预览（8.7），批准后 LF 视图匹配（6.6 的 matchView）；若模型给出的原文有出入，三级降级匹配接力（精确→排版归一化→行级忽略空白），仍失败则 missHint 投票提示（6.6）。每次写操作前快照静默捕获（13.3），patch 事件经 Bus 广播（13.4），TUI 的 patch-diff 渲染变更。**验证期**：模型跑测试——shell 工具的命令级解析授权（6.5），npm test 命令族被批准并记住（8.4 的 always 沉淀 PermissionSaved 规则）；测试输出折叠渲染（12.9），失败栈进上下文。**循环管理**：任务做到第十步，上下文逼近水位——压缩在步间触发（5.2 的 due），预计算已提前备好检查点（5.3 的套利），历史换入，会话继续，用户只看到"历史已折叠"的分界。**收尾期**：模型输出修复总结，步骤完成（Completed 出口，3.5），用户审查 diff 并提交。一次普通的修复，串联了 plan/build 权限分级、检索四路径、edit 三级降级、diff 预览、命令授权学习、快照、patch 事件、压缩预计算——**没有一个机制是主角，但每个机制都在岗位上**，这正是架构成熟度的标志。

## 18.4 场景三：进程崩溃与恢复的全景

走到一半，机器断电（或用户升级重启）。走读恢复全程。崩溃瞬间：内存态丢失，但一切重要状态已在库里——消息追加式落库（4.2）、收件箱事实落库（4.3）、事件带序列号落库（4.4）、压缩的 running 状态落库、工具调用的 streaming/running 状态落库（4.2 的状态字段）、PTY 子进程独立存活（13.6 的 persistent-pty）。重启后：用户打开同一个会话，drain 启动前先做两次陈旧结算（3.8）——settleStaleCompactions 把遗留压缩改判 interrupted、settleStaleToolCalls 把遗留工具调用改判中断（子代理调用带上子会话 ID，成果不丢）。用户视角的恢复体验：会话历史完整呈现（回放协议补历史，4.9 的无缺口性质），收件箱里未消费的输入还在等待（4.3 的事件溯源），Continuation 记录着执行位置（3.8），用户按一下继续，循环从断点附近重新出发；转后台的测试作业如果还在跑，notifyWhenDone 会在完成时唤醒会话（6.5 加 13.6 的票据寻回）。恢复走读的核心观察：**"可恢复"不是一个功能，是一组存储纪律的总和**——第四章的每一条公理（内容不可变、状态先行落库、事件溯源、序列号单调）在崩溃后各自兑现了一角。用户在这次断电中可能损失的只有"崩溃前最后一秒的流式输出"（未落库的瞬态），其余全部无损——这就是 3.8 说的"把意外变成可结算的历史"的实景。

## 18.5 场景四：多会话并行的工作日

重度用户同时推进三个任务：主仓库修 bug、worktree 里做实验性重构、第三个目录做代码调研。走读并行全程。物理隔离：worktree 服务创建第二棵工作树（13.5 的 Slug 目录名），每个工作目录是独立的 Location（2.5）——各自的会话组、配置视图、权限状态、MCP 连接（池按 Location 分轨）。界面组织：TUI 的多会话标签（12.12——session-tabs，每个标签一个独立投影），三个会话各自 drain 互不干扰（3.14 的会话级互斥）。注意力分配：用户在主仓库标签工作，实验会话在后台跑长任务——后台会话完成或弹出权限请求时，attention 系统提醒（12.8 的铃声），用户切过去处理；不相关的事件不制造噪音（12.12 的"数据全量更新、渲染按需降级、注意力事件驱动"）。子代理协作：调研会话派出 general 子代理做地毯式检索（6.15 的会话式委托），主循环不被海量中间输出污染（5.7 的预压缩效应），子代理的总结回到主上下文。并行走读的架构观察：**并行的安全边界全部是结构性的**——Location 树隔离状态（2.5）、worktree 隔离文件（13.5）、会话收件箱隔离输入（3.2）、权限单调收窄隔离代理（8.14）——没有一个隔离靠"小心编程"，全部靠结构的不可绕过性。

## 18.6 场景五：CI 里的无人值守

团队把 OpenCode 接进 GitHub 仓库：issue 评论 /oc fix 触发修复。走读自动化全程（机制参考 doc_zh/components/07 与 11、14 章）。**触发**：GitHub Actions 的评论事件命中触发词（大小写不敏感、可配置 mentions），composite action 在用户的 runner 里启动 OpenCode。**身份**：OIDC 令牌向平台换取短时 GitHub App installation token（07 组件文档的安全模型——不存长期 PAT），模型凭据来自 secrets 注入（Credential 的环境形态）。**执行**：headless 形态的会话（SDK 或 serve 驱动，11.10 的远端连接），agent 权限取托管与配置的交集——无人值守意味着 ask 不可用，权限配置必须显式 allow（或 fail-closed 拒绝，8.2 的公理让无人值守天然保守）。**执行环境**：runner 的 checkout（fetch-depth: 1、persist-credentials: false 的最小凭据面），任务在隔离工作区进行，快照机制照常工作（13.3）。**产出**：修复完成，agent 开分支、push、创建 PR、回评论链接——产物以 PR 为界面回到人类审查流程。**审计**：全部事件落库（headless 也有完整时间线），PR 的 diff 就是 vcs/patch 协议的产出（13.4）。CI 走读的观察：**无人值守是人类在环的极限情形**——权限系统在 ask 不可用时退到纯规则判定（第八章的公理保证它不会变宽松），事件与快照让"看不见的过程"依然可审计——自动化场景对架构的检验最严格，而这套架构恰好在最严格处最完整。

## 18.7 场景六：扩展开发者的第一天

一个开发者想为 OpenCode 做两件事：一个内部 MCP 工具服务器和一个行为插件。走读扩展开发全程。**MCP 侧**：写一个最小的 MCP 服务器（echo 式单工具，10.14 的最小复现起点），配置进 opencode.json 的 mcp 段（10.3 的配置即连接），启动后观察 dialog-mcp 的连接健康（16.3 的状态面）；工具经汇入管线出现（10.8 的五步：发现、翻译、归类、注册、快照），默认进 Code Mode（mcp-codemode-defaults），测试工具调用走 elicit 表单（10.11 的双向交互）验证表单链路；协议层问题用 stdio 的遗言机制定位（10.2 的 EXIT_WAIT）。**插件侧**：从空插件起步（10.14 的逐步加钩子法），先挂 tool.execute.before 观察参数（hooks.ts 的契约），再加 system-prompt 织入（10.5 的编织表），配置项声明进插件 schema（10.12 的第一公民配置），调试在 simulation 模式进行（14.2——不连真模型）；发布走 npm，更新由 plugin/update 接管（10.6）。第一天结束时，开发者的体验结论应当是：**扩展面的每一步都有状态可看、有错误可查、有模拟可跑**——这是第六章注册隔离、第十章生命周期协议、第十四章模拟资产、第十六章状态面四处机制的合力，也是"扩展生态健康度"（10.16）对开发者个体的意义。

## 18.9 场景七：跨天长任务的上下文管理

一个大型重构任务横跨三天、上百步——检验上下文工程的极限场景。走读全程。**第一天**：任务启动，目标写入 todo 工具（6.12 的会话内元数据——18.9 前文 5.17 说的"目标物化"），探索与首批评实施并行；上下文水位在傍晚逼近，压缩触发（5.2 的水位线），检查点落库（5.8 的原子替换），会话以"折叠的历史 + 完整的近期"过夜——会话是持久实体（3.1），进程可以退出，第二天继续。**第二天**：恢复昨天会话（回放协议补全画面，4.9），模型从检查点与 todo 双锚点重建任务语境（5.13 的骨架保真与 todo 目标物化的双保险）；中途出现一次方向漂移（5.17 的模式一），用户 steer 一条转向消息（3.2 的收件箱投递），循环在下一个安全切点接住新意图；下午用户手动 /compact 释放探索期的噪声（3.3 的控制项压缩）。**第三天**：收尾与回归——测试套件的最后修正跑在后台（6.5 的作业化），完成时注意力提示（12.8）；最终 diff 经 patch 协议呈现（13.4），用户审查合并。走读的观察：**跨天任务的可用性来自"上下文的可重建性"**——检查点（摘要）、todo（目标锚）、快照（工作区状态）、事件回放（画面状态）四样东西共同回答"第二天醒来时，系统如何知道自己在哪里"。四样东西缺一，长任务就会在重启时失忆——这是第五章与第四章协同的产品级呈现。

## 18.10 场景八：贡献者之旅：从读码到 PR

最后一个场景面向仓库的未来贡献者，把全书的方法论串成一次真实贡献。**起点**：想给 edit 工具加一个小的改进（比如更友好的失败提示）。**读码**：按第十四章结语的方法论——先立模型（6.6 的 edit 机制：LF 视图、三级降级、missHint、文件锁），再读实现（packages/core/src/tool/plugin/edit.ts），验证咬合；本章 18.3 的场景走读提供"机制在真实流里何时被触发"的时间线参照。**复现**：写一个失败用例——core 的测试环境（14.1 的包内测试）加 simulation 手段（14.2），让新提示路径可以在伪 LLM 流下验证。**实现**：改动收敛在工具层（6.1 的注册体系保证不碰引擎），遵守依赖方向（2.2）、错误反馈三形态（6.13）、权限元数据不动（改动只涉及结果文本）。**验证**：bun run test 与 typecheck（CONTRIBUTING 的包内校验），相关回归（edit 的既有测试若有）全绿。**提交**：PR 描述按三层规范引用（14.13），等待依赖方向与生成物纪律的审查（14.7 的纪律点）。旅程的总结：贡献的每一步都有第十四章与第十八章的对应章节作地图——**开源仓库的贡献体验，本质上是它的架构自明性（17.6 的决策完备性）乘以文档与测试的完备度**；本套文档希望在这两个乘数上都做一点加法。

## 18.13 场景九：远程执行的前瞻走读

一个前瞻场景（机制接缝已存在、完整实现属未来，标注为作者推演）：开发者的代码在远程开发机上，本地只有终端——agent 的执行应跟随代码。走读基于既有接缝的推演：**执行位置抽象**——Environment 服务（13.11）决定进程在哪里跑，远程执行即提供远程实现；**文件一致性**——工具的读写走远端文件系统（file-access 的边界语义随 Location 而去，8.5），本地不再直接碰文件；**会话归属**——Location 仍指向远端目录（2.5 的实例模型），server 可以跑在远端（11.10 的远端连接形态）或本地代理远端；**终端与 PTY**——shell 与测试跑在远端 PTY（13.6 的持久票据跨网络附着），输出流经事件通道回本地渲染（12.3）；**快照与回滚**——快照对象库随远端数据目录（13.3），回滚作用于远端工作区；**权限与观测**——权限弹窗仍出现在本地界面（事件面跨网络，4.9），观测数据在远端落库、按需查询（16.3 的状态面加 16.20 的出口格式）。走读的结论：**远程化不新增机制，只新增实现**——第二章的替换清单（2.6）加 Environment 抽象加三套 SQLite 后端（4.1）已经把"换执行位置"的接口预留完毕，这正是"内核与传输分离、执行与环境解耦"两条架构决策的前瞻价值：**未来的部署形态，在今天的接口里已有座位**。

## 18.14 场景十：安全事件的应急演练

最后一个场景面向运维与安全-minded 用户：假设怀疑一次异常（agent 行为怪异、疑似提示注入——8.10 的攻击面一），如何做一次结构化的应急演练。走读全程。**第一步：圈定现场**——立即停止可疑会话（Esc 中断的安全语义保证已发生动作已落库，3.8 的结算），快照当前工作区状态（13.3 的 capture，作为取证基线），导出事件时间线（4.9 的回放协议）。**第二步：审查动作**——遍历可疑窗口内的事件：哪些工具被调用、参数是什么、哪些被批准（8.12 的审计面：请求与回复的完整记录）、哪些被拒绝；重点核对写类动作的 diff（8.7 的预览记录）与外发类动作的目标（webfetch 的 URL）。**第三步：判定边界**——对照 8.10 的三条攻击面：注入（是否有异常来源的内容后紧跟异常动作）、外泄（是否有敏感内容出现在外发参数）、破坏（是否有破坏性命令的未遂尝试）。**第四步：止损与加固**——工作区回滚到可信快照（13.3 的 restore），收紧规则（托管策略加 deny，8.9），轮换可能暴露的凭据（7.7），必要时关闭可疑的 MCP 服务器与插件（10.3 的连接治理、10.4 的代切换）。**第五步：复盘**——事件时间线归档（16.5 的取证叙事），规则与检测的缺口补进 16.4 的对照表与 14.9 的测试面。演练的总结论：**应急的每一步都有对应设施**（中断安全、快照取证、事件审计、规则收紧、凭据轮换）——安全事件的可处置性同样是架构性质的兑现，而不是临场发挥。

## 18.15 场景之外的空白：走读没有覆盖什么

诚实的走读应当指出空白（作者分析）。**空白一：多人实时协作**——本套走读的场景都是"一个人的多会话"，两个人同时驱动同一个会话的协作语义（冲突的输入、并发的批准）在现有机制里是"run-coordinator 的合并或拒绝"（3.7）这一保守处理，真正的实时协作（光标级、消息级）不在当前机制谱系内。**空白二：跨项目的全局记忆**——会话与 Location 绑定（3.1），"我在所有项目里的偏好与历史教训"没有一等公民的载体（kv 与全局配置是雏形，但语义化的跨项目记忆是另一回事）。**空白三：长生命周期的知识沉淀**——todo 是会话级的（6.12），项目级的知识沉淀依赖 AGENTS.md 的人工维护（9.9），"agent 自己维护项目知识库"的自动化闭环在当前机制里只有 /init 一个起点。**空白四：成本的实时干预**——15.12 的预算上限是事后刹车（超了就停），"花到一半提醒并让用户选择"式的实时干预交互尚不存在于走读到的机制里。**空白五：评估闭环**——17.13 的指标讨论了口径，但"每次任务的自动评分与回归"没有机制载体（simulation 能复现，评分是人工）。五个空白的价值不在批评而在**预告演进方向**——它们每一个都能在现有架构里找到接缝（协作走事件面、记忆走存储面、沉淀走指令面、干预走权限交互面、评估走测试面），这与 18.13 的结论呼应：**好架构对未来的态度，是把接口留好，把实现留白**。

## 18.16 场景走读的收束观察

十个场景走完，做最后一次收束。场景一验证了"复杂性的下沉"（启动链路吸收全部环境复杂度）；场景二验证了"机制的协奏"（二十余个机制在一条任务时间线上各就各位）；场景三验证了"存储纪律的兑现"（可恢复是公理的总和）；场景四验证了"结构性隔离"（并行安全不靠小心靠结构）；场景五验证了"无人值守的完整性"（最严格场景下的权限与审计）；场景六验证了"扩展面的一等公民地位"（扩展开发的每一步都有设施支撑）；场景七验证了"上下文可重建性"（跨天任务的四锚点）；场景八验证了"架构自明性对贡献的价值"；场景九验证了"前瞻部署形态已有接口座位"；场景十验证了"安全事件的可处置性"。十个场景合起来覆盖了产品语义的完整光谱：从人的第一天到机器的无人值守，从正常流到崩溃流，从单会话到并行，从使用到扩展，从短任务到跨天长任务，从当下形态到未来部署，再到贡献者的第一条 PR 与安全应急的演练。**架构的最终检验不是任何单一场景的表现，而是场景之间不互相拆台**——并行不破坏崩溃恢复（Location 与会话的隔离在结算时依然成立）、自动化不弱化权限（无人值守恰是 fail-closed 的主场）、扩展不侵蚀可观测（MCP 事件走同一 Bus）。回望全书：第一章的循环模型预言了机制的存在，中间十六章解剖了机制的内部，本章验证了机制的协奏——至此，从公理到机制到系统到场景的完整链条闭合。愿这条链帮助读者在面对下一个系统时，也能走一遍同样的路：立模型、解机制、验协奏。

## 18.17 结语：三层索引与一条主线

全书至此可以压成三层索引加一条主线。**第一层是公理**（第一章与第三、四章）：循环的三条数学性质（无内建终止、信息单调增长、环境不可预知）与三条工程公理（状态先行落库、切点转移状态、可恢复错误不失败）——它们回答"为什么必须有机制"。**第二层是机制**（第二至十六章）：二十余个子系统的解剖——它们回答"机制如何运转、付出什么代价"。**第三层是场景**（第十七章的生态坐标与本章的十个走读）——它们回答"机制在真实世界里如何协奏、边界在哪里"。三层之间是双向可走的：从场景问"为什么会卡"可以沿矩阵（18.11）回到机制，从机制问"为什么存在"可以沿各章开头回到公理。**一条主线**则是反复出现的那句话：agent 的一切架构都是循环性质与稀缺资源在工程上的必然投影——步数上限对应无内建终止，压缩对应单调增长，恢复与权限对应不可预知，Code Mode 与缓存对应 token，流式呈现对应时间，注意力系统对应人。本套文档的全部努力，就是把这条主线从口号验证成体系：每一章都从公理出发落到代码，再从代码回到公理。如果读者合卷时能用自己的语言向同事复述"OpenCode 为什么在收件箱里放两种投递模式、为什么压缩要提前算摘要、为什么权限是三值的"，并且每个答案都带着"因为循环的某条性质"或"因为某个约束的不对称"这样的推导，那么这十八章就完成了它的使命——**原理性介绍的目标从来不是让读者记住结论，而是让读者获得重新推导结论的能力**。
