# 第七章 · 模型接入层

## 7.1 问题的形状：几十家服务商与一个统一循环

第三章的会话引擎消费的是一条统一的 LLMEvent 事件流，它对"模型是谁"完全无感。但现实世界有几十家模型服务商：协议不同（Anthropic 的 messages 协议、OpenAI 的 chat/completions 与 responses 协议、Google 的交互协议）、鉴权不同（API key、OAuth、云厂商签名）、流式格式不同（SSE 分帧、事件语义）、错误语义不同（限流、溢出、无效请求的表达各异）。模型接入层的使命是**把这几十种差异吸收在循环之下**，让引擎只见一条流。OpenCode 用三层结构完成这个吸收：元数据目录（models.dev）、按需加载的 provider 包（core/src/provider.ts）、自研协议层（packages/ai）。三层各管一件事：模型"是谁、多贵、多大"（元数据）、"从哪里装"（分发）、"怎么对话"（协议）。

## 7.2 元数据目录：models.dev 与模型解析

每个 provider 有哪些模型、上下文窗口多大、价格多少、是否支持图片/推理/原生压缩——这些元数据 OpenCode 不在自己仓库维护，而来自开源项目 models.dev（CONTRIBUTING.md:19-21 明确：新增 provider 先加到 models.dev）。这个外包决策的理由值得拆解：模型目录是**高频变化、多方贡献、跨工具共享**的数据——今天上新模型、明天调价格，若在产品仓库维护，每个 agent 工具都要各自跟进，而目录本身没有产品逻辑，独立维护反而让全生态受益。OpenCode 侧的对应设施是 ModelsDev 服务（server 装配清单可见，routes.ts 导入并按 options 装配）负责目录的拉取与缓存，core 的 Model 服务（core/src/model.ts）按 providerID/modelID 提供查询；更上层的 model-resolver.ts（core/src/model-resolver.ts）处理"用户写了个模糊的模型名"到"唯一确定模型"的解析。

元数据的消费点遍布引擎，两个最关键：压缩模块按窗口计算水位线（窗口未知时按 200k 假设，第五章），runner 的模型解析结果 SessionRunnerModel.Resolved（runner/model.ts）携带 route、limit、cost、capabilities 四类元数据——cost 参与成本展示与预算决策，limit（上下文与输出上限）参与压缩与 OutputLimit 判定，capabilities（图片、推理、原生压缩支持）参与组装决策。**元数据的形状直接塑造引擎的决策面**：capabilities 里的每个布尔位都对应引擎里的一个分支。

## 7.3 Provider 包与按需加载

core/src/provider.ts 是 provider 注册表，它的关键决策是**发行包与能力包分离**。OpenCode 的发行体积里只有两个 AI 基础依赖（@ai-sdk/provider 与 @ai-sdk/provider-utils，core/package.json:96-97），几十家服务商的接入代码不在发行包里，而是运行时按需安装加载。provider.ts 的机制支持两类入口：原生 provider 包（OpenCode 自有格式，packages/ai 的 providers/ 目录即其内置集合）与任意 AI SDK 兼容包——aisdk: 前缀（provider.ts:19-23）让用户可以直接接 @ai-sdk/* 生态的任何包， packageName() 还处理 npm scope 迁移的兼容（provider.ts:25-28，包改名后旧配置仍然有效）。加载用 importModule/resolveModule（provider.ts:10），配合 Npm 工具按需把包安装到用户机器。

这个设计要放在产品分发语境里理解：桌面级产品对安装体积与依赖面极敏感，而模型生态的爆炸式扩张让"全量内置"必然走向臃肿与许可复杂化。按需加载的代价是**首次使用的时延与失败面**（网络下载可能失败），换取的是发行包的精简与生态的开放。Service 接口（provider.ts:361）暴露 provider 与模型的增删改查——用户添加自定义 provider、配置自定义模型都走这里，注册表把"内置目录"与"用户自定义"合流成统一视图。

## 7.4 packages/ai：自研协议层的结构

packages/ai 是"Effect 化的 AI 层"，值得注意它的依赖清单里没有 vercel ai-sdk 的运行时（只有 aws、google 等厂商的鉴权库，packages/ai/package.json）——**OpenCode 自己实现了协议编解码与流解析**，只复用厂商鉴权库。自研的理由：ai-sdk 的抽象面向通用生成场景，而 agent 需要的是事件流的精细控制（工具调用边界的实时识别、思考流的分离、每步的 usage 统计）与错误的精细分类（第七章 7.6），通用抽象在这里要么不够用要么要大量绕过。自研协议层的目录结构按职责分块：

providers/ 下是四十余个协议实现目录与文件：anthropic、openai（含 openai-compatible 与 openai-compatible-responses 两个兼容变体）、google 与 google-vertex 系（vertex-chat、vertex-interactions、vertex-messages、vertex-mistral、vertex-responses、vertex-shared——同一个厂商按 API 面拆分）、amazon-bedrock（含 mantle）、azure、cloudflare-ai-gateway 与 cloudflare-workers-ai、alibaba、deepseek、moonshot、minimax、mistral、groq、cerebras、xai、zai（含 zai-coding-plan）、openrouter、vercel-ai-gateway、togetherai、fireworks、deepinfra、baseten、venice、digitalocean、cohere、meta、typesafe-ai、opencode（自家网关）；另有语音与媒体方向的实现：assemblyai、deepgram、elevenlabs、cartesia、runway。每个实现目录含鉴权、端点、协议编解码三部分。

route/ 下是请求的统一抽象：auth.ts（各厂商签名与令牌）、executor.ts（执行器）、transport/（HTTP 传输与流解析）、protocol.ts（wire 协议）、decision.ts 与 decision-client.ts（重试与轮换决策，7.6 展开）。llm.ts 与 effect.ts 把"一次 LLM 流式调用"建模为 Stream<LLMEvent>——这是全层的核心抽象，下一节专述。外围还有 generation.ts、image/media/speech/transcription/video 五组客户端（多模态的生成与理解面）、cache-policy.ts（缓存策略声明，第五章预计算的上游）、provider-error.ts（错误分类）、tool.ts 与 tool-runtime.ts、tool-history.ts（工具在协议层的表达）、loop.ts、effort-updates.ts（推理力度更新）、experimental/（实验面，语音 Realtime 在此）。

## 7.5 LLMEvent：把流式响应建模为事件流

一次模型调用在协议层是一条事件流。LLMEvent 的事件类型覆盖：文本增量（textDelta）、思考流、工具调用（开始/参数增量/完成）、每步结束（stepFinish）、整体结束（finish）。建模为 Stream 的收益在消费端全兑现：引擎用统一的流消费代码处理所有厂商（第三章 step.ts:110-135 的逐事件消费）；工具调用边界在流中实时识别，已完成的调用即刻派发 fiber（第三章的并发执行）；事件翻译由 createLLMEventPublisher 单向投影为会话事件（保序）。流的另一个属性是**可组合**：重试、超时、断流续写都是对流的变换（失败则重开一条流，续写时把已收到的前缀记为有效），Effect Stream 的组合子让这些变换保持声明式。

值得点破一个深层收益：**事件流抽象是"多厂商统一"的真正落点**。元数据统一的是"选型"，provider 包统一的是"加载"，而只有事件流统一了"运行时行为"——引擎对 Anthropic 的 SSE 与 Bedrock 的事件帧写出完全相同的消费代码。三层各自统一一个维度，缺一层都会让差异泄漏进引擎。

## 7.6 错误分类与两层重试

agent 对模型调用的容错是分层的，OpenCode 明确做了两层。**传输层**（packages/ai 的 route/decision.ts 与 decision-client.ts）处理传输与协议级问题：连接失败、HTTP 状态码、API key 失效时的 key 轮换（rotate）、限流退避。它产出带 recovery 标记的错误：AIError 体系区分 Transport（传输层问题）、InvalidRequest（请求构造问题）、InvalidProviderOutput（厂商返回了不合协议的内容）等类别，并给出恢复建议标记——"retry-full"（整步重来）与"rotate-and-retry-full"（换 key 再来）。**会话层**（SessionRunnerRetry，core/src/session/runner/retry.ts，另有 core/src/model-retry.ts 支撑）消费这些标记做会话级决策：值不值得整步重试、退避多久、重试几次。两层的分工原则：传输层只修"连接"问题（换 key、重连、退避），会话层只修"步"问题（重试策略、续写决策）；传输层能解决的错误不上抛（引擎无感），上抛的错误必带结构化标记（引擎据此分派）。错误分类的另一个关键产物是 isContextOverflowFailure——把"上下文溢出"从一般错误里辨出来，第五章的收缩循环（compaction.ts:680 消费）靠它驱动：溢出不是失败，是压缩的触发信号。错误分类的粒度决定恢复策略的精度，这句话在压缩、续写、轮换三处都得到了验证。

限流与用量还得到了专门的设施：usage-limits.ts（core/src/usage-limits.ts）跟踪限额状态（Claude 等订阅制模型的周期限额），usage.ts（session/usage.ts）按会话累计用量统计。订阅制接入（Claude Max、GitHub Copilot 等）有专门的认证模块（core/src/github-copilot/ 等）。

## 7.7 凭据与 OAuth

凭据管理统一在 Credential 服务（core/src/credential.ts:39-70），接口只有三个动作：get、set、remove。存储按平台走系统安全机制（macOS keychain 等），ID 命名空间区分 provider 凭据与 integration 凭据——同一个凭证库里住着两类秘密，命名空间防止混用。OAuth 流程在 core/src/oauth/ 目录（各家 OAuth 流程的差异封装），凭据测试有专门文件（packages/core/test/credential.test.ts 与 credential-lock.test.ts——凭据写入的并发与锁有独立测试，可见"凭据操作是并发敏感面"）。这里必须区分两个"鉴权"：**provider 的 API key**（本节，引擎调模型用）与 **client 连 server 的密码**（ServerAuth，packages/server/src/auth.ts，第十一章）——前者是 agent 的能力凭证，后者是会面的门禁，两层绝不能混。

## 7.8 一次模型调用的完整路径

把本章与第三章缝合：SessionModelRequest.primary（session/runner/llm.ts:260-285）组装请求并过请求钩子 → LLMClient.stream（step.ts:110 的消费点）→ route 按 provider 选择传输与协议 → 厂商流式响应 → LLMEvent 流 → publisher 投影成会话事件 → 工具调用派发 → 结果回灌。若流失败：传输层先尝试恢复（轮换、重连）；不可恢复则上抛带标记的错误；会话层按标记决定 Retry/Continue/RecoverFull。若上下文超限：isContextOverflowFailure 触发压缩收缩循环。整条路径上没有一步是厂商特定的——所有差异都在 providers/ 目录与 route 抽象下。这就是"接入一家新厂商"的成本为什么可以低到"加一个目录"：协议实现放 providers/、元数据放 models.dev、循环代码一行不动。

## 7.9 传输与流解析：从字节到事件的四级翻译

一次模型响应从网线到引擎，经历四级翻译，理解这四级就理解了 transport/ 与 protocols/ 的分工。第一级是**字节层**：HTTP 连接上的字节流，chunked 分帧，TLS 终结；第二级是**帧层**：SSE（text/event-stream）的 event/data 分帧，或 Bedrock 的 event-stream 帧——transport/ 的职责是把字节流切成语义帧，处理半包、粘包与连接中断；第三级是**消息层**：每帧内的 JSON 载荷按厂商协议解码（content_block_delta、choices[0].delta 之类），providers/ 目录里的编解码器在此工作——厂商各自的增量语义（哪段是文本、哪段是工具参数、哪段是思考）被翻译为统一形态；第四级是**事件层**：统一形态映射为 LLMEvent（textDelta、tool-call、stepFinish、finish），携带 usage 与排序信息。四级分离的价值在故障定位与演进两方面：断流是第一二级的问题（重连策略）、解析错乱是第三级的问题（编解码器 bug）、语义错位是第四级的问题（投影 bug）——问题在那一层，修复就在那一层；厂商升级协议时只动第三级，引擎无感。自研协议层（7.4 的理由）在这四级的粒度控制上才会显得必要：通用 SDK 往往把二三四级揉在一起，粒度粗了之后，断流续写（第三章 Continue）这类精细机制就没了着力点——续写需要的是"已完整解析的事件前缀"，只有事件层边界清晰才能定义"前缀"。

## 7.10 错误分类的决策表：从错误到恢复动作

7.6 说错误分类决定恢复精度，这里把"错误 → 类别 → 恢复动作"的决策链整理成表（类别与恢复标记来自 packages/ai 的 provider-error.ts，消费点在 step.ts 与 compaction.ts）：

| 错误类别 | 典型成因 | recovery 标记 | 消费者与动作 |
| --- | --- | --- | --- |
| Transport | 网络断、超时、5xx | retry-full / 退避重连 | 传输层先试；不可恢复上抛会话层 Retry |
| InvalidRequest | 请求构造违规（参数、格式） | 不重试（确定性失败） | 直接失败，模型或引擎修请求 |
| InvalidProviderOutput | 厂商返回不合协议内容 | rotate-and-retry-full | 换 key/换通道整体重来 |
| 上下文溢出 | 历史超窗口 | isContextOverflowFailure | 触发压缩收缩循环（第五章 deliver） |
| 限流（429） | provider 速率限制 | 退避（usage-limits 跟踪限额） | 指数退避或切换 provider |
| 凭据失效 | key 过期、订阅限额耗尽 | 换凭据或提示登录 | Credential 层处理，可能触发 OAuth 重登 |

表的右两列揭示了设计的对称性：**每个类别恰好对应一个恢复主体**（传输层、请求构造者、路由层、压缩模块、退避器、凭据层），没有两个类别共享同一恢复路径，也没有恢复路径无类可依。错误分类的完备性检查因此有一个可操作的标准：新错误出现时，若无法归入既有类别并指派恢复主体，说明分类体系需要扩充——这与可辨识联合的穷尽性检查（第二章 2.4）一脉相承：类型系统强迫你思考"还有什么错"，错误表强迫你思考"谁来恢复"。状态（usage-limits 的限额跟踪）还让恢复具有记忆：连续 429 不再盲目退避，而是查限额窗口、必要时降级到备用模型——恢复策略从无状态反射升级为有状态决策。

## 7.12 协议族分析：三大 wire 协议的谱系

providers/ 目录的四十余个实现初看庞杂，实际上可以归并为三大协议族加若干特化族，归并后就能看清"加一家厂商"的真实工作量。**族一：OpenAI 系**（openai.ts、openai-compatible.ts、openai-compatible-responses.ts）——chat/completions 与 responses 两种 API 面，兼容变体承接所有"OpenAI 风格"的厂商（deepseek、moonshot、groq、togetherai、fireworks 等大量兼容实现），一家新厂商若兼容 OpenAI 协议，接入成本接近零（配 base_url 与模型元数据即可）。**族二：Anthropic 系**（anthropic.ts、anthropic-compatible.ts）——messages 协议与独立的内容块模型（文本块、工具块、思考块分立），流事件语义与 OpenAI 系差异大，但同样是"一家实现、多家复用"的兼容格局。**族三：云托管系**（azure、amazon-bedrock、google-vertex 系）——协议复用厂商原生族，鉴权与端点全换（云签名、区域端点、deployment 命名），azure 与 vertex 还各有多个 API 面变体（vertex-chat/interactions/messages/mistral/responses 的拆分正是 API 面的碎片化证据）。特化族包括自网关（opencode.ts）、聚合器（openrouter、vercel-ai-gateway、cloudflare-ai-gateway——它们本身是"协议的协议"，向下转发到真实厂商）与媒体特化（assemblyai、deepgram、elevenlabs、cartesia、runway——语音视频方向）。谱系的启示：**协议兼容是生态的引力**——OpenAI 系协议事实上成了行业 wire 标准，兼容实现撑起了 providers/ 目录的大半；接入工作的主要量集中在云托管系（鉴权与端点）与真正的特化族上。理解了谱系，providers/ 目录的四十个条目就坍缩为"三个族加一群配置"。

## 7.13 模型选择的经济学：成本、能力与路由的三角

模型接入层最终服务于一个用户决策：选哪个模型跑这个任务。把决策因素整理成经济学框架。**成本轴**：models.dev 的价格元数据（输入/输出单价）参与成本展示（Resolved 的 cost），结合第一章的二次律，长会话对输入单价敏感、单步重活对输出单价敏感——成本敏感度随任务形态变化。**能力轴**：capabilities 位集（图片、推理、原生压缩、上下文窗口）决定"能不能做"，窗口大小与 limit 决定"做多大"——压缩模块的预算公式直接消费窗口值。**路由轴**：route 选择（7.4 的 executor 与 transport）叠加了可用性维度——同一模型可能有多条路（直连、网关、云托管），路由决策引入延迟与稳定性差异。三轴交叉的实际决策模式在产品层表现为：agent 配置绑定默认模型（第九章），子代理可以绑定更廉价的小模型（探索类任务降级到便宜模型是常见的成本优化），用户随时切换（TUI 的 dialog-model 面板）。架构层提供的支撑是**元数据驱动的可比性**：窗口、价格、能力都在 models.dev 元数据里结构化，任何上层决策（自动降级、成本预警）都有数据可依——没有结构化元数据，模型选择就只能靠人的经验口口相传。

## 7.15 兼容轨的双实现：aisdk 与 native 的取舍

第七章开头说 OpenCode 自研协议层，但 core 里同时存在 aisdk.ts 与 aisdk-native.ts，且有对应测试（aisdk.test.ts、aisdk-native.test.ts）——这揭示了接入层的**双轨实现**。原生轨（native）是 packages/ai 的自研协议栈（7.4-7.5 的四级翻译与事件流），特点是控制粒度细（断流续写、工具边界识别、usage 统计都建立在自有事件语义上）。兼容轨（aisdk:）是 provider.ts:19-23 的前缀机制，直接桥接 @ai-sdk/* 生态的任意包——特点是覆盖面广（社区生态的厂商接入零成本）但控制粒度受制于桥接层（SDK 抽象到哪，OpenCode 就细到哪）。双轨的服务边界清晰：主流厂商走原生轨（享受精细控制），长尾厂商走兼容轨（享受生态广度），两者在 provider.ts 的注册表里合流成统一视图，SessionRunnerModel.Resolved 的消费者（runner 与压缩）完全不感知轨的差异。双轨的代价是维护两条实现路径的一致性（同一能力两轨都要有——测试文件成对出现就是这条纪律的痕迹），收益是"控制深度"与"生态广度"兼得。这个模式与第六章 6.3 的双轨（直接工具与 Code Mode）、第十二章 12.5 的双轨（自研编辑器与 zed）形成了一个仓库级的设计习惯：**核心路径自研保深度，长尾路径桥接保广度**——凡是"少数高频场景需要深度、大量低频场景需要覆盖"的地方，这个习惯都适用。

## 7.17 推理力度与输出控制：请求参数的治理面

除了"选哪个模型"，请求级还有一组参数影响成本与质量，本章补上这个治理面。**推理力度**（reasoning effort）：支持推理的模型可以在"想多久"上分档（低/中/高，ai 层的 effort-updates.ts 处理推理力度的动态更新），力度与 token 消耗正相关——力度选择因此是成本旋钮（GitHub 集成的 variant 配置——high/max/minimal，doc_zh/components/07——就是它在产品面的暴露）。**输出上限**：单次响应的最大长度（OutputLimit 结局的上游参数，3.6 的两次阈值依赖它）——上限调低省预算但增加续写频率，调高反之，最优值取决于任务形态（写大文件的步需要高上限，问答步不需要）。**缓存策略**：cache-policy.ts 声明请求的缓存意图（哪些段稳定、哪些段易变，第五章 5.15 的分层模型是其理论依据）。**工具选择面**：第七章 6.2 的 snapshot 决定哪些工具在请求里——它既是权限面也是参数面（工具清单影响模型的行为分布）。这四类参数的共同治理原则：**请求参数是策略变量，不是魔法数字**——每一类都应该能被配置表达（agent 级、会话级）、被元数据约束（模型能力位决定合法取值）、被观测验证（15.14 的度量点回读效果）。参数治理的成熟度是模型接入层从"能调通"到"调得聪明"的分水岭，也是 7.13 经济学框架在请求粒度的落实。

## 7.18 本章小结

模型接入层的三层解耦——元数据（models.dev）、分发（按需 provider 包）、协议（packages/ai）——各自统一了一个变化维度（选型、加载、运行时），合起来让引擎对"几十家服务商"保持无感。事件流抽象（LLMEvent）是运行时统一的落点；错误分类（AIError 与 recovery 标记）让传输层与会话层各司其职；凭据与 OAuth 封装在 Credential 与 oauth/ 里，与连接鉴权严格分层。下一章转向约束这一切的手铐：权限系统——模型的手（第六章）再强，也要看权限让它摸哪里。
