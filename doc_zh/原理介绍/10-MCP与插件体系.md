# 第十章 · MCP 与插件体系

## 10.1 同一个问题的两个答案

扩展 OpenCode 的能力有两条路：让外部程序提供工具（MCP，Model Context Protocol），或让宿主内的代码挂进引擎生命周期（插件）。两条路解决的是同一个问题——**在不修改内核的前提下增加能力**——但力学不同：MCP 是进程外的、协议化的、语言无关的；插件是进程内的（或由宿主管理的）、API 化的、深度耦合引擎类型的。OpenCode 同时维护两条扩展面，正是因为它们的适用域互补：通用工具（别人写的检索器、数据库浏览器）走 MCP；针对引擎行为的定制（改提示词、注入钩子、定制权限流）走插件。本章先讲 MCP 的连接与汇入，再讲插件的生命周期与编织点，最后对比两者。

## 10.2 MCP 传输层：stdio 与 Streamable HTTP

MCP 客户端实现在 core/src/mcp/（client.ts、index.ts、stdio.ts、pool.ts、connection.ts、oauth.ts、socket-client.ts、instructions.ts），基于官方 MCP SDK（@modelcontextprotocol/client）。协议能力覆盖三类：工具（tools/list、tools/call）、资源（resources 与 ResourceTemplate）、提示词（prompts），外加表单交互（ElicitRequestFormParams/URLParams/ElicitResult——MCP 服务器可以向用户请求结构化输入，OpenCode 把它接到自己的表单体系 form.ts 上）。

stdio 传输（mcp/stdio.ts）把 MCP 服务器作为子进程运行，通过 stdin/stdout 的 JSON-RPC 消息通信。实现里的一组常量读起来就是一部"子进程协议治理手册"：关闭宽限期 CLOSE_GRACE = 2 秒（stdin 关闭后等子进程优雅退出，注释明言对齐官方 SDK 的 StdioClientTransport 行为）；强杀时限 FORCE_KILL_AFTER = 2 秒（SIGTERM 后超时升级 SIGKILL）；出站队列容量 OUTGOING_CAPACITY = 64（背压控制——服务器消费不动时，客户端的发送要被反压而不是无限堆积）；单帧上限 MAX_FRAME_BYTES = 16 MiB（超出视为协议错误——一个失控的 server 输出不该拖垮客户端内存）；意外退出的线索收集窗口 EXIT_WAIT = 1 秒（等待退出码与 stderr 尾部，stderr 末尾通常写着崩溃原因）。这五个数字共同表达一个立场：**对外部进程既合作又设防**——给它优雅退出的机会，给它收集遗言的时间，但不给它无限的信任与资源。

HTTP 传输（mcp/client.ts 的 StreamableHTTPClientTransport）服务远程 MCP 服务器，鉴权走 UnauthorizedError 与 OAuthClientProvider（SDK 的 OAuth 接口，OpenCode 的实现对接 core/src/mcp/oauth.ts 与第七章的凭据体系）；另有 socket-client.ts 处理 socket 形态的连接。传输层的抽象是 SDK 的 Transport 接口，OpenCode 的贡献是把它 Effect 化：每个传输是一个资源作用域内的 fiber，作用域关闭时走 stdio 的优雅退出协议——SDK 的过程式传输与 Effect 的资源安全在 connection.ts 里缝合。

## 10.3 连接池与生命周期

Mcp 服务（mcp/index.ts）管理全部连接的生命周期。它的设计要点：**配置即连接**——配置里声明的每个 MCP 服务器对应池里的一个槽位，配置变更（isDeepStrictEqual 对比新旧配置）触发对应连接的重建，未变的连接保持不动（连接是贵资源，启动子进程、握手、列工具都要时间，能不动就不动）。集成身份用 SHA1 哈希生成（index.ts 的 createHash），使"同一个服务器配置"跨重启有稳定 ID。事件的出口是 McpEvent（工具列表变化、资源变化等），其中瞬时通知走 ephemeral 构造器（第四章持久/瞬时双通道的分类在这里又出现一次——工具列表的抖动不值得落库）。并发治理的原语齐全：Fiber/FiberSet 管理连接 fiber，Semaphore 串行化敏感区（如初始化握手），Latch 做状态闩（防止连接与关闭的竞态），Scope 承载资源。pool.ts 专门抽象"池"语义：连接的获取、健康检查与失效重建。

连接的上层语义是**能力目录**：每个连接把它的工具、资源、提示词注册进统一目录，供第六章的 snapshot 计算本轮可见集。MCP 工具的输入 schema 是原始 JSON Schema（MCP 协议里 schema 就是 JSON Schema），core/src/tool/runtime.ts 对这类"非 Standard Schema 输入"做了专门的编解码缓存（jsonSchemas 这个 WeakMap，注释解释了为什么用弱引用而不是 Effect Cache：每个缓存项持有查找 fiber，强引用会让被驱逐的 Location 服务无法回收——一个内存生命周期的细节，但正是这类细节决定了多 Location 长时运行不泄漏）。MCP 工具默认进 Code Mode（core/src/plugin/mcp-codemode-defaults.ts），因为它们多为"查询类"（查数据库、查 API），编排价值高；用户可以配置改回直接暴露。

## 10.4 插件的生命周期：代（Generation）与前缀差异

插件体系的主入口是 core/src/plugin.ts，实现的注释透露了它的核心机制：active 这个 Map 按**激活顺序**为每个请求的定义保留一个槽位，包括 setup 失败的也占位——注释原文解释：这样"前缀差异（prefix diff）保持索引对齐，失败的修订版在变化前不会被重试"。这句话浓缩了一套精巧的热重载协议：插件的期望定义列表（来自配置）与实际激活列表做**前缀对齐**——从头往后逐个比，定义没变的插件保持激活（不重新 setup），从第一个变化点开始全部重新激活。"失败占位"保证索引不因失败而错位：第 2 个插件 setup 失败时它仍占着槽位 2，第 3 个插件对应槽位 3，下次重载时比较仍然对得上。"失败不重试直到变化"防止坏插件在每次配置抖动时反复崩溃重试。

"代（Generation）"（plugin/service.ts 导出的 Generation 类型）是这套协议的时间单位：一次全量重载产生新的一代，旧代的插件在事务里退出（transform/reload，第九章 State 模式的插件入口），新代的插件依次激活（awaitActivation 等待就绪）。Service 类型（plugin/service.ts）暴露插件的查询与失败信息（Failure 类型——哪个插件、什么错误），失败被收集而非抛出（第六章注册隔离的同一原则）。根作用域 Scope.make()（plugin.ts 顶部）让所有插件激活的作用域都从根 fork——插件占用的资源（子进程、句柄）登记在作用域里，代切换或关闭时统一释放。supervisor.ts（core/src/plugin/）负责插件进程的治理面（健康、重启、日志），host.ts 的 PluginHost 是钩子能力的载体。

## 10.5 钩子契约：插件能改变什么

插件的能力由钩子（hooks）契约定义（core/src/plugin/hooks.ts，钩子类型来自 @opencode/plugin 包——packages/plugin 是插件 API 的契约层，Effect 风格的钩子签名）。按编织点清点（以 core/src/plugin/ 目录的模块为证）：

| 编织点 | 模块 | 能力 |
| --- | --- | --- |
| 工具执行 | tool.execute.before/after（hooks.ts） | 改写入参/改写结果（第六章管线） |
| 系统提示 | system-prompt/ | 织入提示词内容（第五章 5.6） |
| Agent | agent.ts | 注册/修改 agent 定义（第九章 9.7） |
| 命令 | command/ | 用户命令（斜杠命令） |
| 技能 | skill/ | 技能包 |
| Provider | provider/ | 模型接入定制 |
| 模型目录 | models-dev.ts | 目录数据补充 |
| 检索 | websearch/ | 网页搜索行为 |
| VCS | vcs/ | 版本控制适配 |
| 输入修复 | tool-input-repair.ts | 参数修复 |
| 目录缓存 | source-directory.ts | 工具目录来源 |
| 行为调优 | verbosity.ts、warming.ts、optimize.ts | 输出冗长度、预热、优化钩子 |
| 更新 | update.ts | 插件自身的更新 |

这张表说明插件的编织面是**全纵深**的：从提示词到工具参数到权限流（第八章 hooks 服务参与权限判定链）都有接缝。能力大必然治理重——10.4 的代机制、supervisor、失败隔离都是为了"能力大而不失控"。SDK 插件（plugin/sdk.ts 与 SdkPlugins，routes.ts 导入）是另一形态：用 packages/sdk 编写的程序化插件，在 SDK 进程里运行而非宿主进程——第十一章 SDK 语义的延伸。

## 10.6 插件包生态与身份

插件从哪来？plugin/module.ts 与 plugin/identity.ts 处理模块加载与身份（npm 包名、来源目录、版本）；plugin/source-directory.ts 与 plugin/instance.ts 处理目录级与实例级的插件来源。官方示例是 packages/plugins/figma（设计工具集成）。插件更新的生命周期由 plugin/update.ts 承担（检查、下载、替换、经代机制热换）。GUI 包（plugin.ts 导入的 GuiBundle 与 readFile 读取 GUI bundle 源码）是插件的界面扩展物——插件可以携带前端资源（配合 packages/gui-plugins 与 dialog 相关组件呈现）。

## 10.7 MCP 与插件的对比选型

把两条扩展面放进一张对比表：

| 维度 | MCP | 插件 |
| --- | --- | --- |
| 进程边界 | 独立进程，协议通信 | 宿主进程内或受管进程 |
| 语言 | 任意（协议无关语言） | TypeScript（Effect 契约） |
| 能力面 | 工具/资源/提示词/表单 | 全纵深钩子（提示词、agent、命令…） |
| 信任模型 | 低信任（设防常量、背压、帧上限） | 高信任（可改写入参与结果） |
| 适用 | 通用能力复用 | 引擎行为定制 |
| 失败影响 | 单连接失效，宿主无恙 | 失败占位隔离，宿主无恙 |

选型判据一句话：**能力是"给模型用的新工具"就走 MCP，能力是"改变引擎行为"就走插件**。两者共享的底层原则也一致：宿主可用性优先、失败隔离、状态可恢复、配置驱动的生命周期。MCP 的连接管理与插件的代管理在结构上是同构的——"期望状态 vs 实际状态，前缀对齐，差异重建"——这个模式值得记住，它是所有声明式资源管理（Kubernetes 的 reconciler、Terraform 的 plan/apply）的共同骨架，OpenCode 在两个尺度上都用了它。

## 10.8 MCP 工具的汇入管线：从 tools/list 到统一注册表

10.2 说连接把能力汇入统一目录，这里走一遍汇入的完整管线（以工具为例）。第一步**发现**：连接建立后客户端调 tools/list，得到该服务器的工具清单（名称、描述、JSON Schema 输入）；第二步**翻译**：MCP 工具被包装成 OpenCode 的工具定义（第六章五部件），name 加命名空间前缀（防撞名——两个 MCP 服务器都有 search 工具时，前缀区分），description 原样透传（模型可读），输入 schema 走 core/src/tool/runtime.ts 的 JSON Schema 编解码缓存（WeakMap 生命周期的细节见 10.3）；第三步**归类**：默认进 Code Mode（mcp-codemode-defaults），可配置改直接暴露；第四步**注册**：走 6.1 的统一注册校验（名称字符集、Standard Schema 兼容——MCP 的 JSON Schema 经 codec 转换适配），坏定义进 errors 隔离；第五步**快照**：进入 6.2 的 snapshot 计算，权限规则可针对 MCP 工具配置（资源模式含服务器名）。汇入管线的要点是**MCP 工具与内置工具在模型视角完全同构**——模型不知道也不需要知道某个工具来自本地实现还是外部进程。同构的前提是第五步之后所有管线（权限断言、钩子、规范化、结算）共用，这正是"统一注册表"设计的收益：扩展源可以多，执行管线只有一个。

## 10.9 代切换的完整时序：一次插件热重载的生命周期

把 10.4 的代机制展开成时序，看清"事务"的边界。触发：配置文件修改（或插件更新，plugin/update.ts）产生新的期望定义列表。对齐：当前 active 的槽位列表与新列表做前缀比较——第一个差异点之前的插件保持激活，差异点之后的进入重建。事务开启：State 的 transform/reload 提供事务语义（第九章），新代的作用域从根作用域 fork。激活：差异点之后的新插件依次 setup（awaitActivation 等待就绪），失败的按"占位不重试"原则登记 Failure。切代：新代插件全部就绪（或失败占位）后，旧代插件在事务内退出——它们占用的资源（子进程、句柄）随其作用域关闭而释放（Scope 的资源安全，第二章 2.4）。广播：代切换完成经 Bus 广播事件，前端刷新插件状态面板（dialog 相关组件）。回滚路径：若新代整体失败到无法服务，事务语义允许退回旧代定义重新激活——回滚本身就是一次普通的代切换（旧列表重新成为期望列表）。这个时序的关键性质是**切换期间服务不断**：前缀对齐保证未受影响的插件零打扰，事务边界保证不会出现"旧代已退、新代未起"的服务真空。声明式资源管理（10.7 的 reconciler 类比）在这里给出了它最考验工程功力的部分：**从期望状态到实际状态的迁移必须是平滑的**，OpenCode 的答案是前缀对齐加事务切代。

## 10.11 MCP 会话时序走读：initialize 到 tools/call

把 10.8 的汇入管线与 10.2 的传输层接起来，走一遍一次完整 MCP 会话的时序（对齐 MCP 协议的握手语义）：

```
客户端(OpenCode)                          MCP 服务器(子进程/远端)
   │ initialize 请求(协议版本、能力)  ──►  │
   │   ◄──  initialize 响应(版本、能力)   │
   │ initialized 通知               ──►  │
   │ tools/list                     ──►  │
   │   ◄──  工具清单(name/description/     │
   │        JSON Schema)                  │
   │ ……工具经汇入管线进注册表……          │
   │ tools/call(参数)                ──►  │   执行
   │   ◄──  CallToolResult(内容/错误)     │
   │ （资源与提示词同理：resources/、prompts/）│
   │ elicit 表单请求                 ◄──  │   需要用户输入
   │   ──►  ElicitResult ──► 表单体系(form)│
   │ 连接关闭：stdin 关闭 ─► CLOSE_GRACE   │
   │   ─► SIGTERM ─► FORCE_KILL_AFTER     │
```

时序里的两个交互点值得点评。其一是 **elicit 的双向性**：MCP 服务器可以在执行中向用户要输入，OpenCode 把它接进自己的表单体系（form.ts 与 server 的 form handler），权限弹窗、TUI 的 dialog 与 Web 表单共用同一呈现通道——外部协议的交互需求被翻译进宿主的交互基础设施，而不是各自为政。其二是 **握手协商的降级语义**：协议版本不匹配（UnsupportedProtocolVersionError）与未授权（UnauthorizedError，触发 OAuth）在握手期就暴露，失败的连接不进入池——10.3 的"配置即连接"以健康连接为单元，半开连接不算数。stdio 的关闭时序（2 秒宽限、2 秒强杀）画在时序图尾部，作为"善后协议"的备忘。整张时序的工程要义：**协议交互的每一步都有超时、有降级、有善后**——外部进程会做任何事，客户端的每个 await 都要设防。

## 10.12 插件的配置面：声明、作用域与自描述

插件系统与配置系统的交界处有一个容易被忽略的设计问题：插件自己的配置怎么管理？OpenCode 的答案是插件复用宿主的配置管线而非自建：插件在定义里声明自己的配置形状（经 schema），配置值来自 opencode.json 的插件段（9.2 的发现与合并管线处理），归一化后随激活传入 setup——插件不直接读文件、不自己解析环境变量，配置语义与宿主完全一致（优先级、热重载、来源标记全部继承）。作用域上，插件可声明实例级（per-Location）或全局级（source-directory 与 instance 模块处理），实例级插件在 Location 生命周期内激活、随 Location 释放。自描述的另一个侧面是 **GUI bundle**（10.6）：插件可以携带前端资源，把配置界面也一并打包（dialog 呈现）——配置项、配置值、配置界面三者同源。这个设计的对照面是"插件自己管理配置"的常见做法（读自己的 yaml、监听自己的文件），后者的问题在与宿主合并语义冲突（全局与项目两级配置怎么办？热重载谁来触发？）——OpenCode 的答案是把插件配置纳入宿主配置的第一公民地位，一致性优先于插件自由度。这与第六章 6.1 的注册隔离一脉相承：**插件在行为上自由，在契约上受管**。

## 10.14 扩展面的测试与调试实践

扩展系统（MCP 与插件）的测试与调试有自己的特殊性：被测物一半在宿主内、一半在宿主外。宿主侧的设施是齐全的：codemode 有专项目录与测试（packages/core/test/codememode/ 与 codemode.test.ts——受限解释器的语义回归）；插件的注册隔离有机制保证（6.1 的 errors 收集），插件作者的调试循环靠注册错误日志与 Failure 查询（10.4 的 Generation 与 Failure 面）。宿主外的部分（MCP 服务器的行为）调试图谱包括：连接健康面（dialog-mcp 的连接状态、pool 的健康检查——10.3）、协议层错误的遗言收集（10.2 的 EXIT_WAIT 抓 stderr 尾部）、以及最有效的手段——**用最小的独立 MCP 服务器复现**（写一个只有一两个工具的 echo 式服务器，验证宿主管线正常后，再逐项替换为真实服务器，二分定位问题在宿主还是服务器）。插件侧同理：从空插件开始逐步加钩子，每次一个编织点（10.5 的表），失败即可归因于最近加的那一层。这套实践的通则：**扩展故障的定位靠把"宿主 × 扩展"的二维空间一维化**——固定一方、扰动另一方，把联合调试退化为单侧调试。另外值得一提：simulation 模式（14.2）对扩展开发同样友好——扩展可以在模拟后端上开发调试，不必每次都连接真实的模型与文件系统，这大幅降低了插件与 MCP 服务器的开发迭代成本。

## 10.16 扩展生态的健康度：五个可观测指标

扩展系统（MCP 与插件）的生态健康度可以量化观测，五个指标及其机理来源如下。**指标一：连接存活率**——MCP 连接池中健康连接的占比（10.3 的池语义），掉线率高的服务器暴露的是传输或子进程治理问题（10.2 的常量集就是为压这个指标设计的）。**指标二：注册失败率**——工具注册 errors 的占比（6.1 的隔离收集），坏 schema 的扩展在此现形，且不影响其他扩展（隔离的意义就是这个指标的分母稳定）。**指标三：激活延迟**——插件 Generation 完成的时间（10.9 的时序），退化通常意味着某个插件 setup 卡住（awaitActivation 的等待面）。**指标四：钩子注入率**——实际被插件改写的工具调用与请求的占比（6.4 的 before/after 触发面），异常高的注入率提示某个插件在过度干预，是行为异常的排查线索。**指标五：代切换频率**——Generation 的更替频次（10.4），频繁切换说明配置或插件更新在抖动（isDeepStrictEqual 的对比没压住噪声）。五个指标全部可以从既有设施推导（事件面与状态面，16 章），不需要额外埋点——**可观测性设施 reusable 到生态健康度的测量**是事件驱动架构的又一次红利。对使用者，这五个指标构成"扩展生态体检表"：安装一堆扩展之后看一眼，就知道哪些在帮忙、哪些在添乱。

## 10.18 扩展面的信任链：从安装到执行的信任传递

扩展代码与外部进程最终获得了影响会话的能力（10.5 的编织表），它们的信任从哪里来、如何传递，值得画一条完整的链。**链一：来源可信**——插件来自配置声明的来源（npm 包、目录，10.6 的 identity 与 source-directory），来源的校验与锁定是链的起点；**链二：装载可控**——加载与激活隔离失败（6.1 的 errors 收集、10.4 的占位），坏来源不能破坏宿主；**链三：行为受限**——插件的能力由钩子契约界定（10.5 的表），MCP 服务器的行为由协议面界定（工具、资源、提示词、表单），越界即协议错误；**链四：执行有闸**——扩展提供的能力最终经过权限断言（第八章的规则求值），扩展不能自带免检通道；**链五：变更可审计**——代切换、连接重建、注册错误都有事件与状态面（10.16 的指标）。五环链条的薄弱点分析：最难防的是**链一的供应链风险**（恶意的 npm 包）——它的缓解依赖生态手段（来源审查、锁定版本、最小安装），宿主内无法彻底解决，这正是 8.8 多层边界的又一实例：**扩展面的信任是分层的、可降级的，不是二元的全信或全不信**。给用户的安全建议由此清晰：安装扩展等同于给模型新增能力通道，应当像对待权限规则一样对待扩展清单——定期审计（10.16 的体检表）、最小安装、来源锁定。

## 10.19 本章小结

MCP 侧：双传输（stdio 的五个设防常量、Streamable HTTP 的 OAuth）、连接池的配置驱动重建、能力目录向统一工具注册表的汇入、JSON Schema 编解码的内存细节。插件侧：代与前缀差异的热重载协议、失败占位与不重试、根作用域的资源安全、全纵深的钩子编织表。两条面合起来回答了"OpenCode 如何既保持内核紧凑又容纳无限扩展"：内核只定义接缝（协议与钩子契约），接缝之外的无限可能性交给外部进程与插件代码。下一章转到传输与装配面：这些服务如何被装成一个 HTTP 服务器、如何被三种前端与 SDK 调用。
