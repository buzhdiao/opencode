# 第八章 · 权限与安全

## 8.1 威胁模型：为什么权限是 agent 的第一等公民

传统软件的权限系统防御"恶意用户"，agent 的权限系统防御一个更微妙的东西：**能力极强但会犯错的自动化决策者**。模型不是恶意的，但它会误判——把重要文件当成临时文件删掉、在错误的目录跑破坏性命令、把不该外发的数据 fetch 到提示词里。错误决策的后果与恶意攻击同等严重（工作区损坏、数据泄漏），因此 agent 的权限系统必须按"决策可能错"来设计，而不是按"决策是善意的"来设计。

OpenCode 的权限设计可以浓缩成三条公理。公理一：**缺省拒绝**（fail closed）。没有任何规则时，一切需要授权的动作都被拒绝——core/src/permission.ts 顶部的 missingAgentPermissions 规则集就是这条公理的代码形式：代理缺失权限配置时的默认规则集是 [{ action: "*", resource: "*", effect: "deny" }]（全部动作对全部资源拒绝）。安全系统必须从"全拒"出发靠规则放行，而不是从"全放"出发靠规则拦截——因为遗漏一条放行规则的代价是可用性问题（可修复），而遗漏一条拦截规则的代价是安全事故（可能不可逆）。公理二：**执行前断言**。权限检查发生在工具执行之前（第六章管线的阶段二入口），而不是事后审计——被拒的动作根本不会发生。公理三：**人是最终权威**。规则之外的授权决策回到用户，用户的批准可以被"记住"从而沉淀为规则——权限系统因此是一个**学习系统**：从零开始几乎全拒，随使用逐渐积累个性化的放行集。

## 8.2 规则模型：三元组与通配符

权限规则的数据结构极简：每条规则是三元组 (action, resource, effect)。action 是动作类别（如 edit、bash、webfetch）；resource 是资源模式（文件路径、命令模式、域名）；effect 是 allow、ask 或 deny 三值（Permission.Effect 枚举）。resource 支持通配符，匹配由 Wildcard 工具（core/src/util/wildcard.ts）完成。规则集是有序列表，求值按顺序找匹配，**最后一条匹配规则的 effect 决定结果**——后写优先，让"先宽后窄"或"先窄后宽"的叠加语义有确定解释（例如 allow "bash:npm *" 后跟 deny "bash:npm publish *"，则 publish 被拒、其他 npm 命令放行）。三值 effect 中 ask 是 OpenCode 的特色：它显式表达"这个动作每次都要问人"，与 allow（免问放行）和 deny（直接拒绝）区分——三值而不是二值，是因为"需要人工"是一种独立的安全语义，不能靠"不写 allow 规则"隐式表达（隐式表达的默认值会随实现漂移，显式 ask 让策略在配置文件里自解释）。

"整体禁用"的判定也有精确语义：当最后一条匹配规则是 resource: "*" 加 deny 时，该动作类别整体禁用（工具注册表据此在 snapshot 阶段直接隐藏工具，第六章 6.2 的前置过滤）。规则的三种来源合流成最终规则集：agent 自带规则（plan agent 的 deny 集）、项目配置（opencode.json 的 permission 段）、用户会话中保存的批准（PermissionSaved）。合流顺序与优先级是配置系统的一部分（第九章）。

用一张小表总结 effect 语义与典型来源：

| effect | 语义 | 典型来源 |
| --- | --- | --- |
| allow | 静默放行 | 用户选择"总是允许"后保存 |
| ask | 每次询问用户 | 项目配置的谨慎动作 |
| deny | 直接拒绝 | plan agent、组织策略、用户明令 |

## 8.3 两个原语：assert 与 assertNotDenied

权限服务的公开接口刻意只有两个方法：assert（permission.ts:113）与 assertNotDenied（permission.ts:115）。assert 是完整断言：对 (action, resource) 求值，allow 则放行、deny 则抛权限错误、ask 则发起批准流并等待用户回复——**它可能阻塞**（等人回复）。assertNotDenied 是轻量断言：只检查"是否被明确拒绝"，allow 与 ask 都放行——它用于"已经有更细粒度的交互在前面"的场景（比如 shell 命令已逐条弹过授权，后续的子检查只需确认没有 deny）。

两个原语的分工背后是对调用方负担的深思：assert 的调用方必须能承受"阻塞等待用户"，assertNotDenied 的调用方则承诺自己已处理交互。接口的小是刻意的——权限语义的全部复杂性被压进规则求值与批准流，调用方面对的只有两个动词。这遵循一条 API 设计公理：**安全机制的可组合性来自接口的最小性**，动词越多，调用方犯错的空间越大。

## 8.4 批准流：请求、回复与记忆

ask 分支展开成完整批准流。引擎侧构造 Permission.Request（含 ID、action、resource、消息、来源工具、可选的 diff 或命令详情等字段），经 Bus 广播为权限请求事件——**权限请求是一等公民事件**，因此三端（TUI、Web、桌面）都能弹出一致的授权界面，同一会话的多端观察者看到同一个待决请求。用户回复是 Permission.Reply 枚举，三个值：allow（本次放行）、always（放行并记住）、reject（拒绝）。reject 的语义不是"报错"而是"告知模型"：权限拒绝作为工具结果回灌，模型知道被拒及原因，可以调整方案——被拒也是信息，藏起来反而诱发盲目重试。

always 分支触发**记忆**：PermissionSaved 服务（core/src/permission/saved.ts，持久化在 permission/sql.ts 的表里）把这次批准固化为一条规则，写入已保存规则集。下次同样的 (action, resource) 匹配到这条 allow 规则，assert 直接放行不再打扰。记忆的写入位置经过规则合流进入后续所有会话——权限系统由此完成一次"从交互中学习"。值得注意 remember 的作用域设计：记住的是**模式**（比如"npm test 命令族"）而不是字面请求，否则规则库会退化为逐条请求的流水账；作用域过大又有安全代价（批准了 "bash:npm *" 等于放行 npm 的一切），因此保存的规则粒度是产品层反复调校的权衡点。

## 8.5 路径与命令：两类高频资源的专门策略

文件路径与 shell 命令是最高频的两类资源，各自演化出专门策略。**路径**：Location 定义了"界内"（工作目录树），file-access.ts（core/src/file-access.ts）提供路径访问的判定面；shell 等工具在执行前用 access.authorizeExternal 校验命令涉及的目录是否出界（第六章 shell 深读），出界目录需要显式授权。路径规则的通配符语义与文件系统语义的拼接处有大量细节（符号链接、路径归一化、大小写），通配匹配发生在**归一化后的绝对路径**上以避免绕过——"../"逃逸是路径权限的经典漏洞，归一化是第一道闸。

**命令**：ShellParse.scan 把命令串解析成具体命令列表（第六章已述），每条命令独立断言。这个设计的深层理由是**解析器对抗**：命令行是图灵完备的（变量、子 shell、管道、命令替换），任何"字符串包含检测"都能被构造绕过；解析成结构化命令列表后，规则匹配的对象从"文本"变成"语义单元"，绕过面大幅缩小。当然解析器本身也有盲区（动态构造的命令名），OpenCode 的兜底是 ask：解析不确定的构造退回人工批准——**在自动化与安全冲突时，把决策权降级给人**是权限系统的最终退路。

## 8.6 Agent 维度：build 与 plan 的权限表达

权限规则挂在 agent 维度上：每个 agent（第九章讲 agent 配置）有自己的规则集，同一会话内切换 agent 即切换权限语境。两个内置 agent 是这种表达的两个端点。build（默认，defaultID = "build"，core/src/agent.ts:10）携带宽松规则集，面向正常开发流；plan 是只读端点——默认拒绝文件编辑、bash 需批准（README 明示），实现上就是 plan 的规则集含相应 deny 与 ask 规则，进入 8.2 的同一套求值机制，**没有工具系统层面的特判**。这一点值得强调：能力差异被表达为数据（规则集）而不是代码（if agent == plan），新增一个"只能跑测试的 agent"只需写规则，不需要改引擎。子代理（general）的权限则继承调用方上下文并按定义收窄——权限集沿代理树**单调收窄**是另一条隐含公理：子代理的权限不得超过其调用者（否则一次 subagent 调用成为权限逃逸通道）。

## 8.7 写授权的交互形态：diff 预览

编辑类动作的授权请求携带**变更预览**：edit 工具的写授权展示 diff（edit.ts:321 附近），用户批准前看到的不是"edit /path/to/file"这样的抽象请求，而是将要发生的实际改变。预览把授权决策的依据从"信任模型的意图"升级为"审阅具体的差异"——同样的机制覆盖 write、patch 等写路径（file-diff.ts、patch.ts 的 diff 产物结构被权限请求复用）。这个设计回应了 agent 场景的一个特殊问题：写操作的破坏力取决于内容，而内容只有模型知道——预览是唯一让用户在批准前获得完整信息的通道。对"总是允许"的编辑（用户已 always），预览仍然在界面上展示（只是不再阻塞）——**放行不等于隐身**，观察者始终能看到发生了什么。

## 8.8 沙箱观：边界不止一层

权限系统是"授权面"，但安全还需要"隔离面"，OpenCode 的隔离观是多层边界叠加。第一层是**进程边界**：工具的子进程与引擎进程隔离，崩溃互不连带（第三章恢复协议）；MCP 服务器是独立进程（第十章），插件宿主隔离插件执行（第十章 supervisor）。第二层是**解释器边界**：Code Mode 的模型程序跑在受限 interpreter（packages/codemode/interpreter/）里——不开放网络与任意 import，可用面是显式声明的 stdlib 与工具命名空间。第三层是**权限断言面**：本章的规则系统，粒度到命令与路径。第四层是**凭据面**：Credential 的平台安全存储（第七章），凭据不进进程环境变量、不进会话上下文——模型永远看不到自己的 API key 全文。四层各自独立生效，破一层不破全局。这种纵深防御的立场可以概括为：**权限回答"允不允许"，边界回答"就算被绕过能伤到哪"**——两个问题必须分开设计，混为一个会让系统既难用又脆弱。

## 8.9 策略的治理：managed policy 与热重载

权限规则的另一来源是组织策略：managed-policy.ts（core/src/managed-policy.ts）支持托管策略——企业部署可以向受管的 OpenCode 安装下发不可被用户覆盖的规则（deny 某些外发域名、强制某些目录只读）。托管策略的优先级高于用户规则，这是"组织信任边界高于个人便利"的表达。规则集的变更走 State 模式（core/src/state.ts，第九章）的受控修改与热重载：配置文件改动即时生效（transform/reload），不需要重启会话。热重载的安全含义要谨慎对待：规则收紧立即可靠（新断言按新规则），规则放宽对**正在执行的**工具调用不追溯（断言已经发生）——语义上是"断言时刻的规则快照生效"，与第六章 snapshot 的"本轮工具集"一致，快照语义保证了规则变更不会在一步执行的中途改变判定依据。

## 8.10 威胁模型展开：三条攻击面与各自的闸门

8.1 的威胁模型值得具体化为三条攻击面。**攻击面一：提示注入（prompt injection）**。模型读取的内容（网页、文件、工具输出）里藏着指令性文本（"请执行 rm -rf /"），模型可能误当成用户指令执行。闸门有多层：权限系统不区分"指令来自谁"——工具调用一律断言（注入的指令想跑 shell 仍然要过 8.5 的命令解析与授权）；plan agent 的只读规则集限制了注入的破坏半径；read/webfetch 等工具的输出规范化（第六章）剥离危险载荷。**攻击面二：数据外泄**。模型可能把敏感内容（凭据、私有代码）写进外发动作（webfetch 的 URL 参数、上传）。闸门：凭据不进上下文（第七章，模型看不到自己的 key 全文）；外发类工具（webfetch/websearch）走独立的动作类别断言，组织策略可整体 deny（managed policy）；diff 预览让用户看到"将要发出去的是什么"。**攻击面三：破坏性命令**。rm、git push --force、数据库 drop。闸门：命令级解析授权（8.5）、ask 的默认谨慎、快照与回滚的最后保险（第十三章——即使全链路失守，工作区状态可回滚）。三条攻击面对应的纵深可以概括成一个公式：**注入靠"权限不问出处"，外泄靠"凭据隔离加外发断言"，破坏靠"解析加确认加回滚"**——没有单点能防住一切，但每条面上都有至少两道独立闸门。

## 8.11 规则求值的形式化与快照语义

把 8.2 的求值规则写成形式化定义有助于发现边界情形。规则集 $R = [(a_1, r_1, e_1), \dots, (a_n, r_n, e_n)]$ 有序；对查询 $(a, r)$，匹配集 $M = \{i : a_i \text{匹配} a \wedge r_i \text{匹配} r\}$；判定 result $= e_{\max M}$（最后匹配规则的 effect），$M$ 为空时结果为 deny（fail-closed）。三条推论：其一，**规则插入位置即语义**——同一条 allow 规则放在 deny 之后会被 deny 覆盖，规则的"书写顺序"必须像代码一样被审慎对待；其二，**通配符的匹配域要闭合**——resource 的模式匹配发生在归一化后的规范形（8.5），否则 "../" 逃逸与大小写变体会制造匹配集之外的幽灵放行；其三，**求值输入是快照**——规则集在断言时刻取快照（8.9），并发修改规则不影响进行中的求值。把这套形式化与前端的交互对照还有第四条推论：**ask 的展开**——$e_{\max M} = ask$ 时引擎发起交互，用户回复 allow/always/reject 三值中，always 的效果等价于"在用户规则集末尾插入一条 allow 规则并重求值"（语义一致性：记忆的规则服从与显式规则完全相同的求值机制，没有特权通道）。形式化的价值在这里兑现为可审计性：任何一次放行都可以还原为"哪条规则、在什么位置、为什么是最后匹配"。

## 8.12 审计与可解释性：权限系统的黑匣子

权限系统处置的都是"险些发生的事故"，事后审计因此是刚需。OpenCode 的审计面由三部分构成：**事件记录**——权限请求与回复走 Bus 广播并按聚合落库（第四章），谁在何时请求什么权限、用户答了什么，构成完整时间线；**已保存规则的溯源**——PermissionSaved 的每条规则来自某次"always"回复（8.4），规则的出生记录可查，配合第九章的配置来源标记，任何放行规则的出处（会话批准/项目配置/托管策略）可分辨；**拒绝的可解释性**——权限拒绝回灌给模型时携带原因（哪条规则拒绝），模型据此调整方案而不是盲目重试，同时用户在界面上看到的拒绝理由与模型看到的一致。审计面的设计立场：**权限系统不追求"零打扰"，追求"每次打扰可解释、每次放行可追溯"**。这与 8.7 的"放行不等于隐身"共同构成权限系统的透明性公理——安全机制不能依赖用户看不见的东西，可见性本身是安全属性。

## 8.14 Agent 树上的权限继承：单调收窄的形式化

8.6 说子代理权限"继承并收窄"，这里形式化。设调用方 agent 的规则集为 $R_{parent}$，子代理定义自身的规则集为 $R_{self}$，则子代理的有效规则集 $R_{child} = R_{parent} \oplus R_{self}$（拼接后求值，parent 在前 self 在后——self 的后位规则可覆盖 parent 的放行，但**不能解禁 parent 的 deny**：deny 在前位被后位 allow 覆盖时求值结果是 allow，这与"单调收窄"矛盾，因此收窄的真正实现是**先并集再取严**：对每个 (action, resource) 查询，取两个规则集求值结果中更严者（deny > ask > allow）。写成偏序：$\text{effect}(R_{child}, q) = \max_\text{strict}\big(\text{effect}(R_{parent}, q), \text{effect}(R_{self}, q)\big)$）。取严而不是拼接求值的理由正是防解禁：拼接求值下后位的 allow 会翻转前位的 deny，破坏收窄不变量。取严语义下可以证明**收窄定理**：对任意查询 $q$，$\text{effect}(R_{child}, q) \succeq_\text{strict} \text{effect}(R_{parent}, q)$（子代理不比父级更宽）——subagent 调用因此不可能成为权限逃逸通道，无论子代理的定义怎么写。多级嵌套（子代理再派生）时定理逐级归纳成立。这个形式化的工程价值：审阅一个子代理定义时只需看它的 $R_{self}$ 想"收什么"，不用检查它有没有"偷开什么"——取严语义让偷开在数学上不可能。

## 8.15 与操作系统权限模型的对照

把 OpenCode 权限与 Unix/OS 权限做一次系统对照，可以看到两者在设计目标上的深层分野：

| 维度 | 操作系统权限 | OpenCode 权限 |
| --- | --- | --- |
| 决策主体 | 进程身份（uid/gid） | 动作类别加资源模式 |
| 判定依据 | 静态归属（文件属主、位） | 有序规则集加动态批准 |
| 三值语义 | rwx 位（能力描述） | allow/ask/deny（处置描述） |
| 缺省 | 依系统（多 fail-closed） | 明确 fail-closed |
| 交互性 | 无（失败即错） | ask 可等待人 |
| 学习性 | 无 | always 沉淀为规则 |

分野的根源是**信任模型**：OS 权限回答"这个身份能不能碰这个对象"，身份由系统管、决策静态；agent 权限回答"这个来源不明的动作要不要放"，来源是概率性的模型决策，因此必须引入动态批准（ask）与学习（always）两个 OS 没有的维度。OS 的 rwx 位描述"对象能被怎么用"，OpenCode 的三值描述"决策者该被怎么管"——同样是三个值，语义坐标系完全不同。对照的实用价值在于迁移判断：OS 的成熟经验（最小权限、审计、能力分离）可以迁移，但"静态归属"的思维不能迁移——agent 场景里没有稳定可信赖的主体身份，只有需要持续被约束的决策流。这个判断也解释了 8.9 为什么需要快照语义与热重载的谨慎设计：规则集本身是高频可变物，OS 权限模型里没有对应物，只能自建语义。

## 8.17 安全的经济学：打扰成本与事故成本的平衡

权限系统的所有参数（哪些动作 ask、保存规则的粒度、托管策略的松紧）最终都在调节一个隐式比值：**打扰成本与事故成本之比**。打扰成本是用户批准弹窗的时间与心流中断（每多一个 ask，交互损耗一分）；事故成本是错误动作的期望损失（动作概率乘损失量级）。设计的目标不是两个成本最小化（它们互相拉扯），而是**在给定事故容忍度下最小化打扰**。OpenCode 的几个机制都可以在这个框架下重新解释：三值 effect 让"需要人"精确化（只对事故成本高的动作 ask——8.2）；"记住"机制让高频安全动作的打扰一次性摊销（8.4 的 always）；diff 预览提高单次批准的信息密度（8.7——同样的打扰买到更多的审查价值）；plan agent 把探索期的打扰结构性降为零（只读模式无写授权——8.6）。反之，打扰成本的失控是权限系统被弃用的头号原因：弹窗太多用户会机械式全点 allow，权限系统退化成仪式——**过度打扰会训练出糟糕的用户行为**，这是安全设计里真实的反馈回路。因此参数调校的实操建议：从较严起步（信任建立期打扰多一点），随"记住"的积累自然松弛；破坏性动作永远保留 ask；定期审计保存的规则（8.12 的溯源面）回收过宽的授权。安全系统的健康度不看规则多少，看这个比值是否在合理区间。

## 8.19 边界失效的推演：如果某一层被穿透

8.8 的四层边界值得做一次失效推演（假设每一层单独被穿透，看损失控制在哪里）——这是安全设计里比"正常流程"更有信息量的练习。**推演一：权限断言被绕过**（假设模型构造出未过断言的执行路径）。兜底：进程边界仍在（子进程崩溃隔离）、快照仍在（工作区可回滚，13.3）、审计面仍在（8.12 的事件记录暴露异常）。**推演二：解释器被逃逸**（Code Mode 程序突破受限面）。兜底：解释器进程与宿主隔离（10.2 的进程边界原则同样适用）；逃逸后的代码仍是宿主权限下的普通代码，权限断言管它。**推演三：凭据泄漏**（key 被读到）。兜底：凭据不进上下文（7.7）意味着泄漏渠道主要是本地进程层面，平台安全存储缩小面；泄漏后的止损是轮换（rotate，7.10 的恢复动作）。**推演四：批准被误操作**（用户手滑 allow 了危险请求）。兜底：diff 预览降低误批准概率（8.7）、快照回滚止损（13.3）、危险动作的 ask 不可被 always 一次性放行过宽（保存粒度，8.4）。推演的结论值得记下：**四层中没有一层是"绝对信任层"**——每一层都被默认可能失效，每层失效都有下一层兜底，且最外层的兜底（快照与审计）永远存在。这与纵深防御的标准定义一致，但工程上真正的难点是让"兜底"真的实现（快照真的在做、审计真的落库）——OpenCode 把兜底做成了默认开启的机制而不是可选配置，这是它的安全立场里最值得肯定的一条。

## 8.20 本章小结

权限系统的设计可以复述为五个决策：缺省拒绝的公理（missingAgentPermissions）、三元组有序规则集与三值 effect、两个最小原语（assert/assertNotDenied）、批准流的三种回复与"记住"的学习机制、多层边界（进程、解释器、权限、凭据）的纵深。它的哲学立场是：模型是能力极强但会犯错的协作者，系统的职责不是假设它正确，而是让每个错误决策在到达世界之前有一个被拦截或被确认的机会。下一章讲规则的另一半来源——配置系统，看 opencode.json 与 AGENTS.md 如何被发现、归一化、合并与热更，以及贯穿 core 的 State 模式如何让"配置"成为可审计的状态机。
