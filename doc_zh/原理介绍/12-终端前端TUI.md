# 第十二章 · 终端前端 TUI

## 12.1 终端渲染为什么特殊：cell 网格上的响应式 UI

终端不是画布，是**字符网格**：渲染的最小单位是 cell（一个字符位），每个 cell 有字符、前景色、背景色、样式位。TUI 的一切视觉表达——面板、滚动、动画、diff 高亮——都是在 cell 网格上画出来的。这带来四条与 Web 完全不同的工程约束：布局单位是字符不是像素（等宽假设下宽度计算要精确到字符显示宽度——东亚全角字符占两格，emoji 占一到两格且依赖终端）；没有浏览器排版引擎（换行、裁剪、对齐全部自己算）；刷新是全屏重绘或差量更新（性能敏感：一秒六十帧的平滑滚动意味着每帧要在时间片内算完整个可视区）；输入是字节流不是 DOM 事件（按键序列要自己解析成语义事件，方向键、功能键在不同终端的转义序列不同——parsers-config.ts 正是按键解析的配置面）。

OpenCode 的解法是**用响应式框架写终端 UI**：packages/tui 基于 solid-js 与 @opentui（终端渲染引擎，tui/package.json 的依赖）。solid-js 提供细粒度响应式（信号驱动的最小更新），@opentui 把 solid 的渲染树落到 cell 网格上。这个组合的价值与 Web 前端用框架的理由同源：声明式描述 UI，让"状态到画面"的映射由框架维护，人只写状态逻辑。终端场景比 Web 更需要这个：会话视图是高频更新面（token 流、工具进度、 spinner 动画），手写重绘的差量逻辑会迅速失控。

## 12.2 应用骨架：路由、上下文与运行时

TUI 的骨架在 packages/tui/src：app.tsx 是应用根（组件树的组织），runtime.tsx 是运行时接线（服务连接、事件订阅、全局 provider），index.tsx 是启动入口。路由面在 routes/：home.tsx 是主页（会话列表、新会话入口），routes/session/ 是会话路由（进入某个会话的完整视图）。跨组件共享的状态通过 context/ 提供：context/event.ts 是事件订阅的上下文（把 server 的事件流接入 solid 的信号系统），context/program-status.ts 跟踪程序状态（连接中、运行中、空闲），context/thinking.ts 跟踪模型的思考状态（思考流的显示），context/editor.ts 与 context/session-tabs-model.ts 分别服务编辑器与多会话标签。这个结构是标准的响应式分层：**事件流入 context（信号），组件订阅信号（视图），用户操作发起请求（副作用）**——与第十一章的协议视图严丝合缝：TUI 是协议的又一个消费者，没有任何"直达内核"的捷径。

连接层还有两个健壮性组件值得点名：reconnecting.tsx（断线重连的界面表现——配合 event-feed 的补历史语义，重连后画面无缝续上）与 retry-provider.tsx（请求重试的上层包装）。它们的存在提醒我们：TUI 是网络客户端，server 可能重启、连接可能断——前端的状态机必须把"暂时失联"建模为正常状态而不是崩溃。

## 12.3 会话视图：一切的核心

会话视图是 TUI 的主体，由三层组成。外层是 frame 与 tabs：session-frame.tsx 提供会话框架（边框、状态栏、布局容器——border.ts 与 layout.ts 提供边框与布局原语），session-tabs.tsx 与 session-tabs-rail.tsx 提供多会话标签（一个窗口里并行观察多个会话——第三章的多会话拓扑在 UI 上的对应物）。中层是消息时间线：消息按类型渲染（用户消息、助手文本、工具调用卡片、思考流、权限请求、检查点分界），工具卡片的内容由 util/tool-display.ts 决定展示形态（哪些工具显示命令行、哪些显示文件路径、哪些显示进度条），util/collapse-tool-output.ts 实现**长输出的折叠**（shell 输出几百行时折叠为一行摘要加展开提示——屏幕是稀缺资源，折叠是终端的信息密度管理，与第五章的上下文折叠形成"屏幕折叠 vs 上下文折叠"的对偶：一个为人的注意力省空间，一个为模型的窗口省 token）。diff 类内容有专门渲染器 patch-diff.tsx（编辑授权预览、文件变更展示——第八章 diff 预览的终端呈现）。内层是微交互：one-cell-spinner.tsx 与 spinner-frames.ts（单 cell 的旋转动画——进度指示只占一个字符位，这是终端审美与空间经济学的结合）、shimmer-text.tsx（微光文字，用于"进行中"的占位）、fade-in-text.tsx 与 masked-text.ts（淡入与掩码文本）。

会话视图的渲染性能有一个隐藏约束：**token 流的帧率**。模型每秒吐几十上百个 token，若每个 token 触发一次完整重排，终端会闪成频闪灯。响应式批处理（solid 的信号去抖）与工具输出的缓冲（util/scroll.ts 的滚动管理）共同把更新频率压到终端可接受的程度——前端性能优化的第一课在这里依然是"别让高频源直接驱动渲染"。

## 12.4 输入区：prompt 组件与自动补全

输入区（component/prompt/）是用户交互最密集的组件。index.tsx 是主输入框（多行编辑、粘贴、附件）；autocomplete.tsx 是自动补全（@ 引用文件、/ 斜杠命令、模型切换等上下文相关的补全面板——补全数据来自 server 的文件与命令目录）；local-attachment.ts 处理本地附件（图片粘贴进会话）；metadata.tsx 显示输入的元信息（模型、token 估算）；move.tsx 处理输入的移动（跨会话搬运）；draft-stash.ts 是草稿暂存（切换会话时输入内容不丢——多会话并行的细节体贴）。输入区与编辑器的关系是组合：prompt 内嵌编辑器（12.5），编辑器提供光标、选区、撤销等文本原语，prompt 补全会话语义（@引用、/命令、发送）。

## 12.5 编辑器双轨：自研与 zed 集成

packages/tui/src 的编辑器有两条轨：editor.ts 是自研编辑器（在 @opentui 上实现的多行文本编辑组件）；editor-zed.ts 与 editor-zed-sqlite.{bun,node}.ts 是 **zed 集成轨**——把编辑委托给 zed 编辑器的后端（zed 是高性能编辑器，其编辑核心可以作为外部服务），sqlite 变体处理状态持久化，bun/node 双文件处理运行时差异。"双轨"的理由是体验与可控性的权衡：自研轨零外部依赖、行为完全可控；zed 轨提供专业级编辑体验（多光标、正则替换、极快大文件）。用户可以选择哪条轨作为自己的输入体验——这与模型接入层的"provider 可替换"、PTY 的"实现可替换"（第二章装配替换清单）构成同一模式：**关键交互面都留了可替换的轨**。

## 12.6 对话矩阵：二十余个 dialog 的职责地图

TUI 的交互大量以"对话框"呈现（按了什么键，弹出什么面板），component/ 下的 dialog-* 文件构成一张功能地图：dialog-model.tsx 与 dialog-model-free.tsx、model-options.tsx（模型选择——第七章 provider 体系的 UI 面）、dialog-agent.tsx（agent 切换——第九章 agent 配置的消费）、dialog-mcp.tsx（MCP 服务器状态——第十章连接池的观察窗）、dialog-permission 相关（权限批准，第八章批准流的终端呈现）、dialog-session-list.tsx 与 dialog-session-rename.tsx（会话管理）、dialog-worktree-name.tsx、dialog-workspaces.tsx、dialog-workspace-file-changes.tsx（worktree 与 workspace 管理——第十三章的 UI 面）、dialog-config.tsx（配置查看）、dialog-theme-list.tsx（主题）、dialog-open.tsx（打开会话）、dialog-pair.tsx（配对——第十一章 ServerPairing 的终端流程）、dialog-shell-output.tsx（后台 shell 输出查看——第六章作业化的观察面）、dialog-image-preview.tsx（图片预览——终端里看图需要特殊协议（sixel/kitty graphics），media-source.ts 处理媒体源协商）、dialog-skill.tsx、dialog-stash.tsx、dialog-status.tsx、dialog-update.tsx（更新提示）、dialog-experiments.tsx（实验特性开关）、dialog-highlights.tsx、dialog-error-details.tsx 与 error-component.tsx（错误展示）、dialog-debug.tsx 与 devtools-bar.tsx（调试面）、migration-overlay.tsx（第四章迁移过程的覆盖层）、plugin-route-missing.tsx、panel-host.tsx（面板宿主）、command-palette.tsx（命令面板——一切功能的键盘入口）。这张地图验证了第三章的一句话：三端消费同一份事件流——每个 dialog 都只是某个领域状态的投影加一个回传端点。

## 12.7 终端 UI 工程学的底层原语

ui/ 目录是终端渲染的数学层：subcell.ts（子 cell 精度——比字符更细的渲染单位，用于进度条与图形的亚字符绘制，例如用部分块字符画出半个 cell 的进度）、one-cell-motion.ts（单 cell 动画）、animation.ts（动画调度）、border.ts（边框绘制）、layout.ts（布局计算）、pane-resize.ts（面板调整——分割视图的拖拽）、spinner.ts（spinner 状态机）。util/ 是支撑层：string-width.node.ts（字符显示宽度——东亚宽度表与 emoji 宽度，等宽假设的基石）、scroll.ts（滚动）、marquee.ts（跑马灯）、delayed-presence.ts（延迟出现的 UI——避免闪烁式提示）、single-flight.ts（单飞——并发的同类请求合并，与第三章 run-coordinator 同构的客户端版）、persistence.ts（本地持久化）、signal.ts、system.ts、path-format.ts、form.ts、project.ts。

这些原语的存在说明一个事实：**终端 UI 的"简单"是错觉**——没有浏览器兜底，每一层（宽度、换行、颜色、动画、输入）都要自己实现。OpenCode 的选择是把这些实现集中成原语库，上层组件只做组合。这个分层的纪律性（原语不掺业务、组件不做像素计算）是 TUI 代码保持可维护的原因。

## 12.8 注意力系统与外围

TUI 的独特交互问题是**用户会离开终端**：后台任务跑完了、权限请求在等人、长任务失败——用户可能在另一个窗口。attention.ts 与 attention-sounds.{bun,node}.ts 实现注意力通知（终端铃声/系统声音提醒；双文件处理 Bun 与 Node 的音频后端差异），audio.ts 管音频。外围还有：feature-plugins/（TUI 的特性插件——前端也有自己的插件面）、mini/（迷你模式界面）、theme/（主题系统，dialog-theme-list 呈现）、simulation/（模拟模式的前端配合——第十四章测试）、devtools/（开发调试）、config/ 与 plugin/（TUI 层配置与插件接线）、clipboard.ts（剪贴板，跨平台差异处理）、logo.ts（启动画面）、model-preference.ts（模型偏好记忆）。

## 12.9 折叠与信息密度：终端的稀缺资源管理

12.3 提到 collapse-tool-output 折叠长输出，这里把"终端信息密度管理"作为一个设计专题展开。终端屏幕同时向用户呈现的是**一次会话的全部可见历史**，而 agent 会话的内容产出速度（token 流、工具输出、diff）远超人的阅读速度——信息密度管理因此是 TUI 的核心问题，OpenCode 用一套分级的呈现策略应对：**完整层**（用户消息、简短助手文本、最近工具结果全量呈现）、**折叠层**（长工具输出折叠为一行摘要加可展开提示——collapse-tool-output 的职责）、**省略层**（历史深处的工具输出只留标题行）、**替代层**（diff 不全文渲染而用 patch-diff 的紧凑视图，检查点用分界标记替代被摘要的历史——与第五章"屏幕折叠对偶上下文折叠"呼应）。分级策略的决策因素是**信息的新近度与类型**：越新越完整、越结构化越紧凑（diff、表格有紧凑语义；散文没有）。这套策略与第五章的上下文管理构成一个完整的"双面信息经济学"：对模型省 token（压缩），对人省注意力（折叠），两者共享同一个价值判断函数——"这条信息对下一步决策/理解有多重要"。前端实现层面的支撑是 util/scroll.ts（滚动锚定——折叠展开时不跳屏）与 util/marquee.ts（超长单行的跑马灯显示）。

## 12.10 键盘驱动的交互模型与命令面板

终端 UI 是键盘驱动的，交互模型的完整性取决于"任何功能都有键盘路径"。OpenCode 的实现围绕三层组织。第一层是**直接键位**（编辑、发送、Tab 切 agent、Esc 中断——README 提到的 Tab 切换即此类），键位绑定可配置（配置系统的 keybinds 段，第九章）。第二层是**对话框层**（12.6 的 dialog 矩阵——模型选择、会话列表、主题等以面板形式呈现，键盘导航选择）。第三层是**命令面板**（command-palette.tsx——一切功能的统一入口，模糊检索命令名执行），它是键盘驱动模型的完备性保证：记住一个入口就记住一切。三层的分工符合渐进披露原则：高频操作直达（一层），中频操作进面板（二层），低频与长尾操作检索（三层）。autocomplete（prompt 组件）可以看作第四个特化入口——上下文敏感的补全（@ 引用文件走 fff 检索，/ 命令走命令目录，模型切换走 model 目录）。键盘模型的实现支撑是 parsers-config.ts（按键转义序列解析的配置——不同终端的按键编码差异在此抹平）。一个值得注意的细节：所有交互层的操作最终都汇到同一个 client API（第十一章生成物）——键盘路径与 Web 端的鼠标路径在协议层汇合，UI 形态不同而语义面唯一。

## 12.12 多会话并行：标签、状态隔离与注意力分配

12.2-12.3 的骨架是单会话视图，12.6 的 tabs 组件引入了多会话维度，这里展开多会话并行的前端语义。**状态隔离**：每个会话标签对应一个独立的本地投影（12.1-12.3 的"事件流到信号"管线按会话 ID 分轨——context/session-tabs-model.ts 管理标签模型），切标签只是切换可见投影，后台会话的事件继续流入并更新各自投影——切回来的瞬间画面是完整的（重连协议 11.4 的"补历史续实时"在标签切换的微观场景同样成立）。**注意力分配**：多会话的核心人因问题是"用户只看一个，其他会话的状态变化怎么传达"，attention 系统（12.8）回答它——后台会话出现需要人介入的事件（权限请求、任务完成、出错）时触发注意力提示（终端铃声、attention-sounds 的平台后端），前台会话不受干扰；util/delayed-presence.ts 的"延迟出现"防止瞬时状态闪烁误报。**资源约束**：每个投影都在消耗渲染资源（不可见标签的事件仍在产生），前端对不可见标签做渲染降级（只更新数据不重排画面——折叠到摘要级），可见标签恢复完整渲染——与 12.9 的折叠策略同构，只是作用在"会话"粒度而不是"输出"粒度。多会话并行的整体设计可以概括为：**数据层全量更新（不丢事件），渲染层按需降级（省资源），注意力层事件驱动（省人）**——三个层的策略共同保证"同时开五个会话"是可用的工作方式而不是资源灾难。

## 12.13 启动路径与性能预算

TUI 的启动路径值得走读一遍，因为它决定了用户的第一印象（终端工具的启动慢半秒都会被记住）。链路：入口（index.tsx）→ 运行时装配（runtime.tsx：连接 server、订阅事件流）→ 应用根（app.tsx）→ 路由（home 或直接恢复会话）→ 首屏渲染。首屏的渲染预算管理有三处：logo.ts 与 spinner（启动期的视觉反馈——"连接中"的状态可见，等待不空白）；主题与解析器的配置在装配早期完成（parsers-config.ts、theme/——避免首屏后样式跳变）；会话列表与最近状态按需拉取（home.tsx 的首屏只取列表元数据，完整历史进会话后才拉——与第四章的游标投影衔接）。性能预算的另一个重要场景是**恢复大历史会话**：几千条消息的会话打开时全量渲染会卡顿，投影层的分页与 12.9 的省略层策略（只完整渲染可视区附近）共同把首帧时间与消息总量解耦。前端性能的通则在这里全部适用但有一个终端特化：终端的"帧"是字符重绘，成本模型与像素不同（cell 写入比像素便宜，但全屏重绘仍有成本），因此优化焦点是**最小重绘范围**（solid 的细粒度信号天然对齐这个目标——状态变了才重算对应 cell）。

## 12.15 前端的错误态与降级策略

前端的健壮性集中在"server 不可用或半可用"时的表现策略，这是终端客户端最重要的容错面。**断连态**：reconnecting 组件（12.2）给出明确的"失联中"视觉状态，重连由事件回放协议支撑（重连即补历史，11.4），用户无需手动刷新——降级策略是"冻结视图加自动恢复"，不弹错误对话框（错误对话框会打断心流，而断连多数是自愈的）。**半可用态**：server 活着但某些服务降级（MCP 服务器掉线、模型目录过期）——对应的面局部显示降级标记（dialog-mcp 的连接健康、模型列表的过期提示），其余功能照常——降级粒度到"服务"而不是整个应用。**错误态**：业务请求失败（权限拒绝之外的真实错误）——error-component 与 dialog-error-details 呈现结构化错误（11.12 的协议错误形态），错误可展开看细节（面向排障）、可关闭（面向继续工作）。**崩溃态**：前端自身崩溃——error-component 的边界捕获防止整屏白屏（React/Solid 的错误边界语义），崩溃边界外仍可操作。四个状态构成前端的"可用性阶梯"：正常 → 局部降级 → 冻结等待 → 明确报错，每一级都有对应的组件与协议支撑。阶梯的设计哲学与 16 章呼应：**前端是系统的哨兵**，它的容错表现直接决定用户对整个系统的可靠性感受——server 崩了但 TUI 优雅冻结并自动恢复的体验，远好于 server 明明正常而 TUI 报错闪烁。

## 12.17 终端兼容性：探测、降级与能力协商

终端不是同质环境（12.1 提过按键序列差异），兼容性面包括：**渲染能力**（256 色/真彩色的支持差异、sixel/kitty graphics 的图片协议有无——dialog-image-preview 与 media-source 的能力协商，12.6）、**按键编码**（方向键、功能键、组合键的转义序列因终端而异——parsers-config.ts 的解析配置面）、**尺寸语义**（单元格像素比例影响图片缩放，subcell 的亚字符绘制依赖字体渲染的近似假设）、**行为差异**（滚轮转发、焦点事件、剪贴板访问的授权——clipboard.ts 的平台路径）。兼容性的工程策略是**探测加降级**：启动时探测能力（环境变量、终端查询响应），能力缺失时降级到最低公分母（图片预览降级为路径提示、真彩色降级到 256 色近似）——降级是静默的、渐进的，用户感知到的是"这个终端里功能少一点"而不是"这个终端里全是错误"。与 Web 前端的渐进增强思想完全同源，只是探测对象从浏览器 API 换成终端协议。兼容性还有一层测试含义：14 章的 simulation 模式对终端同样有价值——模拟一个标准终端环境让视觉回归测试不依赖真实终端差异，而 parsers-config 的解析正确性则用转义序列的单测覆盖。兼容性清单的维护原则与 9.16 的配置演进一致：**探测结果决定功能开关，开关必须有默认值，默认值必须可用**。

## 12.19 延伸：终端前端的未来接缝

以三个"可能的接缝"结束 TUI 章（均为基于现有机制的推断，标注为作者分析）。**接缝一：更深的会话组件复用**——packages/session-ui 已承载 TUI 与 Web 的共享会话组件，随其覆盖面扩大，三端渲染同一会话的代码重叠度将继续上升，"同一份数据流加同构组件"向"更多同构组件"演进。**接缝二：图形能力的深化**——图片协议（sixel/kitty graphics）的成熟与普及（12.6 的 media-source 能力协商）可能让 diff 预览、图表、截图在终端内呈现得更接近 GUI 体验，subcell 的亚字符绘制是这条路上的先声。**接缝三：LSP 的回归通道**——doc_zh/components/04 分析过 v2 移除内置 LSP 的历史与接缝（edit 工具的 TODO），若 LSP 以插件或独立 runtime 回归，TUI 的诊断呈现（悬停提示、错误下划线在 cell 网格上的表达）将是一个自然的新组件面——diagnostics 事件走 Bus、渲染走 patch-diff 同类的组件模式。三个接缝的共同点：它们都**不需要改动 TUI 的分层**（原语、组件、context、协议消费），只是往既有层里添内容——分层架构对演化的友好性，在这里得到最后的例证。

## 12.20 本章小结

TUI 的架构可以概括为一句话：**把浏览器级的前端工程（响应式框架、组件分层、状态管理、网络客户端）搬进 cell 网格的约束里**。它的分层是：@opentui 的渲染原语（ui/）→ solid 组件（component/、routes/）→ context 状态（事件投影）→ 协议消费（client 生成物）。终端特有的工程问题（宽度、动画、注意力、折叠、按键解析）都有专门的原语与组件。与第十二章的会话视图对应，Web 形态（packages/app）复用同一协议与大量共享组件（packages/session-ui、packages/ui）——三端一致的承诺在 UI 层的落法不是"同一份代码"，而是"同一份数据流加同构的组件语义"。下一章看一圈卫星系统：那些让 agent 能力半径变大的支撑设施。
